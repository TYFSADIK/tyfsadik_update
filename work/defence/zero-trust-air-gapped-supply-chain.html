Zero-Trust Air-Gapped Software Supply Chain

A pipeline that builds container images reproducibly, generates SBOMs with syft, signs everything with sigstore/cosign, then transfers artifacts across a simulated one-way data diode into an offline Harbor registry, with controls mapped to Canadian Centre for Cyber Security guidance.

2026 Defence In Progress

Overview

Software that ends up on disconnected networks, ships, forward operating bases, classified enclaves, still has to come from somewhere. This project builds the supply chain that gets it there safely: every artifact is built reproducibly, inventoried with a software bill of materials (SBOM), cryptographically signed, and only then moved across a simulated one-way transfer (a data diode) into an offline registry that disconnected environments pull from.

The core problem is trust across a boundary you cannot query back through. Once an artifact crosses into the air-gapped side, the low side can never ask "did you get it intact?", so every check, hash verification, signature validation, SBOM diff, has to happen either before the transfer or entirely on the receiving side. That constraint shapes the whole design, and it is exactly the constraint real isolated networks live with.

This is a DevOps-engineering take on a defence-grade problem. I am mapping each control to published Canadian Centre for Cyber Security guidance, including ITSAP.10.096 (how supply chain attacks work and how to defend against them) and the Cyber Centre's recommendations on verifying software integrity, so the project doubles as a practical study of how that guidance turns into pipeline code. Everything runs on open-source tooling in my homelab; there is no weapons logic, no classified data, and nothing here touches a real operational network.

The low side is a normal CI pipeline with one extra property: the build is reproducible, meaning the same source and pinned toolchain produce a bit-identical image digest. The verification gate refuses to release anything whose cosign signature, vulnerability scan, or SBOM policy check fails. The bundle that crosses the diode is a tarball containing the image, its SBOM, its signatures and attestations, and a manifest that ties them together by digest, so the high side can re-verify everything without ever talking back.

Figure 2: store-and-forward transfer with hash-chain integrity checking and re-verification on the high side.

  • No acknowledgements: a real data diode physically cannot send data back, so the sender retransmits on a schedule and the receiver detects gaps by chunk numbering rather than requesting resends.
  • Hash chain: each chunk carries the hash of the previous chunk, so a missing or corrupted chunk anywhere invalidates the chain root and the bundle is quarantined, never partially imported.
  • Re-verification on arrival: the high side runs cosign verify and cosign verify-attestation itself, because trusting the low side's checks would defeat the point of a zero-trust boundary.
  • Simulation approach: my homelab diode is two VMs connected by a UDP-only forwarder with firewall rules blocking all return traffic, plus a small forwarder daemon doing the chunking. Not hardware, but it enforces the same one-way contract.

How I'm Building It

01
Reproducible builds

A reference service builds through BuildKit with pinned base-image digests, locked dependency files, and SOURCE_DATE_EPOCH set from the commit timestamp. Two clean builds must produce the same image digest before anything else proceeds.

02
SBOM generation

syft runs against the built image and emits both SPDX and CycloneDX documents, stored as registry artifacts alongside the image so consumers get the inventory without re-deriving it.

03
Signing and attestation

cosign sign covers the image digest, and cosign attest attaches SLSA-style provenance (builder identity, source commit, build parameters) as an in-toto attestation. I use keyless signing on the connected side and a local key pair whose public half crosses with the bundle.

04
Diode simulation

A Python forwarder on the low VM chunks the release bundle, hashes each chunk, and streams over UDP to the high VM. nftables rules on the receiver block every outbound packet, enforcing the one-way property at the firewall, not just by convention.

05
Offline registry and re-verification

The receiver verifies the hash chain, runs cosign verify and cosign verify-attestation locally, pushes to Harbor, and re-scans with grype using a vulnerability database that itself crossed the diode on a schedule.

06
Guidance mapping

Each control is documented against the Cyber Centre publication it implements, so the repo reads as both a working pipeline and a traceable compliance artifact.

How Defence Could Implement This

Disconnected and classified networks are the norm in Canadian defence, not the exception, and they all face the same question this project answers: how do you patch and update software you cannot reach. A realistic implementation looks like:

  • Classified enclave updates: DND networks at different classification levels already exchange data through accredited cross-domain solutions and hardware diodes. A signed, SBOM-inventoried bundle format gives the receiving enclave independent proof of what it just imported, instead of trusting the transfer process alone.
  • Ships and deployed platforms: RCN vessels and forward units under operations like LENTUS or deployed task groups sync over intermittent satellite links. A store-and-forward model with hash-chain integrity tolerates dropouts, and reproducible builds let a ship verify that the update it received matches the exact bits the vendor or ADM(IM) produced.
  • NORAD modernization and infrastructure hardening: the Cyber Centre's guidance on supply chain integrity (ITSAP.10.096, plus its advice on verifying software updates) maps directly onto SBOM generation, signature verification, and provenance attestation. A pipeline like this is how that guidance becomes an auditable control rather than a checklist item.
  • Coalition interoperability: SBOMs in SPDX or CycloneDX are the emerging common language for allied software exchange, so a Canadian pipeline that already speaks them slots into combined programs without translation work.

The homelab version uses simulation throughout. An operational version swaps my UDP forwarder for an accredited hardware diode and my self-signed CA for the departmental PKI, while the pipeline stages stay identical.

How to Build This Yourself

  1. Get reproducibility first. Pin every base image by digest, lock your dependencies, set SOURCE_DATE_EPOCH, and build twice in clean environments. If the digests differ, diff the layers and fix that before anything else.
  2. Generate an SBOM on every build. syft registry.example/app:1.2.3 -o spdx-json takes minutes to add and immediately shows you what you are actually shipping.
  3. Sign digests, not tags. Tags move; digests do not. cosign sign the digest and store the signature next to the image so it travels with it.
  4. Attach provenance. An in-toto attestation recording the source commit and build parameters is what lets a reviewer answer "where did this binary come from" without trusting you.
  5. Simulate the diode with two VMs. A UDP-only forwarder plus firewall rules blocking return traffic reproduces the real constraint. Do not cheat with TCP, the lack of ACKs is the whole lesson.
  6. Verify on the receiving side. Re-run cosign verify and the hash-chain check after transfer. Zero-trust means the high side trusts the math, not the sender.
  7. Stand up Harbor offline. It stores images, signatures, and SBOMs together, and its robot accounts model the pull credentials a disconnected cluster would use.
  8. Map controls to published guidance. Read the Cyber Centre's supply chain and patch management guidance and write one line per control saying where your pipeline implements it. That document is half the value of the project.
Scope and ethics: this is a personal homelab project using open-source tools, sample applications, and simulated network isolation. It contains no weapons logic, no targeting, and no classified material; it is a DevSecOps pipeline study.
