Decision Black Box

A tamper-evident audit layer for human-in-the-loop decisions in a simulated airspace-deconfliction scenario: a hash-chained, signed, append-only log in the style of certificate transparency, a replay tool that reconstructs any decision state, and OPA policy-as-code checks on every entry.

2026 Defence In Progress

Overview

When a decision support system recommends something and a human approves it, someone has to be able to answer afterwards: what did the operator see, what did the system recommend, which policy version was in force, and who signed off? This project is a flight recorder for decisions, built around a fictional airspace-deconfliction simulator. Every recommendation, override, and approval is written to an append-only log that cannot be edited or quietly reordered after the fact.

The core is a hash-chained, signed log modelled on certificate transparency (RFC 6962): each entry includes the hash of the previous one, the log operator signs Merkle tree heads, and auditors can request inclusion and consistency proofs. On top of that sit two tools: a replay engine that rebuilds the exact state of the simulated airspace picture at any entry in the log, and OPA policy-as-code checks that evaluate every decision against the rules of engagement simulated for the scenario (for example: no deconfliction approval without two-operator confirmation).

Why bother: accountability and responsible AI are treated seriously in Canadian defence circles, and DND/CAF has published AI strategy commitments around traceability and human oversight. I wanted to practice the engineering behind those commitments. Everything here runs on simulated data I generate myself. There is no weapons logic, no real targeting information, and nothing classified anywhere in this project.

Figure 1: simulated sources feed the ingestion API; every event is policy-checked, chained, signed, and stored before it can be replayed or audited.

The ingestion API is the only writer. An event (sensor observation, recommendation, operator decision) is validated, sent to the OPA sidecar for a policy verdict, then appended to the log. The append is atomic with the hash-chain link: the new entry commits the SHA-256 of its canonical JSON encoding plus the previous entry's hash, so any edit to history invalidates every subsequent link. Periodically the signer folds the log into a Merkle tree, signs the tree head with an Ed25519 key, and publishes it, which is what lets an outside auditor verify the log without trusting me.

Figure 2: verification proves the log is append-only before replay reconstructs the state at any entry.

  • Inclusion proof: an auditor gets the Merkle path for a single entry and checks it against a signed tree head, the same proof a certificate transparency monitor runs.
  • Consistency proof: two signed tree heads are compared to prove the log only ever grew; this is the property that catches silent history rewrites.
  • Replay: events are folded in order through a deterministic state machine, so state at entry N is always reproducible. The same code path backs the audit dashboard and any after-action review.

How I'm Building It

01
Event schema and append-only store

A versioned JSON schema for the three event types (observation, recommendation, decision), stored in PostgreSQL with a role that physically cannot run UPDATE or DELETE. Inserts compute the chain hash in a trigger-checked transaction.

02
Merkle tree and signer

A Go service that folds pending entries into a Merkle tree every N seconds, signs the tree head with an Ed25519 key held behind a software seal, and publishes signed heads to a gossip-style endpoint so forks are detectable.

03
OPA policy gate

Rego policies evaluate every decision event before it is committed. Current example: a simulated deconfliction approval requires two distinct operator identities within a time window. The verdict (allow/deny plus policy version) is logged alongside the event, so policy changes are visible in history.

04
Scenario simulator

A seeded Python generator produces fictional aircraft tracks, the rule-based stub issues recommendations (re-route, hold, handoff), and scripted operators approve or override. Deterministic seeds mean any reviewer can reproduce an incident exactly.

05
Replay tool and audit dashboard

A CLI (replay --entry N) folds events through the state machine and renders the picture at that moment; a small web UI shows the log, proof status, and policy verdicts per decision.

How Defence Could Implement This

The accountability pattern here is deliberately generic, which is what makes it transferable to real CAF and NORAD contexts:

  • Command and control audit: any C2 system that surfaces machine recommendations (air tasking, track classification aids, logistics triage) could write the same three event types to a tamper-evident log, giving boards of inquiry and after-action reviews a trustworthy record of who saw what and decided what.
  • Responsible AI assurance: DND/CAF AI strategy commitments call for traceable, human-accountable AI. OPA-style policy gates are a concrete mechanism: rules like "human confirmation required" stop being documentation and become enforced, logged code.
  • Cross-network integrity: signed tree heads are small and one-way friendly. A consistency proof can cross a classification boundary where the full log cannot, so a higher-side auditor can verify a lower-side log was not rewritten without the data itself moving.
  • Multi-party verification: in NORAD or coalition settings, each party can hold signed tree heads from the others, so no single operator can quietly edit a shared decision record.
  • Domestic operations: the same pattern applies outside combat contexts, for example Operation LENTUS tasking, where provincial and military decisions interleave and a clean audit trail matters for public accountability.

None of this requires new sensors or new platforms. It is an integrity layer over systems that already exist, and it can be prototyped at homelab scale, which is exactly what I am doing with simulated data.

How to Build This Yourself

  1. Define your events first. Pick three event types for your scenario (I use observation, recommendation, decision) and write a versioned JSON schema before any storage code.
  2. Make the store append-only for real. In PostgreSQL, create a writer role with INSERT and SELECT only, no UPDATE, DELETE, or TRUNCATE. Test that deletion fails; do not assume it.
  3. Add the hash chain on insert. Each row stores the SHA-256 of its canonical encoding plus the previous row's hash. Verify with a full-table rescan that recomputes every link.
  4. Read RFC 6962, then build the Merkle tree. Implement leaf hashing with domain separation prefixes, fold entries into a tree, sign the tree head with Ed25519, and expose inclusion and consistency proof endpoints.
  5. Write one OPA policy early. A single Rego rule (for example, two-person approval) wired into the write path teaches you the whole pattern. Log the verdict and policy version with every event.
  6. Build replay as a fold, not a query. State at entry N is a pure function of events 1 through N. Deterministic seeds in your simulator make replay output reproducible for reviewers.
  7. Attack your own log. Write a test that edits a middle row, one that deletes rows, and one that forks the tree. All three must be caught by verification, or the design is decoration.
Scope and ethics: the scenario is fictional and the tracks are generated. There is no weapons logic, no real targeting data, and nothing classified in this project. The point is the integrity and accountability machinery, which applies to any human-in-the-loop decision system.
