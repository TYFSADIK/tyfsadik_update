Mini Airspace Deconfliction Manager

A small-scale UAS airspace manager on my bench: ESP32 tracker beacons plus ArduPilot SITL simulated drones, dynamic geofences, predicted-conflict alerts, and a human-in-the-loop override for every resolution.

2026 Defence Simulation In Progress

Overview

When a dozen uncrewed aircraft share the same block of sky, somebody - or something - has to keep them apart. The Canadian Army is studying exactly this problem: how to manage airspace shared by many uncrewed aircraft at once, a discipline known as airspace deconfliction. With the Defence Drone Initiative (launched July 23, 2026) promising fleets of cheap tactical drones, and DRDC trials like Operation NANOOK pushing more uncrewed systems into the same training areas, deconfliction stops being an airline problem and becomes a platoon-level one.

This build explores that problem safely and cheaply. It is mostly simulation: several ArduPilot SITL drone instances fly missions on my homelab and stream MAVLink telemetry into a manager I wrote. A handful of physical ESP32 tracker beacons stand in for live tracks, so there is real RF hardware in the loop. On top of that track picture sit the two things a deconfliction system actually does: predict conflicts before separation is lost, and enforce dynamic geofences the operator can draw, move, and resize live.

The design rule that shapes everything: the manager is advisory, never autonomous. It proposes resolutions - climb, hold, reroute - and a human approves every single one. That is deliberate: it mirrors how military airspace control actually works, and it makes the system safe to experiment with at any scale.

How I Built It

01
Simulated traffic

I run 3-4 ArduPilot SITL instances on a homelab node, each launched with sim_vehicle.py -v ArduCopter and its own instance offset (-I1, -I2, ...) so every drone gets separate MAVLink ports. Each one flies an autonomous mission - a waypoint file loaded through MAVProxy or uploaded with pymavlink - so the sky over the virtual field is genuinely busy.

The manager connects to each instance's telemetry output over UDP using pymavlink, subscribes to GLOBAL_POSITION_INT and VFR_HUD, and folds every aircraft into a single track model: id, position, velocity, heading, timestamp, source.

02
Physical beacons

Four cheap ESP32 boards act as tracker beacons. Each runs a small Arduino sketch (built with the Arduino-ESP32 core) that broadcasts a stand-in position packet over Wi-Fi UDP to the manager at a fixed rate - the same track model the SITL instances produce, so the ingest path cannot tell simulated from physical.

The beacons matter less for their data than for their reality: they force the pipeline to deal with dropped UDP packets, clock skew, and intermittent power - the exact nuisances simulated traffic never has. A breadboarded controller with an OLED display sits next to them showing beacon health and the active alert count.

03
Conflict engine

The core of the system. For every tracked aircraft I propagate a predicted trajectory forward - current position plus velocity, with waypoint awareness where the mission is known - and compute the time to closest point of approach (TCPA) between every pair of tracks. If the predicted closest approach falls inside a configurable separation bubble, and it happens inside a lookahead window, the engine raises a conflict alert before separation is actually lost.

The pairwise check is O(n²) but trivial at this scale; the interesting work is in tunable parameters - bubble radius, vertical separation, lookahead horizon - and in keeping alerts stable rather than flapping as tracks jitter.

04
Dynamic geofences

The geofence service holds 3D keep-in and keep-out volumes - cylinders and boxes with floor and ceiling altitudes. The operator can create, move, and resize a volume live from the dashboard, and every incoming track update is tested against all active volumes; a violation raises an alert immediately.

This mirrors the real use case: an exercise safety officer declaring a temporary restricted volume over a live-fire range, or shrinking the keep-in box as weather moves in. The geometry checks are plain point-in-polyhedron tests run per track update.

05
Human-in-the-loop resolutions

When the conflict engine fires, the manager proposes resolution manoeuvres - an altitude change for one track, a hold at the current position, or a reroute around the predicted conflict point. But the alert queue is advisory, never autonomous: nothing is sent to any aircraft until a human clicks approve.

Approved resolutions go back to the SITL instance as MAVLink commands through pymavlink - a guided-mode altitude change, a loiter, or fresh waypoints - and the dashboard tracks whether the approved manoeuvre actually cleared the conflict. Rejected or ignored proposals are logged with their outcomes, which feeds the test-case review.

06
Scripted test cases

Deconfliction logic is only worth trusting if it survives repeatable scenarios, so I scripted a set of conflict cases: two aircraft on crossing paths at the same altitude, a pair converging in altitude on parallel tracks, and a deliberate geofence breach. Each scenario is a MAVProxy/pymavlink script I can run repeatedly with the same initial conditions.

Every run produces a result sheet - the paper copies on the bench in the photo - that gets signed off with what the system detected, when it alerted, and how the resolution played out. The sheets log time-to-alert and a qualitative resolution-quality grade, and a scenario only counts as passing when the alert precedes the separation loss with margin.

07
Integration with the common operating picture

The manager does not live alone: its tracks and alerts publish into the multi-domain common operating picture over the same MQTT/Zenoh bus the other defence nodes use. Air tracks become one more layer alongside the passive radar, acoustic, and ground sensors, and the COP's human-in-the-loop queue is the same one this manager writes to.

Testing & Metrics

Testing is scenario-driven, built around the scripted cases from step 06. The protocol for each run:

  • Time-to-alert: elapsed time from scenario start (or geofence creation) to the alert appearing in the queue. Target: the alert must land before predicted separation loss, with enough margin for a human to read, decide, and approve.
  • Alert precision: false-alarm rate across quiet multi-aircraft runs with no designed conflict; the goal is zero spurious alerts from normal waypoint traffic and beacon jitter.
  • Resolution quality: for each approved manoeuvre, did the predicted closest approach actually move outside the separation bubble, and did the aircraft complete the manoeuvre as commanded? Graded on the signed result sheets.
  • Geofence responsiveness: time from a live volume edit (create / move / resize) to enforcement on the next track update. Target: immediate on the following telemetry packet.

Results are in progress: the scenario harness runs and the result sheets are being filled in, but I am not publishing numbers until every scripted case has been run repeatedly and the sheets are consistent.

Legal & Safety Notes

Simulation-first by design: this build is deliberately mostly software. ArduPilot SITL carries all flying while the legal side stays simple - real flying waits for Transport Canada compliance (registration, pilot certification, and airspace checks), the same rule that gates the thermal SAR drone build.
Scope: this project coordinates only my own aircraft and simulated traffic. The ESP32 beacons broadcast stand-in positions on my own network; nothing here tracks, commands, or interferes with anyone else's aircraft.
