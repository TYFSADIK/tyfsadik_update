Overview

The CD-DAR Testbed is a planned, bench-scale version of the capability National Defence describes in its Cyber Defence - Decision Analysis and Response project: see every device on a network, collect what the defence tools report into one trusted store, show it as a single cyber picture, and help an analyst decide what to do, fast. This page is a build guide; nothing here is built or tested yet.

CD-DAR is one of the largest cyber projects in the Defence Capabilities Blueprint, with a listed funding range of $250 million to $499 million and Assistant Deputy Minister (Digital Services) as the sponsoring group. Its goal is to improve decision support and security across DND/CAF networks so Defensive Cyber Operations (DCO) can detect, analyze and respond to threats in time. That is the same problem every security operations centre faces, at a much larger scale and with much higher stakes.

This build takes the public requirement list and answers each line with open-source tools on my own homelab: Zeek and Suricata on the wire, Wazuh on the hosts, my own Daru SIEM holding a copy of everything, OpenSearch as the data repository, Grafana as the operating picture, Velociraptor for remote forensics, and TheHive for cases and response. On top sits an AI-assisted SOC layer: a Python detection engine, a correlator that turns alerts into incidents, and a local language model on vLLM that explains each incident with evidence. The design rule throughout: the tools rank and explain, a person decides. The model only suggests, code checks what it says, and every response needs human approval and is written to a tamper-evident log.

This is independent research, not part of the CD-DAR project. It uses only public information, synthetic data and my own machines. Where it stands: the whole testbed is now written as code: 120 files of Proxmox scripts, cloud-init, Docker stacks, data pipelines, six Python services, response playbooks and 62 automated tests that pass. What is left is the physical build and the first full run; nothing on this page is measured yet.

Lab Layout

The whole lab runs on one Proxmox node behind its own router VM. Four networks keep the roles apart: management for the security tools, a notional command network of victims, an attacker network that can only reach the victims, and a physical field network behind the deployable kit, which comes home over WireGuard.

How the sensor sees traffic without a physical tap: the lab bridge is set to forget MAC addresses instantly (bridge-ageing 0), so it floods every frame to every port like an old hub. The sensor VM's capture card is a member of the victim and attacker VLANs, so Zeek and Suricata see everything between them. That trick is fine for a lab and never for production; the field kit uses a real switch mirror port instead.

VLAN 20 command (notional)10.10.20.0/24dc01, ws01, srv01, srv02Only the security agent ports, and the attacker's C2 ports so emulation agents can call back
VLAN 66 adversary10.10.66.0/24atk01The command network only; never management, never the internet during tests
Field network (physical)10.10.30.0/24kit01 and field devicesThe internet through its own uplink; the lab only through WireGuard to Kafka, Wazuh and Velociraptor

The router's firewall is default-deny with one switch, lab-internet on|off: on while packages install, off before any attack test runs. Every address and name in the lab is synthetic.

What the Build Will Prove

A homelab cannot stand in for a national defence network, and this one will not claim to. What it can prove, with published methods and data, is narrower and useful:

  • One picture from many tools works. Network, host and forensic data from different tools land in one normalised repository and one operating picture, without analysts switching between consoles.
  • Context speeds up decisions. Ranking alerts by asset criticality and ATT&CK stage, with a stated reason, is measured against a plain severity-sorted queue for time to triage and missed attacks.
  • Discovery finds what the inventory misses. Planted unknown devices are found and flagged, and discovery completeness is measured against the known asset list.
  • Forensics can be done remotely. Evidence is collected from a distant host in a measured time, with hashes that prove it was not changed.
  • AI can help without being trusted. A local model's incident summaries are measured for how often they pass evidence checks, how much of the evidence they cite, and how often the analyst agrees, while the model is never allowed to act.
  • A person stays in charge. No response action runs without approval, and every decision can be replayed from the tamper-evident log.

Architecture

Figure 2: sensors, host agents, discovery and the deployable kit all feed one pipeline into the Cyber Data Repository; the operating picture and decision scoring read from it; an analyst approves every response, and every approval and action is written to the tamper-evident log.

The data path is built around one rule: every tool writes into the same repository in the same schema. Zeek and Suricata watch traffic from a switch SPAN port, Wazuh and Daru watch the hosts, and discovery keeps NetBox current. Vector ships everything through Kafka, normalising it to OCSF on the way, so a login event from a firewall and a login event from a server look the same to the analyst.

On the decision side, a small scoring service reads new alerts, joins them to the asset's criticality in NetBox and to the ATT&CK technique, and writes back a score with a reason the analyst can read. The operating picture shows that ranked list beside the asset map. When the analyst opens a case, TheHive suggests playbook steps, Velociraptor collects evidence remotely, and nothing that changes a system runs until a person approves it.

Every event is stored in one schema, the Open Cybersecurity Schema Framework (OCSF): Zeek and Suricata flows become Network, DNS or HTTP Activity, and every alert from Suricata, Zeek, Wazuh or the discovery service becomes a Detection Finding with its ATT&CK technique. The mapping is written in Vector's language and ships with its own tests, so a broken mapping fails before it reaches the lab.

Decision Scoring

CD-DAR asks for "reliable contextual analysis to support decisions". In this build that is a small scoring service. For every finding it multiplies four factors, each between 0 and 1, and takes the fourth root so the result reads on a 0 to 100 scale:

FactorWhere it comes fromExample
Asset criticalityNetBox custom field, 1 to 5, set per asset in inventory.yamldc01 = 5 (every login depends on it)
Attack stageThe ATT&CK tactic, from Discovery 0.40 to Exfiltration 0.95 and Impact 1.00Credential Access = 0.80
ConfidenceThe sensor's own confidence, 0 to 100%Suricata rule metadata "confidence High" = 90%
SeverityThe sensor's severity, OCSF 1 to 5Wazuh level 12 = critical

Multiplying means one weak factor pulls the score down hard, which is what an analyst would do in their head. If several different techniques hit the same asset within 30 minutes, the score rises by up to 15 points and says so. Scores of 60 or more open a TheHive alert; 80 or more are P1.

Every score carries its reasons, in plain words, into the alert the analyst reads:

[P1 92] LSASS access on dc01
- Asset dc01 has criticality 5/5.
- ATT&CK T1003.001 (Credential Access) is at attack stage 0.80.
- Detection confidence is 90%.
- Sensor severity is critical.
No response action has been taken.

The AI-Assisted SOC

Scoring single alerts is not enough: an analyst needs to see an attack as one story, with the evidence, and decide quickly. Four pieces turn the testbed into an AI-assisted security operations centre.

1. Detection engine: rules as code

A small Python engine reads every normalised event from Kafka and applies YAML rules, alongside the rules Suricata, Zeek and Wazuh already ship. Three rule types cover most needs:

TypeFires whenShipped rules
MatchOne event meets every conditionAdmin share opened over SMB (T1021.002); any connection from the attacker network into the command network (T1046)
ThresholdN events, or N distinct values, per source in a windowPort scan, 40 ports in 2 minutes (T1046); host sweep (T1018); SSH password guessing (T1110.001); DNS tunnelling, 10 long names in 10 minutes (T1048.003)
SequenceFinding A, then finding B, on the same host in a windowCredential access then lateral movement (T1021); discovery then exfiltration (T1048)

2. Incident correlation

The correlator groups scored findings into incidents. Two findings join the same incident when they share an IP address, in either role, or a user account, within 30 minutes. A finding that links two open incidents merges them, so a workstation that is attacked and then attacks the domain controller stays one story. The incident score is the highest finding score plus 3 for every extra ATT&CK tactic it reached. TheHive gets one alert per incident, updated as it grows, with the full timeline, instead of one alert per detection.

3. AI investigation with a local model

When an incident scores 60 or more and goes quiet for 90 seconds, the investigator asks a local language model, served by vLLM on my own GPU (Qwen2.5-7B-Instruct by default), to explain it. No incident data leaves the lab. Because attackers control some of the text the model reads (DNS names, user agents, file names), the model is treated as untrusted:

  • Evidence is numbered and fenced. Each finding becomes E1, E2, and so on; network context becomes C1, C2. Control characters are stripped and long fields are cut. The prompt says the evidence is data, never instructions.
  • Every claim must cite evidence that exists. A statement with no valid evidence ID is removed.
  • Suggested actions come from an allow-list (block an IP, isolate a host, collect triage, reset credentials, monitor), and the target must appear in the evidence. In the test suite, a DNS name that tells the model to "block 8.8.8.8" produces a suggestion that the checks remove.
  • One retry, then give up. If nothing grounded is left, the model gets the list of problems once; after that the analyst works the incident without a summary.
  • Recorded. The model name, the prompt hash and the answer hash go into the approval log, so every summary can be traced.

This is the shape of what lands in the TheHive alert (format from the test suite, not a lab result):

### AI investigation (model: cddar-llm, suggestions only)
An outside host scanned dc01, then ws01 showed LSASS access and DNS exfiltration.

What happened
- atk01 scanned dc01 (E1)
- Credentials were read from LSASS on ws01 (E2)
- Data left ws01 over DNS (E3)

Suggested actions (an analyst decides):
- block_ip on 10.10.66.10: source of the scan (E1)
- isolate_host on ws01: stop exfiltration (E3)

Checks removed 5 item(s) from the model's answer:
- recommended_actions[1]: target '8.8.8.8' is not in the evidence, removed
- recommended_actions[2]: 'wipe_disk' is not an allowed action, removed

4. Human-approved response playbooks

ResponderWhat it does
TriageVelociraptor collects client info, running processes, network connections and scheduled tasks
Contain hostCollects triage first, then quarantines the host so it can only talk to Velociraptor. If collection fails, it stops before the quarantine
Release hostRemoves the quarantine
Block IPAdds the address to the lab router's block list, refusing anything outside the lab ranges

These are Cortex responders. They run only when an analyst starts one on an observable in TheHive, and every step is written to the approval log. I chose custom playbooks over a full SOAR platform such as Shuffle to keep the lab small and every action easy to audit.

Daru and Splunk-compatible ingestion

Every normalised event is also sent to my Daru SIEM over Splunk's HTTP Event Collector protocol, so Daru's search, dashboards and alerts work on the whole lab. The pipeline also accepts Splunk HEC itself, so any forwarder or script that speaks it can send logs in, and they go through the same detection engine. Incident reports bring it together: one command writes the timeline with evidence IDs, the checked AI summary, every decision and response step, and the approval log's chain check.

The Operating Picture

The main Grafana dashboard has twelve panels, each answering one question an analyst asks. A second dashboard, Incidents and AI Investigation, lists incidents by score with their kill chain and checked AI summary, and tracks how often the model's answers pass the checks, how much evidence they cite, and how long they take.

  • P1 findings, all findings, unknown devices, decisions logged: is anything on fire right now?
  • Decision queue: every finding ranked by score, with the asset, ATT&CK technique and the reasons. This replaces the plain severity-sorted list most consoles show.
  • Findings by ATT&CK tactic and over time by priority: how far along is an intruder, and is it getting worse?
  • Most-targeted assets and top talkers: where is the activity concentrated?
  • Network activity per sensor: a flat line means a sensor or its link is down, which matters for the deployable kit.
  • Discovered devices and the approval log: what is on the network, and who decided what.

How to Build It

The build splits into a physical part, which I do by hand over about one weekend, and a scripted part, which the repository does. Full step-by-step instructions, with the exact menu path for every setting, are in the docs/ folder of the public repository on GitHub.

Step 1: The physical part

  1. Proxmox node: free about 71 GB of RAM (53 GB with the lite profile) and 1 TB of disk on one node, enable Snippets on the local storage, and install git, rsync and genisoimage.
  2. Windows ISOs: download the free Windows Server 2022 and Windows 11 Enterprise evaluation images and virtio-win.iso, and upload them to Proxmox.
  3. Home router: give the lab router VM a DHCP reservation. Forward UDP 51820 to it only if the kit will sit on a different network.
  4. Field kit: install Ubuntu Server 24.04 on the mini PC with user lab and the Proxmox node's SSH key, then wire it as in Figure 6.
  5. Switch mirror port: on a TP-Link Easy Smart switch, Monitoring > Port Mirror: enable, destination port 2, sources ports 1 and 3 to 5, ingress and egress. Netgear calls it System > Monitoring > Mirroring.
  6. GPU machine for the model: any box with an NVIDIA GPU of 16 GB or more, the NVIDIA driver and the NVIDIA Container Toolkit. An existing vLLM or other OpenAI-compatible server works too.
  7. Windows installs: install Windows Server in dc01 and Windows 11 in ws01 from the Proxmox console, loading the vioscsi driver so the disk appears.

Step 2: Build the lab (scripted)

cp lab.env.example lab.env          # set node name, storage, SSH key
./proxmox/setup-lab-bridge.sh        # isolated VLAN-aware bridge in hub mode
./proxmox/create-lab.sh              # router, core, soc, sensor, srv01-srv10, atk01
./proxmox/create-windows-shells.sh   # dc01 and ws01, with a CD of lab scripts

Step 3: Windows domain (three scripts from the CD)

E:\01-dc01-promote.ps1 -SafeModePassword "..."   # dc01: lab.cddar.test forest
E:\02-dc01-populate.ps1                          # dc01: synthetic users, audit policy
E:\01-ws01-join.ps1                              # ws01: join the domain

Step 4: Deploy everything else

./deploy/deploy.sh all          # 30 to 60 minutes
./deploy/deploy.sh passwords    # every web console login
./deploy/deploy.sh status       # every service should say "up"
./deploy/deploy.sh llm lab@192.168.1.60   # vLLM on my GPU machine for the AI investigator

That one command generates every password and key, then sets up the router (responder key, WireGuard configs), the core (OpenSearch, Kafka, Vector, Grafana, NetBox with the asset list, detection engine, scorer, correlator, AI investigator, discovery, approval log), the SOC (Wazuh, Daru, TheHive, Cortex with the block and playbook responders, Velociraptor, and links them all), the sensor (Zeek, Suricata with ET Open rules), the Linux agents and Caldera. Then E:\install-agents.ps1 on both Windows machines adds Sysmon, the Wazuh agent and the Velociraptor client.

Step 5: The field kit

./deploy/deploy.sh kit 192.168.1.50   # the kit's home-network address
./deploy/deploy.sh internet off       # close the lab before any attack test

The kit becomes the gateway and DHCP server for its field network, opens WireGuard to the lab, installs k3s and runs Zeek, Suricata and Vector as one pod, using the same configuration files as the lab sensor.

Step 6: Test it

.\run-atomics.ps1 -RunId ...    # on ws01: Atomic Red Team, 15 techniques, scored the same way
./deploy/deploy.sh ddil        # kit outage test: healthy, degraded, cut, restored

Metrics to Publish

  • ATT&CK technique coverage: share of emulated techniques detected.
  • Mean time to detect and mean time to respond, for the ranked queue and the plain queue.
  • False-positive rate per day of normal lab activity.
  • Asset discovery completeness against NetBox, and time to flag a planted unknown device.
  • Remote forensic collection time per host, and hash verification of every artefact.
  • Operating picture freshness: time from event to screen.
  • Analyst workload: alerts per hour, time per triage, and NASA-TLX score.
  • Deployable kit: events lost during link outages, target zero.
  • Incident correlation: alerts per incident, and how many separate alerts the analyst no longer has to open.
  • AI investigation: share of answers that pass the evidence checks, evidence coverage, analyst agreement with the assessment, items the checks removed, and latency.

Frequently Asked Questions

What is CD-DAR?

Cyber Defence - Decision Analysis and Response (CD-DAR) is a National Defence project listed in the Defence Capabilities Blueprint. It will acquire defensive cyber capabilities for DND/CAF networks: network discovery, integrated cyber defence tools, an authoritative Cyber Data Repository, a Cyber Common Operating Picture, attention to human factors, and remote cyber forensics. The listed funding range is $250 million to $499 million, with implementation starting in 2026/2027 and final delivery in 2030/2031.

Is this build part of the CD-DAR project?

No. This is an independent, personal research build. It uses only the public project description to shape a bench-scale testbed on homelab hardware. It is not affiliated with, funded by, or submitted to DND, the CAF or ADM(DS), and it touches no government network or data.

Which open-source tools does the testbed use?

Zeek and Suricata for network sensing, Nmap and NetBox for discovery, Wazuh with Sysmon and auditd on hosts, the Daru SIEM, Vector and Kafka feeding OpenSearch as the OCSF Cyber Data Repository, a Python detection engine and incident correlator, a local language model on vLLM for incident investigation, Grafana for the cyber COP, TheHive and Cortex for cases and approved response, Velociraptor for remote forensics and quarantine, and Caldera with Atomic Red Team for testing.

Does the AI take any action on its own?

No. A local model on vLLM writes an incident summary and suggests actions, and code checks every claim: each statement must cite evidence that exists, each suggested action must be on an allow-list, and each target must appear in the evidence, or it is removed. The checked summary goes into the TheHive alert. Nothing runs until an analyst starts a responder, and the model's answer is recorded in the tamper-evident approval log.

How will detection and response be tested?

With adversary emulation in an isolated lab segment: MITRE Caldera and Atomic Red Team run known ATT&CK techniques against my own machines. The testbed is scored on ATT&CK coverage, time to detect, time to respond, false-positive rate, asset discovery completeness and remote forensic collection time.

Is anything built or measured yet?

The code is. The whole testbed is written as scripts, configuration, six Python services and response playbooks, with 62 automated tests that pass. The physical build and the first lab run come next, so no capability is measured yet; results will be added to the status table as each one is.
