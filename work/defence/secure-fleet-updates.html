Secure Robot-Fleet Updates

Every node in my fleet boots only signed code, accepts only updates signed by an offline key, and rolls a bad update back automatically - then I prove it in a freezer, because that is where Canadian robots actually work.

2026 Defence Hardware In Progress

Overview

The Army's MINERVA challenges say it plainly: Canada has bought foreign robotic systems of mixed quality, with components from unstable supply chains. The Defence Drone Initiative (launched July 23, 2026) makes supply-chain integrity a theme rather than an afterthought. A drone or ground robot that will accept any firmware image anyone hands it is a liability, no matter how good its sensors are.

This build connects my DevOps discipline to hardware. The fleet is small - the Raspberry Pi nodes from my rover and sensor builds - but the rules are the ones a real program needs:

  • Every device boots only signed code - a secure-boot chain from the bootloader up, with a TPM 2.0 measuring each stage and holding the disk keys hostage to that measurement.
  • Every update is signed by an offline key - Ed25519 keys that live on YubiKeys, not on any machine connected to a network.
  • A bad update rolls itself back - A/B partitions with health checks, so a broken image never strands a node in the field.

And because these robots are meant to operate in the cold - the same cold the MINERVA documents complain about - the whole update-and-rollback cycle gets validated in a freezer, not just on a warm bench.

Two trust chains meet here. The boot chain (signed bootloader, signed kernel, TPM measurement) guarantees the node runs only what I signed. The update chain (offline signing, per-device policy, A/B slots with automatic fallback) guarantees I can change what it runs without ever being able to brick it. A node that misses a campaign because its link is down simply picks the bundle up when the link returns - the same DDIL store-and-forward pattern as my field nodes.

How I Built It

01
Secure boot chain on the Pi

I enabled Raspberry Pi secure boot so the chain from the EEPROM bootloader to the kernel is signature-checked end to end. Using the usbboot tooling, I generated the device key pair, programmed the public key hash into the Pi's OTP, and signed boot.img (which bundles the kernel, initramfs, and device tree) with the private key. With SIGNED_BOOT=1 set in the EEPROM config, the board refuses to execute any boot image that does not verify - an unsigned or tampered kernel simply never runs.

The private half of that key lives offline. The Pi that has OTP programmed is now a device that will only ever boot my code, which is exactly the property the rest of the stack builds on.

02
TPM 2.0 measured boot and sealed disk keys

The TPM 2.0 add-on board rides the Pi's SPI header. Each boot stage - bootloader, kernel, initramfs, rootfs hash - extends a Platform Configuration Register, so the TPM ends up holding a hash chain of exactly what booted. I inspect it with tpm2-tools (tpm2_pcrread) and verify the event log matches expectations.

The root filesystem is LUKS-encrypted, and the LUKS key is sealed to the TPM's measured state with systemd-cryptenroll --tpm2-device bound to a PCR policy. The consequence is the one that matters: if anyone swaps in a modified image, the PCRs change, the TPM refuses to unseal, and the tampered image cannot decrypt user data. Tampering is not just detected - it is useless.

03
Signing infrastructure: YubiKey, SBOM, cosign-style verification

Update images are signed with Ed25519 keys held on a YubiKey - the private key was generated on the device and cannot be exported. The build machine talks to it over PKCS#11 / OpenPGP-card interfaces only for the signing operation itself. The backup key lives on a second YubiKey, generated the same way, stored separately and offline.

Every image build also produces an SBOM with syft (SPDX output, committed alongside the image), and the signature is verified cosign-style before any node will install: signature over the image digest, checked against the known public key, with the SBOM as the provenance record of what is inside. This is the same pipeline discipline as my zero-trust air-gapped supply chain project, applied to physical devices instead of containers.

04
A/B over-the-air updates with automatic rollback

Each node runs an A/B partition scheme: two rootfs slots, one active and one idle. An update is a signed bundle (RAUC format - rauc bundle to build, rauc install on the node) that writes to the inactive slot, so the running system is never touched mid-update. The bootloader is configured to try the new slot exactly once.

After the trial boot, a health-check service has to confirm the essentials - system services up, TPM attestation clean, heartbeat to the fleet server established - and only then marks the slot good with rauc status mark-good. If any check fails or the mark never arrives, the bootloader falls back to the last-known-good slot on the next reset, automatically. A bad update is an inconvenience measured in one reboot, not a bricked field node.

05
Fleet server: identity, policy, campaigns

The homelab runs the fleet server. Every node enrols with its own device identity (a per-device certificate, with the TPM holding the node's private key where possible), so an update campaign is targeted and auditable: which devices, which image version, what rollout order. Policies are per-device - a rover in active testing gets builds more often than a deployed sensor node.

Delivery is store-and-forward. Nodes that are offline - or behind a link that drops - do not miss a campaign; the bundle waits and transfers when the link returns, resuming partial downloads rather than restarting. These are the same DDIL patterns as my DDIL-proof DevOps build, because a robot on a degraded mesh and a laptop on hotel Wi-Fi are the same problem.

06
Cold-chamber validation

The update-and-rollback cycle is tested cold, not just on the bench. The node goes into the chest freezer (shared with the cold-soak rig) with the temperature logged alongside the update logs, and I run the full sequence at freezer temperatures around -20 °C: enrol, download, verify, install to the idle slot, trial boot, health check, mark-good - and then the same again with a deliberately bad image to force a cold rollback.

This matters because flash and SD cards genuinely behave differently in the cold - slower, higher error rates, occasional marginal reads at temperature extremes. A rollback mechanism that has only ever been tested at room temperature is an assumption, not a capability.

07
Chaos tests

The final gate is deliberately breaking things. I corrupt an image mid-transfer (truncated bundles, flipped bytes in the payload), kill power mid-flash with a switched power strip at random points in the write, and feed the node a correctly-structured bundle with an invalid signature. Each fault is injected repeatedly, not once.

The pass criterion is absolute and binary: after any fault, in any order, at any temperature in the test matrix, the device must return to a signed, working state - either the new verified slot or the last-known-good one - with no manual intervention. Anything less fails the test and gets fixed before the fleet grows.

Testing & Metrics

The test protocol treats trust properties as measurable, pass/fail things:

  • Boot-chain negative tests: unsigned image, validly-signed image from the wrong key, and a signed image with one byte flipped - all three must refuse to boot. Target: zero acceptances across the matrix.
  • TPM attestation: PCR values logged at every boot and compared against the known-good measurement; any unexpected change must block disk decryption. The sealed-key test is rerun after every legitimate update, since a new image changes the measurements and the policy must be re-sealed.
  • Update-cycle reliability: repeated full campaigns (enrol, transfer, verify, install, trial boot, mark-good) across the fleet, with success counted per stage. Deliberately-bad-image campaigns measure rollback: every one must end on the last-known-good slot.
  • Cold matrix: the same campaigns run at room temperature, freezer temperature (~-20 °C), and during warm-up, to catch cold-specific flash and SD behaviour.
  • Fault injection: mid-transfer corruption and mid-flash power cuts, repeated, warm and cold. Pass criterion: always returns to a signed, working state with zero manual recovery.

Full numbers (campaign counts, rollback rates, cold-vs-warm failure comparison) will be published once the test matrix has accumulated enough runs to mean something; that work is in progress. The negative boot-chain tests and the basic rollback path are already passing on the bench rig.

Key discipline: the root signing key lives on a YubiKey that never touches a networked machine - signing happens on an offline machine, and only signed bundles cross to the fleet server. The backup key is stored separately and offline, so losing or compromising any single device cannot produce a valid signature.

Status & Roadmap

  • Done: hardware on the bench (TPM board, both YubiKeys, fleet nodes); secure-boot chain with signed bootloader and kernel; TPM measured boot with LUKS keys sealed to PCRs; basic A/B update with manual health-check confirmation; first cold rollback runs in the freezer.
  • In progress: automated health-check gate and mark-good flow; per-device enrolment and campaign policies on the homelab fleet server; store-and-forward delivery for nodes on degraded links; accumulating the cold-temperature test matrix.
  • Next: full chaos-test battery (mid-transfer corruption, mid-flash power cuts) warm and cold; publish the test dataset (campaign counts, rollback rate vs temperature); extend enrolment to every rover and sensor node in the program.
