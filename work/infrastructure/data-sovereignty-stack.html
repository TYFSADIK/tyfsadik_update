Data Sovereignty & Secure Media Stack

Written by Taki Sadik · Last updated 2026-10-22 · 16 min read

Self-hosted Nextcloud and Immich on external SSDs with BTRFS snapshots, multi-user ACL isolation, and a 3-2-1 offsite backup strategy to BorgBase and rsync.net.

2025 to 2026 Infrastructure / Storage / Privacy GitHub ↗

Overview

This stack replaces Google Drive and Google Photos with fully owned infrastructure. Nextcloud AIO and Immich run in Docker on a BTRFS pool of external USB 3.2 SSDs, with per-user ACLs enforcing isolation and zstd compression reducing capacity needs. A 3-2-1 backup design keeps local BTRFS snapshots as fast recovery points, replicates encrypted archives to BorgBase, and keeps a secondary copy on rsync.net, aiming for GDPR-aligned retention with monthly restore drills.

Implementation

1

Create the compressed BTRFS pool [PRIVILEGED]

Warning: mkfs.btrfs destroys all data on the target disks. Use stable /dev/disk/by-id/ names, never /dev/sdX (those can reorder between boots), and double-check each name before running. Note that -d single stripes data with no redundancy: one failed SSD loses the whole pool. That is a deliberate capacity tradeoff here; redundancy comes from the offsite backups, not the pool itself.

# Identify the disks by stable ID first ls -l /dev/disk/by-id/ # DESTRUCTIVE: creates the filesystem (replace with your disks' by-id names) mkfs.btrfs -d single -L data \ /dev/disk/by-id/usb-Samsung_SSD_A-0 \ /dev/disk/by-id/usb-Samsung_SSD_B-0 mount -o compress=zstd:3 /dev/disk/by-id/usb-Samsung_SSD_A-0 /mnt/data
2

Deploy Nextcloud AIO and Immich

Run each stack as its own Compose project. Do not merge unrelated stacks with multiple -f flags; that merges their networks, volumes, and service namespaces into one project.

docker compose -f nextcloud-aio.yml up -d docker compose -f immich.yml up -d
3

Encrypted offsite backup with Borg

Initialize the repository once with encryption, and store the passphrase somewhere safe: losing it loses the backups. Databases need consistent dumps: enable Nextcloud maintenance mode during the backup and pg_dump Immich's Postgres into the data tree first, because backing up open database files can produce unrestorable copies. A BTRFS snapshot is a local recovery point, not a backup; the offsite Borg archives are the backups.

# One-time: initialize the encrypted repository export BORG_REPO="ssh://user@user.repo.borgbase.com/./repo" export BORG_PASSPHRASE="a-long-passphrase-stored-in-a-password-manager" borg init --encryption=repokey-blake2 "$BORG_REPO" # Quiesce and dump databases before the backup mkdir -p /mnt/data/db-dumps docker exec nextcloud-aio-nextcloud php occ maintenance:mode --on docker exec immich_postgres pg_dump -U postgres immich > /mnt/data/db-dumps/immich.sql # Snapshot, then back up (container names are examples; use yours) btrfs subvolume snapshot -r /mnt/data /mnt/data/.snapshots/daily borg create --stats "$BORG_REPO::data-{now}" /mnt/data docker exec nextcloud-aio-nextcloud php occ maintenance:mode --off # borg prints archive statistics with --stats; the first run takes the longest

Key Results

  • 3-2-1 backup design in place: three copies, two offsite (BorgBase and rsync.net); restore drills run monthly.
  • Replaces recurring cloud storage subscriptions with owned hardware (exact savings depend on capacity and drive prices).
  • External USB 3.2 SSDs form the fast local tier (measure throughput on your own hardware before quoting numbers).
  • Enforced multi-user isolation via filesystem ACLs preserved across container mounts.

How I built it

This project consolidates two goals I cared about: owning my files and photos outright, and surviving hardware failure or a house fire. The architecture separates the fast local tier from two independent encrypted offsite copies.

  1. Phase 1, build the local storage pool: Created a BTRFS pool across external USB 3.2 SSDs with zstd compression, giving transparent checksumming and cheap snapshots on commodity drives.
  2. Phase 2, deploy the services: Brought up Nextcloud AIO for files and Immich for photos as Docker containers on top of the pool.
  3. Phase 3, isolate users: Configured multi-user ACL isolation so each person's data stays in their own namespace.
  4. Phase 4, wire the 3-2-1 backups: Set up encrypted Borg backups to BorgBase and a second copy to rsync.net, keeping three copies with two offsite.
  5. Phase 5, prove restores work: Made restore testing a monthly routine, because a backup you have never restored is only a hope.

Challenges and lessons learned

  • USB-attached storage reliability: external drives can drop off the bus under load, which BTRFS notices immediately. Lesson: use quality enclosures and cables, and monitor dmesg after any disconnect.
  • Backup verification discipline: it is easy to let backups run silently for months. Lesson: schedule the monthly restore test like any other maintenance window and keep a log of each one.
  • Deduplication surprises: Borg's deduplication keeps offsite sizes manageable, but the first full backup is still the long pole. Lesson: seed the initial backup over a fast local link before switching to incremental uploads.

What is next

  • Add a second local mirror on separate hardware for faster recovery from total pool loss.
  • Send BTRFS snapshots offsite directly as an additional recovery path.
  • Add SMART monitoring with alerts so drive degradation is caught before failure.
  • Evaluate an object-storage tier for cold archival of old photo originals.

Storage & Backup Architecture

The stack has three physically and administratively separate tiers. The primary tier is the BTRFS pool on external USB 3.2 SSDs: all live Nextcloud and Immich data lives here, with zstd compression and per-data-area subvolumes. The local recovery tier is read-only BTRFS snapshots of those subvolumes, kept on the same pool for fast rollback. The offsite tier is two independent destinations: encrypted, deduplicated Borg archives on BorgBase, and a secondary copy on rsync.net held under a separate account.

Replication is not backup. Any mechanism that mirrors the primary data (RAID, a second synced drive, or continuous replication to another host) faithfully mirrors deletions and corruption too. Delete a folder (or have malware encrypt it) and the replica deletes or encrypts its copy within seconds. Replication protects against exactly one failure class: loss of the primary device. What actually protects data is independent recovery points: copies that (a) cannot be modified by the system they back up, (b) retain history so you can roll back to before the damage, and (c) live somewhere the same event cannot reach.

The 3-2-1 layout addresses each of those properties directly. The local BTRFS snapshots are read-only, so neither the containers nor any user process can rewrite history, and they retain point-in-time views for rolling back accidental changes. The BorgBase archives are encrypted client-side before anything leaves the host, deduplicated so history is cheap to keep, and append-oriented so a compromised host cannot silently rewrite old archives. The rsync.net copy sits with a different provider under different credentials, so an account-level problem at one provider cannot take out both offsite copies. Three copies, two providers, one offsite-and-then-some. The "0 data-loss events" claim in this project's metrics is a statement about this design and its drills, not about hardware never failing.

Data Flow

Two ingestion paths converge on the same storage and backup pipeline.

Phone photo to offsite (Immich): the Immich mobile app uploads new photos and videos in the background over HTTPS to the Immich server. The server writes the original assets into its library directories on the BTRFS pool and stores metadata, thumbnails, and ML results in its PostgreSQL database (which is dumped to the data tree before each backup run, so the database is covered by the same pipeline). On the backup schedule, a read-only BTRFS snapshot freezes a consistent view of the pool, borg create sends the deduplicated, encrypted delta to BorgBase, and the rsync.net copy is updated as the second offsite destination. A photo taken on the phone therefore ends up in three places: the pool (plus its local snapshots), BorgBase, and rsync.net.

Desktop file sync (Nextcloud): the Nextcloud desktop client watches the local sync folders and pushes changes over HTTPS to Nextcloud AIO, which writes them into per-user data directories on the same BTRFS pool. Nextcloud's own versions and trash bin provide the first, in-application line of undo; below that, the BTRFS snapshots give filesystem-level rollback; and the same snapshot → Borg → BorgBase / rsync.net pipeline carries everything offsite. Because both services share the pool and the snapshot schedule, one backup run covers files, photos, and the database dumps together.

Security Model

  • Multi-user ACL isolation: each person gets their own Nextcloud account and Immich user, and the underlying data directories on the BTRFS pool carry POSIX ACLs so one user's files are not readable by another's, even where directories are bind-mounted into containers. Isolation is enforced at two layers: application accounts (the day-to-day boundary) and filesystem ACLs (the boundary that survives a misconfigured share or app-level bug).
  • Encryption in transit: client-to-server traffic runs over HTTPS, and both offsite destinations are reached over SSH. No service in this stack is exposed over plaintext protocols.
  • Encryption of offsite backups: Borg archives are encrypted client-side with repokey-blake2 before any byte leaves the host, so BorgBase only ever stores ciphertext. The secondary rsync.net copy is transport- encrypted over SSH; at-rest encryption there relies on the provider, which is one reason the BorgBase archives are the primary offsite recovery source.
  • Encryption of the local pool: the primary SSDs are not claimed to be encrypted at rest on this page. Physical theft of the drives is a known gap; full-disk encryption (LUKS) under the pool is the natural fix and is listed as future work rather than asserted as done.
  • Credential handling: the Borg passphrase and the SSH keys for both offsite providers are never stored in the Compose files, scripts, or this repository. Commands reference them as environment variables and placeholders ($BORG_PASSPHRASE, <your-ssh-key>, <user@user.repo.borgbase.com>), and the real values live in a password manager. Losing the Borg passphrase loses the BorgBase archives, so it is backed up in the same way the data is: more than one copy, in more than one place.

Restore Testing

A green "backup completed" message proves a process ran; it proves nothing about whether data can come back. Archives can be subtly corrupt, passphrases can drift from what the password manager holds, and application state (database dumps, config) can silently fall out of the backup set. The only evidence that a backup works is a restore that was actually performed and checked. That is why this stack treats the monthly drill, not the nightly job, as the deliverable, and why the results are logged rather than assumed.

The drill below is the documented procedure. Commands are sanitized: hostnames, users, and paths are placeholders, and no specific drill results are claimed on this page.

# 1. Confirm the repository is readable and list recent archives export BORG_REPO="ssh://<user>@<user>.repo.borgbase.com/./repo" export BORG_PASSPHRASE="<from password manager>" borg list "$BORG_REPO" | tail -5 # 2. Verify repository integrity (data-level check, not just metadata) borg check --verify-data "$BORG_REPO" # 3. Extract a sample subtree to a SCRATCH directory, never over live data mkdir -p /mnt/scratch/restore-drill cd /mnt/scratch/restore-drill borg extract "$BORG_REPO::data-<archive-date>" path/to/sample-directory # 4. Compare checksums of restored files against the live originals (cd /mnt/data && sha256sum path/to/sample-directory/*) | sort > /tmp/live.sums (cd /mnt/scratch/restore-drill && sha256sum path/to/sample-directory/*) | sort > /tmp/restored.sums diff /tmp/live.sums /tmp/restored.sums && echo "DRILL PASS: checksums match" # 5. Spot-check a database dump restores into a throwaway database docker exec -i immich_postgres psql -U postgres -c "CREATE DATABASE drill_check;" docker exec -i immich_postgres psql -U postgres drill_check < /mnt/scratch/restore-drill/db-dumps/immich.sql docker exec -i immich_postgres psql -U postgres -c "DROP DATABASE drill_check;" # 6. Record the outcome (date, archive tested, checksum result) in the drill log, # then clean up the scratch directory rm -rf /mnt/scratch/restore-drill

Two habits make this meaningful. First, restore to a scratch location and compare checksums, rather than "looking at" the files: a diff is objective, an eyeball is not. Second, vary what gets tested: alternate between the newest archive and an older one, and between the BorgBase source and the rsync.net copy, so every tier of the 3-2-1 layout gets exercised over time.

Limitations & Future Work

  • No redundancy inside the pool: -d single trades redundancy for capacity, so a single drive failure is a full-pool event. The offsite backups cover it, but recovery means a full restore, not a degraded-but- running system. The planned second local mirror (BTRFS send/receive to separate hardware) closes most of this gap.
  • USB-attached storage: external SSDs can disconnect under load or with marginal enclosures and cables, and SMART passthrough varies by enclosure, which limits early-warning monitoring until the planned alerting is in place.
  • Manual elements in the pipeline: quiescing Nextcloud and dumping the Immich database before the backup are scriptable but human-supervised today; a fully scheduled, self-verifying job with alerting on failure is future work.
  • Restore drills are periodic, not continuous: a monthly drill can miss a bad archive for up to a month. More frequent automated extraction checks would shrink that window.
  • Secondary offsite copy is not independently encrypted at rest: the rsync.net copy relies on transport encryption and provider-side handling; moving that copy to an encrypted format (or Borg with a separate key) would make both offsite tiers equally strong.
  • Performance claims are hardware-specific: the ~2.5 Gbps SSD throughput figure belongs to this exact enclosure/cable/host combination; anyone reproducing the stack should benchmark their own chain before quoting numbers.
