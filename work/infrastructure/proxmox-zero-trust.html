Proxmox VE Homelab: Zero-Trust Private Cloud

A 3-node Proxmox VE HA cluster with Ceph storage, VLAN segmentation, and zero-trust external access via Cloudflare Tunnel with Tailscale mesh fallback.

2025 to 2026 Infrastructure / Networking / Security GitHub ↗

Overview

This private cloud keeps every self-hosted service reachable with zero open inbound ports. A 3-node Proxmox VE 8.1 cluster provides high availability over Ceph; the network is segmented into four VLANs by trust level; and the only path in from the internet is a Cloudflare Tunnel gated by Access policies, with Tailscale as an authenticated mesh fallback. No inbound ports are open on the homelab router, and tunnel traffic rides Cloudflare's edge network for low-latency global access.

This is a distinct build from the single-host Proxmox Homelab and from the 7-node Kubernetes cluster's own Proxmox underlay: these three nodes are dedicated to this HA cluster, and it is this cluster's services that the Cloudflare Tunnel publishes.

On three nodes, Ceph runs its monitors in quorum with pools at 3x replication, so any single node can fail without data loss, but there is no second failure margin and recovery is I/O heavy on consumer disks. Placement group counts were therefore tuned down from the Ceph defaults, trading slower recovery for stability, and Proxmox HA is set so guests restart on a surviving node when one fails.

How I built it

The design brief was strict: every self-hosted service reachable from anywhere, with zero public ingress. That means no open ports at all, identity-checked access at the edge, and a fallback path that stays authenticated.

  1. Phase 1, form the HA cluster: Joined three Proxmox VE 8.1 nodes with pvecm and built Ceph shared storage across them for high availability.
  2. Phase 2, segment the network: Carved the network into four VLANs by trust level: 10 for management, 20 for production, 30 for IoT, and 40 as the DMZ.
  3. Phase 3, close every port: Exposed services exclusively through Cloudflare Tunnel with Access policies, so the only path in from the internet is identity-gated and no inbound ports are open on the homelab router.
  4. Phase 4, add the mesh fallback: Configured Tailscale as an authenticated fallback so admin access survives even if the tunnel path has issues.
  5. Phase 5, automate data protection: Set up sanoid for automated local ZFS snapshots with hourly, daily, and 30-day retention, plus a separate snapshot strategy for Ceph volumes.
  6. Phase 6, deploy services: Ran the Docker-based services in LXC containers on the production VLAN behind the zero-trust front door.

Challenges and lessons learned

  • Ceph on three small nodes: Ceph assumes datacenter hardware and complains loudly on consumer gear. Lesson: tune placement group counts down and accept slower recovery in exchange for stability.
  • Quorum sensitivity: losing one node in a three-node cluster leaves no failure margin. Lesson: monitor quorum health as a first-class alert, not an afterthought.
  • Access policy UX: every new service needs its Access policy or users hit a wall. Lesson: template the policy creation alongside the tunnel route so nothing ships ungated.

What is next

  • Enforce device posture checks through WARP before granting access.
  • Move toward short-lived certificates for service-to-service auth.
  • Build an audit logging pipeline for every access decision.
  • Expand automated policy tests that verify each VLAN boundary.

Architecture Deep-Dive

Two flows define the system. The first is the ingress path: a request reaches the Cloudflare edge, passes the Access identity and policy check, and rides the tunnel that cloudflared established outbound from the DMZ VLAN. Because the tunnel is initiated from inside, no inbound port is ever opened. The second path is the fallback: Tailscale forms an authenticated WireGuard mesh that reaches the management VLAN directly, bypassing Cloudflare entirely.

Storage follows the same three-node symmetry. Every Ceph pool is configured at 3x replication: a guest write lands on a primary OSD and is replicated to an OSD on each of the other two nodes before it is acknowledged. Three monitors run one per node and hold quorum at 2-of-3, so the cluster keeps serving reads and writes with any one node down, and Proxmox HA restarts the failed node's guests on a surviving host.

Security Design

The design applies zero-trust principles at homelab scale: no implicit trust for any network location, identity verified on every external request, and blast radius limited by segmentation.

  • Egress-only ingress model: cloudflared initiates the tunnel outbound to Cloudflare's edge. The homelab router forwards no inbound ports, so the entire public attack surface collapses to the Cloudflare edge, where Access policies authenticate and authorize before any byte reaches a service.
  • Per-service policy, no blanket rules: each hostname published through the tunnel gets its own Access policy; a new service is not reachable until its policy exists. This is why policy creation is templated alongside the tunnel route, so nothing ships ungated.
  • Authenticated fallback: Tailscale provides a second, independent path into the management VLAN. It is a WireGuard mesh with its own identity and ACLs, so a Cloudflare outage does not become an administrative lockout, and the fallback is never an unauthenticated backdoor.
  • Segmentation by trust level: management (VLAN 10), production (VLAN 20), IoT (VLAN 30), and DMZ (VLAN 40) are isolated at the switch, with the router firewalling between segments. A compromised IoT device cannot reach the Proxmox management plane.
  • Certificate and credential handling: TLS for public hostnames is terminated at the Cloudflare edge, so no certificate private keys need to live on the tunnel-published services. The tunnel credentials file and any API tokens are stored only on the host that runs cloudflared, with restrictive file permissions; commands on this page use placeholders such as <API_TOKEN> rather than real values.
  • Planned hardening: device posture enforcement via WARP, short-lived certificates for service-to-service authentication, and an audit pipeline over every Access decision are designed but not yet implemented (see the component reference and limitations).

Failure Modes & Recovery

Each failure mode below follows from the architecture described above. Commands are sanitized: real hostnames, tokens, and IDs are replaced with placeholders.

Cloudflare outage or tunnel down

Public hostnames stop resolving to a working path, but nothing inside the cluster is affected. Administration continues over the Tailscale fallback, which never touches Cloudflare. Recovery on the DMZ host:

# Is the tunnel client alive? systemctl status cloudflared # Which tunnels does this account know about, and is this one connected? cloudflared tunnel list cloudflared tunnel info <TUNNEL_NAME> # Restart the client if it has wedged; it re-dials outbound, no ports to open systemctl restart cloudflared

Single node failure

Ceph monitors hold quorum at 2-of-3, so the surviving two nodes keep the cluster read-write. OSDs on the failed node go down; Ceph marks the pool degraded and begins re-replicating data onto the surviving OSDs. Proxmox HA restarts the failed node's guests on a surviving host. This is the case the design explicitly tolerates; recovery is I/O heavy on consumer disks, which is why PG counts were tuned down for stability over speed.

# Cluster and storage health from any surviving node pvecm status ceph -s ceph osd tree

Second node failure before the first recovers

With only one node left, corosync and the Ceph monitors lose quorum: the cluster goes read-only and guests stop rather than risk split-brain. This is the accepted limit of a three-node design. After hardware is repaired, rejoining the node lets Ceph backfill and rebalance automatically. If the failed node cannot return, quorum can be temporarily adjusted as a deliberate, documented break-glass step:

# Break-glass only: run the cluster on one node while rebuilding pvecm expected 1

ZFS snapshot rollback on a local pool

sanoid keeps hourly and daily snapshots for 30 days on each node's rpool. Rolling back discards everything written after the snapshot, so it is a deliberate operation:

# List what sanoid has kept zfs list -t snapshot -r rpool/data # Roll back to a known-good snapshot (destroys later snapshots of that dataset) zfs rollback rpool/data@autosnap_<DATE>_daily # Confirm sanoid itself is still creating and pruning on schedule systemctl status sanoid.timer

Ceph RBD data

sanoid does not see Ceph RBD images, so guest disks on Ceph need the separate strategy noted in the component reference (Ceph snapshots, rbd mirroring, or vzdump to external storage). Until that is built, a Ceph pool loss has no point-in-time recovery; this is listed as a limitation below.

Limitations & Future Work

  • No second failure margin: three nodes means quorum at 2-of-3 and Ceph at 3x replication. One failure is tolerated by design; a second concurrent failure stops the cluster. This is accepted, monitored, and documented rather than hidden.
  • Consumer disks bound Ceph recovery: re-replication after a node loss is slow and I/O heavy. PG counts are tuned down for stability, which trades away recovery speed.
  • Ceph RBD has no point-in-time recovery yet: sanoid covers only local ZFS pools. The separate snapshot or backup strategy for Ceph volumes (Ceph snapshots, rbd mirroring, or vzdump to external storage) is planned, not built.
  • Cloudflare is a dependency: public access depends on the tunnel and Access. The Tailscale fallback covers administration, but it does not restore public service reachability during a Cloudflare outage.
  • Single residential uplink: one ISP, one router. The zero-trust design removes the need for inbound ports, but it cannot remove the physical single point of failure.
  • Posture, audit, and policy testing are unfinished: WARP device posture, an access-decision audit pipeline, short-lived service certificates, and automated VLAN boundary tests are the active next steps listed above.
