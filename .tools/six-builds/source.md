# Six Builds for Canadian Defence: 2027 Build Guides (source document)

Prepared October 23, 2026. Numbers marked (est.) are calculated from the cited specs. Items marked (verify) were not confirmed against a primary source.

## Approach and rules for all six

- Canada publishes its needs as measurable specs. Build to a spec, measure honestly, publish the limits. The IDEaS counter-drone sandbox rewards teams that push a system to failure so its limits are understood, and favours systems that plug into military command and control.
- Scope honesty: the Arctic drone spec caps at 25 kg takeoff weight with a 20 km radius and 90 min endurance; the cargo ground vehicle must carry 140 kg. A solo bench build cannot meet those. Each guide says what the hobby-scale version proves and ends with a gap table. Never claim a spec you only partly tested.
- Order of work: Build 4 and Build 5 first (software and simulation), then Build 1 bench and cold work, then Build 6, then Builds 2 and 3 if time and money allow.
- Rules: defensive only (detect, survey, haul, secure; nothing that jams, spoofs or carries munitions; RF receive-only unless licensed). Synthetic data for anything mimicking protected material. Test only your own gear with permission. One repo per build: README (claim, spec table, results), /docs, /hw, /sim, /test, /data, /results, LICENSE, SBOM, signed releases. ROS 2: start on Jazzy (Ubuntu 24.04); Lyrical Luth went GA May 22, 2026 as LTS to May 2031 but package support lags.
- Calendar for southern Ontario: now to December = Builds 4, 5, 6 (software/sim), Build 1 bench, Build 2 sim. December to March = Build 2 snow tests and Build 1 cold tests. April to May after ice-out = Build 3 water trials.

## Who can actually apply

- MINERVA challenges via Innovative Solutions Canada: for-profit company incorporated in Canada, 499 or fewer employees, R&D done in Canada, TRL 5-9. Phase 2 prototype funding up to $500,000 over up to 15 months. Arctic UAS, cargo UGS and surveillance UGS closed Sept 24, 21 and 10, 2026. Six challenges released progressively, including UAS deconfliction.
- IDEaS counter-drone sandbox: individuals, academia, non-profits, industry of any size; applicant owns the IP; TRL 5, or TRL 4 with a plan; every participant receives $20,000; prize money needs an incorporated Canadian entity; next sandbox expected about 2028.
- IDEaS competitive projects: rolling challenges under a call open to March 31, 2027.
- Defence Drone Initiative supply arrangements: current arrangement holders only.
- Business-readiness checklist: incorporate; Controlled Goods Program registration or documented exemption; CPCSC Level 1 self-assessment (introduced April 14, 2026, annual self-assessment; Level 2 third-party; Level 3 DND-assessed planned for select RFPs from 2027); commercial general liability insurance (from $2 million); security clearance documents for sandboxes; supply-chain table of critical components with manufacturer and country of origin.

## Build 1: Arctic ISR drone (cold, glove-operable, thermal detection, TAK output)

Target spec (MINERVA Arctic UAS): operate -40 to +40 C, winds at least 55 km/h, light rain, snow, moderate icing; at least 20 km radius and 90 min endurance; takeoff weight no more than 25 kg; transportable in a 240 L container; operable with winter gloves; desired extras: VTOL, autonomous waypoints, TAK compatibility, fibre-optic or other non-radio mode, production cost about $60,000 or less. Proposals closed Sept 24, 2026; use it as a spec sheet. Recognition requirement (people and vehicles, day and night) is cited to a secondary source (verify).

What the hobby version proves: (1) a heated, instrumented battery bay with cold-test data; (2) thermal person and vehicle detection with a measured pixel-size limit; (3) detections georeferenced and shown in TAK; (4) a glove-operable control kit with measured task times; (5) a cost model and an honest gap table.

Architecture: Lepton 3.5 thermal camera -> Raspberry Pi 5 with Hailo accelerator (detect, track) -> georeferencing from flight-controller position, attitude and camera geometry -> Cursor on Target (CoT) messages via PyTAK to TAK Server / ATAK. Flight controller (ArduPilot) talks to the Pi over MAVLink 2 with signing on. Operator side: RC link, physical macro pad, stripped-down tablet screen.

Steps:
- Phase 0 simulation (weeks 1-2): ArduPilot SITL; write the georeference function and test against SITL telemetry with a fake detection stream; stand up TAK Server (OpenTAK or FreeTAKServer) and ATAK on Android; confirm markers appear.
- Phase 1 thermal pipeline on the bench (weeks 2-6): capture Lepton frames (PureThermal board over USB; drop shutter-correction frames); train a detector (HIT-UAV: 2,898 infrared images from 60-130 m; add own labelled clips; check licences, Ultralytics YOLOv8 is AGPL-3.0, consider YOLOX); compile for Hailo; measure end-to-end latency frame to TAK marker. Pixel math (est.): Lepton 3.5 is 160x120 with ~57 degree horizontal view, one pixel ~6.2 mrad; at 50 m a pixel covers ~0.3 m so a person is roughly 2x5 pixels; at 100 m about 1x3. Report detection against pixels-on-target, not just metres.
- Phase 2 cold rig (weeks 4-8): LiPo internal resistance rises sharply in cold, Li-ion loses roughly 15-20% capacity near 0 C, flight time can drop 20-50% below freezing, raise low-voltage landing threshold to about 3.5 V per cell in winter (starting ranges, measuring the real numbers is the point). Build insulated bay with resistive or PTC heater, DS18B20 thermistors, INA228 power monitor, small MCU; log heater Wh per flight. Lepton operating range starts around -10 C, storage to -40 C (verify), so Arctic use needs a warm enclosure. Test in a freezer (~-18 C), then real winter; report only temperatures actually tested. Moisture: warm gear slowly in a sealed bag; desiccant in the thermal housing.
- Phase 3 flight (weeks 8-12): X500-class quad, ArduPilot, waypoint mission, return-to-launch, geofence, low-battery failsafe with raised cold threshold; fly planted targets at surveyed positions.
- Phase 4 glove usability (weeks 10-12): physical controls for arm/hold/return/land/mark; large targets; no pinch/zoom; one-hand operation; readable in snow glare; 6-button macro pad plus stripped-down tablet view (MAVSDK or pymavlink); test with real mitts, time to launch/abort/mark, error counts vs bare hands.
- Phase 5 spec-gap report.

Spec-gap table: -40 to +40 C = partial (freezer ~-18 C, real winter; report only tested temps). Wind 55 km/h = not met (log real wind). Light rain/snow/icing = partial, no icing test. 20 km radius = not tested (VLOS only). 90 min endurance = partial, different airframe. 25 kg MTOW = not comparable. 240 L container = measure and report. Glove operation = tested. TAK compatibility = tested (CoT via PyTAK). VTOL = yes but not the spec airframe. Fibre-optic mode = not tested. $60,000 cost = argued only via BOM + scaling. Recognize people/vehicles day and night = partial (verify wording).

Metrics to publish: detection recall and false alarms per pixels-on-target day/night; georeference error against surveyed marks; image-to-TAK latency; endurance and voltage sag vs temperature; heater Wh per flight; glove task times; BOM cost with scaling argument.

Hardware to buy first: Pixhawk-class FC with GPS (RTK later); X500-class frame, motors, ESCs; Pi 5 8GB; AI HAT+ (Hailo); Lepton 3.5 + PureThermal; visible camera; 6S 21700 Li-ion pack or LiPo; heater film; DS18B20; INA228; ELRS RC link; USB macro pad; balance charger + fire-safe bag.

Safety and legal: register drones 250 g+ and hold the right pilot certificate (basic for uncontrolled airspace, advanced for controlled or near people); stay VLOS below 122 m. Transport Canada changed rules November 4, 2025: lower-risk BVLOS needs a Level 1 Complex certificate (18+, uncontrolled airspace, away from airports); SFOC applications now carry a fee. Never charge Li-ion below 0 C. An X500 will not hold position in 55 km/h wind; log real wind.

## Build 2: GPS-denied cargo ground vehicle for snow

Target specs (two MINERVA ground challenges, closed Sept 2026, used as spec sheets). Shared essential outcomes: system = ground vehicle + sensor payload + GCS + radio + battery with multi-battery charger + remote antenna 100 m from GCS; operate -20 to +40 C; no more than 410 kg unladen (a cap, not payload); at least 15 km/h and 4 h continuous motion unladen; paved roads, sand, gravel, day/night, minimum 15 degree gradients; sustain 7 km/h cross-country with rated payload; climb 20% grades, 15% side slopes, 250 mm vertical step, cross a trench (surveillance notice says 500 mm; cargo notice prints 500 m, likely a typo, use 500 mm and say so).

Cargo only: carry 140 kg onboard incl. tri-wall container 122x102x92 cm; tow 275 kg; radio radius 5 km unladen with live video, 10 km autonomous. Surveillance only: 3 km radio radius; recognize a 180 cm person at 0.5 km day / 0.25 km night, a 5x3x2 m vehicle at 1 km day / 0.5 km night; look over a 1 m obstacle with 180 degree pan; extras: 48 h stationary endurance on sensor payload; room/power/API for 100 lb payload at 30 W; cost $150,000 or less; no more than 5 dB SPL at 500 m; fibre-optic control from 100 m; NATO tow hook; two vehicles per PLS deck; ready in 30 min; electric/hybrid; front obstacle avoidance; GCS with mission sim, MGRS, TAK push, return-on-link-loss.

What the hobby version proves: a 10-30 kg payload testbed measuring how navigation error, wheel slip and energy use change with sensor set, payload and snow, RTK GNSS as ground truth only. Publish scaling arguments, not compliance.

What research says will go wrong: LiDAR degrades in snow (dropout or near-sensor noise); one study's LiDAR odometry worked in light snow then lost track as snow got heavier while radar SLAM kept operating; fix: denoise snow points before odometry (Charron et al. 2018, dynamic radius outlier removal); the radar study used a 4 Hz spinning radar, so results do not transfer directly to small mmWave boards. Winter teach-and-repeat: teach runs 113, 44 and 4 days old; only a radar repeat taught in the same deployment completed the route; ICP LiDAR localization failed near snowbanks up to 3 m; flattening the trail with a snowmobile lowered power use and improved mobility. Wheel-odometry-leaning algorithms drift when wheels slip (verify exact finding).

Architecture: Pi 5 or Jetson-class + motor-control MCU with hardware wireless E-stop on the motor power line; wheel encoders, good IMU, 3D (or 2D) LiDAR, optional TI mmWave radar for Doppler ego-velocity, RTK GNSS (truth only). ROS 2 Jazzy, robot_localization EKF, Nav2, FAST-LIO2 (or slam_toolbox 2D), snow filter, slip detector, rosbag2 MCAP logging, evo for trajectory error.

Steps: Phase 0 sim (weeks 1-3): Gazebo slip-prone terrain, EKF + Nav2 + evaluation scripts. Phase 1 bench (3-6): calibrate encoders/IMU; verify E-stop cuts motor power on blocks; time sync. Phase 2 easy ground (6-8): pavement/gravel loops GNSS on then off; translation error % of distance per segment (KITTI-style 100-800 m) + APE/RPE with evo. Phase 3 winter (Dec-Mar): packed and loose snow; radar-velocity variant and snow filter; log snow depth/condition/packed. Phase 4 payload sweep 0/10/20/30 kg: drift %, slip ratio, stuck events, Wh/km, max stable speed. Phase 5 stationary energy: 30 W resistive load + compute for 48 h (payload alone 30 W x 48 h = 1.44 kWh est., sets battery size and cold derating). Phase 6 report.

Slip handling: compare IMU yaw rate vs differential wheel-speed yaw; on disagreement inflate wheel-odometry covariance in the EKF.

Hardware to buy first: ROS-compatible 4WD or tracked research chassis (check payload rating); RTK GNSS pair; IMU; LiDAR; encoders; wireless E-stop relay; battery sized from Phase 5; TI mmWave radar eval board.

Safety: hardware E-stop, speed cap, private test area, spotter; charge batteries indoors never below 0 C; check municipal bylaws.

## Build 3: Autonomous boat for seabed surveys and anomaly detection

Target: DND opened a solicitation Sept 10, 2026 for a Canadian autonomous mine-countermeasures USV to survey the seabed (detect, locate, identify mines); offers due Oct 1; only current supply-arrangement holders could bid. The initiative lists route surveying and port protection among maritime priorities (verify). You cannot bid, but you can build the survey-and-detect core.

What the hobby version proves: repeatable autonomous survey lines, georeferenced depth data, a gridded seabed model, anomaly detection scored against planted targets, published minimum detectable target size. Honest limit: a single-beam echosounder only sees under the hull; objects fall between lines unless spacing is tight; mine hunting normally uses swath sensors (side-scan/multibeam); measure how line spacing limits detection.

Architecture: small catamaran, two thrusters; ArduPilot Rover (boat frame) on Pixhawk or Cube; GNSS (RTK optional); Blue Robotics Ping echosounder; telemetry radio or LTE; shore station with Mission Planner or MAVProxy. Community builds target roughly US$1,000-1,500 and survey at 2-5 knots (verify).

Ping sonar numbers: current revision (May 2023): 0.3 m typical min range, 100 m typical usable range, 25 degree beamwidth, range resolution 0.5% of range, 0-30 C operating. Original model: 0.5 m min, 50 m typical, 70 m firmware limit, 30 degree beam; confirm which unit you buy. Beam footprint on the bottom ~ 2 x depth x tan(half beamwidth) (est.): ~0.9 m at 2 m depth, 1.3 m at 3 m, 2.2 m at 5 m (25 degree beam). Line spacing must not exceed the footprint for continuous coverage. Log water temperature (April water is near the lower limit).

Steps: Phase 0 sim (weeks 1-2): ArduPilot Rover SITL boat frame; script generating lawnmower lines from polygon + spacing; geofence and failsafes (RC loss, low battery, GPS loss). Phase 1 bench (2-5): wire FC, GNSS, sonar, thrusters, power; set sensor offsets (ArduPilot measures depth from sonar face, position at centre of rotation; enter offsets) [verify against S32]; tub/pool test. Phase 2 spring field (Apr-May): calm pond or small lake with permission; plant targets (cinder blocks, 3D-printed shapes, sunken crate) at surveyed positions in 1-3 m; surveys at 2-3 line spacings. Phase 3 processing: pymavlink log export; draft and sound-velocity corrections; reference depths to water level (RTK vertical error ~50 mm in one DIY report); grid with IDW or kriging; anomalies as residuals after smoothing (difference of Gaussians); QGIS; repeat survey another day for change detection. Phase 4 report: detection rate vs target size/depth/spacing; false alarms; position error; survey time per hectare; battery use; spec-gap table listing swath sensing, mine ID, range as not tested. Stretch: scanning sonar, tie in hydrophone and AIS node by timestamp.

Safety and legal: stay within sight, off navigation channels, permission for the water body, never launch alone from a slippery shore in cold water. No hobby-USV-specific rule found; Vessel Operation Restriction Regulations limit power-driven vessels on some waters; confirm with Transport Canada boating safety (verify). Ice season ends the work.

## Build 4: Counter-drone test-and-scoring harness with sensor-fleet operations

Why: the CAF national counter-drone tender asked a contractor to design, install, integrate, test, validate, maintain, sustain and modernize the capability as a service (verify dates/scope). The IDEaS sandbox guide asks for systems that integrate into military C2, lists protocols in use, and says networks of low-cost sensors are an emphasis area; plain radar/acoustic/RF/optical detection is less likely to be selected unless clearly improved; detect-only systems are accepted. This build puts DevOps and test discipline into that gap.

What the sandbox asks: threat classes micro UAS (under 2 kg, up to 200 ft AGL, ~5 km radius, up to 200 km/h) and mini UAS (2-15 kg, 3,000 ft, ~25 km, 200 km/h). Hard cases: drones under 250 g, fast FPV, swarms of 3+, fibre-optic tethered drones (tethers to 30 km), birds/clutter, rain/fog/snow/night. Range: early warning well beyond 3 km described as achievable. Six scenarios: fixed base 2.5 km radius; five-vehicle patrol; 12 dismounted soldiers; urban 4x4 blocks up to 10 storeys; frigate-sized ship; 10 km linear border (state node count and spacing). C2 protocols in use: JREAP-C J-series, VMF K-series, Cursor on Target, SAPIENT. Low emissions preferred; emitters need a DND 552 spectrum form.

What to build: 1) SAPIENT (BSI Flex 335) interface on sensor nodes. 2) Bridge to TAK (CoT). 3) Scenario-driven scoring harness using Stone Soup metrics. 4) Coverage planner. 5) Fleet ops: OTA updates, health monitoring, acceptance tests, runbooks.

Steps: Phase 0 standards (weeks 1-2): read BSI Flex 335 v2 (March 2024, free from BSI) (verify date); messages are protobuf over TCP edge to fusion node; Dstl released middleware and compliance test harness open source Apache 2.0 in 2022, which predates v2, so check interface version. Phase 1 adapter (2-5): node registering and sending status/detection reports with official protos, verified with the test harness; forward to TAK with snstac sapientcot (verify version support); add native CoT output. Phase 2 ground truth and time: own drone's ArduPilot logs with GNSS (RTK if possible); GPS PPS + chrony on every node; log clock offset as a health metric. Phase 3 scenario cards in YAML: approach (radial/tangential/hover/descent), speed band, altitude, drone count, class, environment tags, detection definition. Phase 4 simulation at scale: ArduPilot SITL multi-drone truth + sensor models (detection probability and noise vs range); same pipeline replays real logs. Phase 5 scoring: Stone Soup SIAP metrics (completeness, ambiguity, spuriousness, continuity), OSPA, CLEAR-MOT; plus detection probability vs range, first-detection range distribution, time to first alert, false alarms per hour, localization error vs range. Phase 6 coverage planner: measured detection probability vs range -> node count and spacing for the 2.5 km base and 10 km border with Monte Carlo; cost per kilometre. Phase 7 CI: nightly simulated scenarios with regression thresholds, DVC data versioning, HTML report artifact, signed container images. Phase 8 fleet operations: A/B OTA (Mender, RAUC or own signed flow), Prometheus health (battery, temperature, GNSS lock, clock offset, link quality), alerts, per-site acceptance test, maintenance schedule, spares log; runbooks mirroring the tender lifecycle (install, integrate, test, validate, maintain, sustain, modernize). Phase 9 failure envelope: push each metric to failure and publish the limit.

Pitfalls: birds and aircraft create false alarms; log them as their own class. Define detection before flying. Keep RF receive-only.

## Build 5: Secure autonomy for the robot and drone fleet

Why: the Defence Drone Initiative has a digital-enablers stream (communications, cyber, C2 for autonomous platforms) (verify). SOC background is the differentiator: attack your own fleet in the lab, fix it, monitor it.

Threat model first (week 1): STRIDE across radio link (GCS-vehicle), companion computer to flight controller, ROS 2 network, USB/serial, firmware and OTA, logs and keys. Output: data-flow diagram, asset list, threat table, one test case per threat.

Controls: 1) MAVLink 2 signing: 13-byte block (link ID, 48-bit timestamp in 10 us units since 2015-01-01, 48-bit signature = first 6 bytes of SHA-256 over key + packet); authenticates and blocks replay but does not encrypt; one shared 32-byte symmetric key; key travels in SETUP_SIGNING, only over secure link like USB; PX4 stores key as a file on SD card; logs must not capture the key. Tests: unsigned/wrongly signed rejected, correctly signed accepted, replays rejected; policy for MAVLink 1 and unsigned traffic: reject. 2) Link encryption: WireGuard between vehicle and ground station over IP; serial radios: state the limits. 3) Signed firmware: ArduPilot signed bootloader + signed firmware, up to two key pairs, Ed25519 via Monocypher (not ECDSA, a forum post saying ECDSA is wrong); caution: bootloader allows unsigned firmware when all public keys are removed, keys manageable over MAVLink secure-command path, so protect private key and that path; forum reports: USB can bypass MAVLink signing (lock down DFU); wrongly signed board loops in secure bootloader; practise on a spare board, private key offline. 4) SROS2: keystore, enclave per node, signed governance/permissions; enforcement via security env vars; least-privilege topics; restrict multicast discovery; firewall DDS ports; measure CPU/latency with and without. 5) Monitoring: pymavlink-based detector is primary (Suricata has no native MAVLink parser; use it only for raw-payload rules or flow logging); alert on unsigned MAVLink 2, SETUP_SIGNING attempts, parameter writes/mission uploads from unknown sysIDs, arm/disarm from unexpected sources, timestamp regressions, duplicate sysIDs, MAVLink 1 frames; ROS graph monitor for new nodes/topics/QoS; ship alerts to SIEM (Wazuh or ELK). 6) Update integrity: reuse secure-fleet-updates work (TPM measured boot, signed A/B), show tampered update rejected. 7) Attack own lab only: SITL on isolated network, inject unsigned/replayed/malformed MAVLink, fuzz parsers (AFL++/libFuzzer); no RF jamming/spoofing; GNSS detection only.

Deliverables: threat model; test-case table with pass/fail evidence; hardening checklist. Community guidance for compliance reviews: show unsigned and wrongly signed rejected, correctly signed accepted.

Hardware to buy first: spare Pixhawk/Cube, Pi 5 companion, two hardware security keys, managed switch with VLANs.

## Build 6: Sovereign AI and data enclave

Why: DND's AI strategy stresses well-governed data, secure cloud, data-centric security (verify wording). Sovereignty debate focuses on foreign-jurisdiction exposure (US CLOUD Act) and Canadian-held keys; one senator's op-ed makes that case (label it opinion). The private-AI stack (Chakor) is the base; this build adds controls and proof.

Target design: Identity: Keycloak (OIDC) with attributes for notional clearance, compartment, releasability (all labels synthetic). Level 1 policy: OPA (Rego) compares user attributes with document labels; policy tests first incl. negative tests. Level 2 protection: OpenTDF wrapping so policy travels with data; ABAC; Key Access Server releasing keys only to entities with right attributes; federated key management. Keys: OpenBao with PKCS#11 auto-unseal against an HSM (SoftHSM dev, hardware token real); transit engine for envelope encryption; LUKS bound to TPM. Retrieval: pgvector with row-level security and label columns, filter by authorization before similarity search; OWASP LLM Top 10 (2025) lists vector/embedding weaknesses incl. retrieval without per-user access checks; caution: approximate indexes can apply filters after the scan and silently return fewer results; test recall under filtering, per-label partitions, check pgvector iterative index scans (verify). Serving: containers or Firejail, default-deny egress with allow-list, no telemetry, model hashes checked, signed model artifacts. Audit: every retrieval and answer logged to the tamper-evident decision log; human approval for actions beyond answering. Guardrails outside the model: deterministic label checks on outputs; the model is never the security boundary.

Steps: weeks 1-2 threat model vs OWASP LLM Top 10 (prompt injection, sensitive info disclosure, vector weaknesses, excessive agency). Weeks 2-4 labels + OPA policy with unit tests. Ingestion: label, encrypt (envelope or TDF), embed, store with labels + RLS. Key management: OpenBao + HSM; rotation drill; test HSM-unplugged behaviour. Retrieval authorization + audit. Leakage tests: seed canary documents at every label, assert zero cross-label retrieval across many queries and attacks (indirect injection in documents, query rewriting, label spoofing) with promptfoo or garak; also measure recall (catch missing answers, not only leaks). Degraded-network mode: edge box with small model + local store, store-and-forward sync, fails safe. Sovereignty statement: diagram + table showing where each key, byte, process, log lives and who can reach it. CPCSC mapping (stretch): map controls to Level 1 criteria, publish gaps.

Metrics: cross-label leaks (target zero across N attacks), retrieval recall under filtering, policy decision latency, retrieval latency overhead, audit completeness, recovery time after HSM loss, answer quality vs unrestricted baseline.

Hardware: existing hosts, two hardware tokens (one HSM-grade PKCS#11), GPU if none.

## Packaging for recruiters

One page per build: claim, spec table, 90-second video, results chart, gap table. Publish methods and data; keep operational detail generic. Name the standards: SAPIENT (BSI Flex 335), CoT/TAK, MAVLink signing, SROS2, OpenTDF. State TRL honestly (a bench prototype is not TRL 5). Business-readiness block on the portfolio: legal entity, Controlled Goods status, CPCSC Level 1 self-assessment status.
