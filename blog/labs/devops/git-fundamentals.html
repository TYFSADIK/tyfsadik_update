Git Fundamentals: Build a Clean, Recoverable History

BeginnerDevOps~2 hours
git initcommitbranchremote

You will initialize a repository, stage and commit changes, branch, and push to a remote. By the end you will have a clean, recoverable history and understand the staging-area model that makes Git powerful.

Git is the version control system behind almost every professional workflow in security and IT: code, infrastructure definitions, documentation, and lab notes all live in repositories. Unlike older tools that stored snapshots of whole folders, Git records commits as a linked chain of changes, which means you can answer three questions at any moment: what changed, who changed it, and why. That audit trail is exactly what you lean on during incident reviews and collaborative work.

This lab is deliberately hands-on. You will create a small project from nothing, build a short but real history on a feature branch, merge it back, and publish everything to GitHub. Each command below is run in a terminal, and each step includes the output you should expect so you can verify you are on track before moving on. Work through the steps in order; later steps assume the earlier ones succeeded.

Learning Objectives

  • Track changes with the staging area and meaningful commits.
  • Branch and switch context safely.
  • Push to and pull from a remote.
  • Inspect history with git log, git status, and git diff, and recover from a staged-file mistake.
  • Merge a feature branch back into the default branch and keep the local and remote copies in sync.
  • Time: ~2 hours · Difficulty: Beginner · Prereqs: Git installed and a GitHub account.

Architecture Overview

Everything in Git moves between four areas. Your working tree is the folder you edit files in. When you run git add, you copy selected changes into the staging area (also called the index) - a draft of the next commit. git commit freezes that draft into a permanent snapshot inside the local repository, the hidden .git directory. Finally, git push copies commits from your local repository to the remote (here, GitHub), and git pull brings remote commits back down. The staging area is the piece beginners skip and then regret: it is what lets you commit only the changes that belong together, instead of whatever happens to be on disk.

graph LR WT[Working tree] -->|git add| Stage[Staging area] Stage -->|git commit| Local[Local repo] Local -->|git push| Remote[(Remote: GitHub)] Remote -->|git pull| Local

Notice that the working tree has no direct arrow to the remote. Nothing reaches GitHub unless it first went through staging and became a commit. Keep that mental model and most confusing Git output starts to make sense.

Environment Setup

You will need: Git 2.4x and a remote (GitHub) repository.

First confirm Git is installed and check the version. Any 2.x release from the last few years works for everything in this lab; the git switch command used later requires Git 2.23 or newer.

CHECK GIT VERSION

git --version
$ git --version
git version 2.46.0

Before you begin: set your identity with git config --global user.name/user.email. Git stamps this identity onto every commit you make. Use the same email as your GitHub account so GitHub attributes the commits to you.

CONFIGURE YOUR IDENTITY

git config --global user.name "Taki Sadik"
git config --global user.email "taki@tyfsadik.org"

Verify the configuration was saved before continuing - a typo here follows every commit you ever make:

$ git config --global --list
user.name=Taki Sadik user.email=taki@tyfsadik.org

Common mistake: writing -global with a single dash. Git silently treats it as an unknown option or splits it into short flags, and your identity is never set. Long options in Git always take two dashes. If git config --global --list does not show your name and email, go back and re-run the two commands above.

Optionally, set the default branch name to main so new repositories match GitHub's convention instead of the older master:

SET DEFAULT BRANCH NAME

git config --global init.defaultBranch main

Step-by-Step Execution

01
Initialize and make the first commit

The staging area lets you craft exactly what goes into each commit. Here you create a project folder, turn it into a repository, add two files, and commit them. git init creates the hidden .git directory that stores the entire history - delete it and the folder becomes plain files again, which makes experimenting risk-free.

git init && git add . && git commit -m "initial commit"

For this lab, break that one-liner into explicit steps so you can see each area change state. First create the project and a couple of files:

CREATE THE PROJECT

mkdir lab-notes && cd lab-notes
echo "# Lab Notes" > README.md
echo "passwords.txt" > .gitignore
git init
$ git init
Initialized empty Git repository in /home/taki/lab-notes/.git/

The .gitignore file above tells Git to never track passwords.txt - a small habit worth building early, because committing a secret is one of the classic mistakes covered in Troubleshooting. Now check the repository state:

INSPECT STATUS BEFORE STAGING

git status
$ git status
On branch main No commits yet Untracked files: (use "git add <file>..." to include in what will be committed) .gitignore README.md nothing added to commit but untracked files present (use "git add" to track)

"Untracked" means Git sees the files but has never been told to record them. Stage them, then commit:

STAGE AND COMMIT

git add .
git commit -m "Initial commit: README and .gitignore"
$ git commit -m "Initial commit: README and .gitignore"
[main (root-commit) 3f9a1c2] Initial commit: README and .gitignore 2 files changed, 2 insertions(+) create mode 100644 .gitignore create mode 100644 README.md

The output confirms the commit hash (yours will differ), the branch, and exactly what was recorded. A good commit message reads like a changelog entry: short, present tense, specific.

How to verify: run git status again - it should report "nothing to commit, working tree clean". If it still lists untracked files, you staged before creating them; run git add . and commit again.

02
Branch for a change

A branch is a movable pointer to a commit. Working on a branch means your half-finished experiment never touches main, which should always stay in a state you could show someone. git switch -c creates the branch and moves you onto it in one command (the older spelling is git checkout -b).

git switch -c feature/login && git commit -am "add login"

In this lab the "feature" is a notes file - the mechanics are identical to real code. Create the branch first and confirm where you are:

CREATE AND SWITCH TO A FEATURE BRANCH

git switch -c feature/login
git branch --show-current
$ git switch -c feature/login
Switched to a new branch 'feature/login'
$ git branch --show-current
feature/login

Now make the change and commit it. The -a flag stages modifications to files Git already tracks, so you can skip a separate git add - but note it does not pick up brand-new files, which is why the file below is created before the commit, and staged explicitly first:

MAKE A CHANGE ON THE BRANCH

echo "- Draft: login flow notes" >> login-notes.md
git add login-notes.md
git commit -m "Add draft login flow notes"
$ git commit -m "Add draft login flow notes"
[feature/login 7c2e4b8] Add draft login flow notes 1 file changed, 1 insertion(+) create mode 100644 login-notes.md

Prove the isolation is real: switch back to main and the new file disappears from the working tree, because that commit only exists on feature/login.

SWITCH BACK AND CHECK

git switch main
ls
$ git switch main
Switched to branch 'main'
$ ls
README.md

Switch back to the feature branch before continuing:

git switch feature/login

Common mistake: making commits on main because you forgot to create the branch first. Get in the habit of running git branch --show-current (or glancing at your shell prompt) before every commit. If you do slip, create the branch now - it points at the commit you just made - then reset main back one commit.

03
Connect a remote and push

A remote is a named pointer to a copy of the repository on another server. The conventional name is origin. Create an empty repository on GitHub first (do not initialize it with a README - an existing commit there would create a divergent history and your first push would be rejected), then link it and push your branch.

$ git remote add origin git@github.com:tyfsadik/app.git && git push -u origin feature/login
branch 'feature/login' set up to track 'origin/feature/login'.

The -u (short for --set-upstream) flag links your local branch to the remote one so that future git push and git pull need no arguments. You only do it once per branch. A full push transcript looks like this:

$ git push -u origin feature/login
Enumerating objects: 7, done. Counting objects: 100% (7/7), done. Delta compression using up to 8 threads Compressing objects: 100% (4/4), done. Writing objects: 100% (7/7), 602 bytes | 602.00 KiB/s, done. Total 7 (delta 0), reused 0 (delta 0), pack-reused 0 To github.com:tyfsadik/app.git * [new branch] feature/login -> feature/login branch 'feature/login' set up to track 'origin/feature/login'.

Confirm the remote is registered correctly:

VERIFY REMOTE CONFIGURATION

git remote -v
$ git remote -v
origin git@github.com:tyfsadik/app.git (fetch) origin git@github.com:tyfsadik/app.git (push)

How to verify: the branch should also appear on the GitHub web page for the repository. If the push fails with a permission error, your SSH key is not set up - see Troubleshooting. Also push main while you are here, so both branches exist remotely:

git push -u origin main
04
Inspect history and recover from a staged-file mistake

Before merging, learn the two inspection commands you will use daily. git log shows the commit chain; git diff shows line-level changes. Together they answer "what happened" and "what is about to happen" - run them before every commit and every merge until it becomes reflex.

READ THE HISTORY

git log --oneline --graph --all
$ git log --oneline --graph --all
* 7c2e4b8 (HEAD -> feature/login, origin/feature/login) Add draft login flow notes * 3f9a1c2 (main) Initial commit: README and .gitignore

The graph shows both commits in a straight line because main has not moved since you branched. HEAD marks which commit your working tree is based on.

Now rehearse the most common recovery: you staged something that should not be committed. Stage a stray file, then unstage it without losing the file itself:

UNSTAGE WITHOUT LOSING WORK

echo "scratch" > scratch.tmp
git add scratch.tmp
git restore --staged scratch.tmp
git status --short
$ git status --short
?? scratch.tmp

The ?? means the file is untracked again - back out of staging, but still on disk. (git restore --staged is the modern spelling; older tutorials use git reset HEAD <file>, which does the same thing.) Delete the scratch file when done. Warning: plain git restore <file> without --staged discards uncommitted changes in the working tree permanently - that is the destructive twin of this command.

05
Merge the feature branch back into main

Branching is only half the story; the change has to come home. Switch to main and merge. Because main never moved, Git performs a fast-forward: it simply slides the main pointer forward to the feature commit. No merge commit, no conflict.

MERGE INTO MAIN

git switch main
git merge feature/login
$ git merge feature/login
Updating 3f9a1c2..7c2e4b8 Fast-forward login-notes.md | 1 + 1 file changed, 1 insertion(+) create mode 100644 login-notes.md

With the merge done, the feature branch has served its purpose. Delete it locally and on the remote to keep the branch list clean - deleting a branch deletes only the pointer, never the commits, because they are now reachable from main:

CLEAN UP THE MERGED BRANCH

git branch -d feature/login
git push origin --delete feature/login
git push

git branch -d (lowercase) refuses to delete a branch that is not fully merged - a built-in safety check. The uppercase -D forces deletion and will silently discard unmerged work, so reach for it only when you are certain.

How to verify: ls should now show login-notes.md on main, and git log --oneline on main should include the "Add draft login flow notes" commit. If the merge instead reported a conflict, both branches changed the same lines - that scenario has its own lab, Merge Conflicts.

06
Pull to sync with the remote

Collaboration means the remote moves without you: a teammate pushes, or you edit a file in the GitHub web UI. git pull fetches those commits and merges them into your current branch. Simulate it by fetching first - git fetch downloads remote state without touching your working tree, which makes it the safe way to look before you leap:

FETCH, INSPECT, THEN PULL

git fetch origin
git status
git pull
$ git status
On branch main Your branch is up to date with 'origin/main'. nothing to commit, working tree clean
$ git pull
Already up to date.

When the remote does have new commits, the status line instead reads "Your branch is behind 'origin/main' by N commits", and git pull fast-forwards you forward. Make git pull the first command of every work session; merging a small drift daily is painless, merging a month of drift is not.

Common mistake: pushing before pulling. If a teammate pushed first, your push is rejected as "non-fast-forward". The fix is simply git pull (resolve any conflicts if they appear), then push again - covered in Troubleshooting.

Progress So Far

Testing & Validation

Run the two health-check commands below. They are the same pair you will run a dozen times a day in real work, and together they answer "where am I?" and "is anything unsaved?"

git log --oneline --graph --all && git status
$ git log --oneline --graph --all
* 7c2e4b8 (HEAD -> main, origin/main) Add draft login flow notes * 3f9a1c2 Initial commit: README and .gitignore
$ git status
On branch main Your branch is up to date with 'origin/main'. nothing to commit, working tree clean

You should see your commits on the branch and a clean working tree. If so, your history is tracked and pushed. Check three things specifically:

  • HEAD -> main and origin/main point at the same commit - local and remote are in sync.
  • Both of your commits appear in the log - nothing was lost in the merge.
  • The working tree is clean and the feature branch no longer appears - cleanup succeeded.

Final cross-check: open the repository on GitHub. The file list should show README.md, .gitignore, and login-notes.md, and the commit list should match your local git log exactly. If the web page disagrees with your terminal, trust the terminal and run git push - the local repository is the source of truth until you push.

Troubleshooting
  • Author unknown: set user.name/user.email before committing. If you already made commits with a wrong identity, fix the config, then amend the most recent one with git commit --amend --reset-author.
  • Push rejected: pull/rebase first; the remote has commits you lack. Run git pull, resolve any conflicts if Git reports them, commit the resolution, then push again. Do not reach for --force on a shared branch.
  • Committed a secret: remove it and rewrite history with git filter-repo, then rotate the secret. Deleting the file in a new commit is not enough - the old commit still contains it and is visible on GitHub. Rotation is mandatory because you must assume the secret was seen the moment it was pushed.
  • Permission denied (publickey) on push: GitHub cannot authenticate your SSH key. Test with ssh -T git@github.com; if it does not greet you by username, generate a key with ssh-keygen -t ed25519 and add the public half under GitHub → Settings → SSH keys. Alternatively switch the remote to HTTPS: git remote set-url origin https://github.com/tyfsadik/app.git.
  • Detached HEAD: you checked out a commit hash instead of a branch, so commits would not belong to any branch. Recover by creating a branch where you stand: git switch -c rescue, then merge or cherry-pick as needed. Nothing is lost as long as you do not switch away without creating that branch.

Key Results

Key Takeaways

  • Changes move in one direction: working tree → staging → local repo → remote. Nothing reaches the remote without a commit.
  • The staging area is a draft, not a formality - it is how you keep each commit focused on one logical change.
  • Branches are cheap pointers; create one per task and delete it after merging.
  • git status and git log --oneline --graph --all answer almost every "what is going on?" question - run them constantly.
  • Pull before you push, and never commit secrets: history is forever, so prevention beats cleanup.
