Azure VM Configuration with cloud-init and Key-Based SSH

IntermediateCloud~2 hours
az vmcloud-initSSH keysmanaged disk

You will deploy an Azure VM into your VNet, bootstrap it with cloud-init, and access it via key-based SSH only. By the end you will have a secured, reproducible cloud server configured at first boot.

This lab is the natural follow-on to the Virtual Network Deployment lab: instead of stopping at an empty network, you place a real workload inside one of its subnets. The theme is reproducible and secure by default - nothing is configured by hand after the VM exists. All software installation and service setup is declared once in a cloud-init file, applied automatically on first boot, and verified from your terminal. Access is locked down to a single public key and a single source IP, mirroring how you would treat any internet-facing cloud server in the real world.

Learning Objectives

  • Deploy a VM with SSH-key authentication.
  • Bootstrap packages and config with cloud-init.
  • Restrict inbound access to your IP only.
  • Verify the bootstrap from logs and live service state, not just the portal.
  • Time: ~2 hours · Difficulty: Intermediate · Prereqs: a VNet and the Azure CLI.

Architecture Overview

The deployment has four moving parts. The Azure CLI sends a single declarative az vm create request; Azure provisions the VM into your existing web subnet; the cloud-init file is passed in as custom data and executed by the cloud-init service on the very first boot; and the auto-created network security group (NSG) is tightened so only your public IP can reach port 22. There is no password path at any point - the only credential that ever works is your private SSH key.

Environment Setup

You will need: a VNet/subnet (from the VNet lab), the Azure CLI, and an SSH keypair.

Before you begin: note your public IP to scope SSH access.

Sign in and set defaults. Authenticate the CLI and point it at the subscription and resource group you used for the VNet lab, so every later command can omit the -g flag. Setting defaults once up front is a small habit that prevents the classic mistake of deploying a VM into the wrong resource group.

$ az login && az account set -s "My Subscription" && az configure --defaults group=tyf-rg location=canadacentral
A browser window opens; after sign-in the CLI prints your subscription list as JSON.

How to verify: run az account show -query name -o tsv and confirm it prints the subscription you intended. If it prints the wrong one, repeat az account set with the correct name or ID before going any further.

Create an SSH keypair if you do not have one. Ed25519 keys are short, fast, and the current best practice; there is no reason to use RSA for a new deployment. The public half (id_ed25519.pub) is what you hand to Azure - the private half never leaves your machine.

$ ssh-keygen -t ed25519 -C "taki@web01" -f ~/.ssh/id_ed25519
Your identification has been saved in /home/you/.ssh/id_ed25519
Your public key has been saved in /home/you/.ssh/id_ed25519.pub

Common mistake: overwriting an existing key. If ~/.ssh/id_ed25519 already exists, either reuse it or pick a new filename such as id_ed25519_azure - overwriting it will lock you out of everywhere the old key was authorized.

Record your current public IP. This is the address you will scope the SSH rule to in step 03. Using a documented example range below; substitute the value the command actually returns for you.

$ curl -s https://ifconfig.me; echo
203.0.113.10

Common mistake: looking the IP up on a "what is my IP" website while on VPN, then scoping the NSG to the VPN exit address instead of the address your SSH client will actually source from. Check it from the same terminal and network you will SSH from.

Step-by-Step Execution

01
Write a cloud-init file

cloud-init is the industry-standard bootstrap system baked into every major cloud Linux image. The file must start with the literal header #cloud-config on line one - without it the VM treats the content as inert data and nothing happens. The directives below are deliberately minimal: refresh package metadata, install nginx, then enable and start it. Because this is declarative, re-running the lab produces an identically configured server every time.

# cloud-init.yaml
#cloud-config
package_update: true
packages: [nginx]
runcmd:
  - systemctl enable -now nginx

package_update: true runs the equivalent of apt-get update so the package index is fresh; packages is a list of APT packages to install; runcmd executes arbitrary commands late in the boot, after packages are in place. The -now flag both enables nginx at boot and starts it immediately.

Common mistake: broken YAML. cloud-init files are whitespace-sensitive - a tab character or misaligned list item makes the run fail silently. Validate locally before deploying with cloud-init schema --config-file cloud-init.yaml if you have cloud-init installed locally, or at minimum paste it through a YAML linter.

02
Deploy the VM with key auth and cloud-init

One command creates the VM, attaches it to your existing web subnet, injects your public key for the taki user, and passes the cloud-init file as custom data. Passing -ssh-key-values (instead of -admin-password) is what disables password authentication in sshd - Azure configures the image for key-only auth automatically when a key is supplied. Each flag earns its place: -image Ubuntu2204 selects the LTS image alias, -vnet-name/-subnet place the NIC inside your own network rather than a throwaway one, and -custom-data wires in the bootstrap file from step 01.

az vm create -n web01 -image Ubuntu2204 -vnet-name vnet-a -subnet web -admin-username taki -ssh-key-values ~/.ssh/id_ed25519.pub -custom-data cloud-init.yaml

The command blocks for a minute or two while Azure provisions the resources (VM, NIC, public IP, managed OS disk, and an auto-created NSG named web01NSG), then returns a large JSON document. The two fields worth noting are the provisioning state and the public IP:

$ az vm create -n web01 -image Ubuntu2204 -vnet-name vnet-a -subnet web -admin-username taki -ssh-key-values ~/.ssh/id_ed25519.pub -custom-data cloud-init.yaml
"provisioningState": "Succeeded"
"publicIpAddress": "20.151.42.17"

How to verify: "provisioningState": "Succeeded" only means the VM resource exists - it says nothing about cloud-init, which typically still needs another 1-3 minutes to finish installing packages. Do not panic if nginx is not answering the second the command returns; step 05 shows how to wait properly.

Common mistake: omitting -vnet-name/-subnet. Without them, Azure silently creates a new VNet for the VM, and it will not be in the segmented network you built in the VNet lab. If that happened, delete the VM and redeploy - you cannot move a VM's NIC between VNets in place.

03
Restrict SSH to your IP

az vm open-port adds an inbound allow rule for port 22 to the VM's NSG, but its default source is * - the whole internet. Leaving SSH open to the world invites password-spraying and key-scanning bots within minutes, so the second half of the command rewrites that rule's source to the single /32 address you recorded during setup. Priority 100 places the rule ahead of the lower-priority default rules so it takes effect deterministically.

$ az vm open-port -n web01 -port 22 -priority 100 && az network nsg rule update -g tyf-rg -nsg-name web01NSG -n open-port-22 -source-address-prefixes 203.0.113.10/32
"sourceAddressPrefix": "203.0.113.10/32"

How to verify: list the effective rules and confirm exactly one inbound allow exists for port 22 with your /32 as the source:

az network nsg rule list -g tyf-rg --nsg-name web01NSG -o table

Common mistake: scoping the rule to an IP that later changes. Home connections usually sit behind dynamic DHCP addresses; if SSH suddenly stops working next week, re-run curl -s https://ifconfig.me and update the rule with the new address before assuming the VM is broken.

04
Connect over SSH for the first time

Rather than copying the public IP out of the portal, query it directly from Azure and feed it straight to the SSH client. The $() substitution runs az vm show -d (the -d shows runtime details including the public IP) and prints just the address as plain text. The private key in the default location is offered automatically, so no password prompt should ever appear.

ssh taki@$(az vm show -d -n web01 -query publicIps -o tsv)

On first connection the client asks you to trust the server's host key - this is normal exactly once per host:

$ ssh taki@$(az vm show -d -n web01 -query publicIps -o tsv)
The authenticity of host '20.151.42.17' can't be established.
ED25519 key fingerprint is SHA256:xK3...
Are you sure you want to continue connecting (yes/no)? yes
taki@web01:~$

How to verify: you land at a shell prompt on web01 without ever being asked for a password. If you are prompted for a password at any point, key authentication is not in play - see the Troubleshooting section before typing anything.

Common mistake: a REMOTE HOST IDENTIFICATION HAS CHANGED warning on a later rebuild. Deleting and recreating the VM gives the same IP a new host key; remove the stale entry with ssh-keygen -R 20.151.42.17 and reconnect.

05
Confirm cloud-init finished cleanly

Never assume the bootstrap ran - check it. cloud-init status --wait blocks until the run completes and then reports the outcome, which makes it perfect for scripts and for the few minutes right after provisioning. A done status with exit code 0 means every directive in your file executed without error.

taki@web01:~$ cloud-init status --wait
..............
status: done

If anything failed, the human-readable log of everything your directives printed lives in /var/log/cloud-init-output.log; the structured module-by-module trace is in /var/log/cloud-init.log:

taki@web01:~$ tail -n 5 /var/log/cloud-init-output.log
Setting up nginx (1.18.0-6ubuntu14.4) ...
Created symlink /etc/systemd/system/multi-user.target.wants/nginx.service ...
Cloud-init v. 23.x finished at ...

Common mistake: reading status: done as proof the service works. cloud-init reports on its own run, not on the health of what it installed - a package can install fine and still fail to start. The next two checks close that gap.

06
Verify the service and the security posture

Two final checks turn "the VM exists" into "the lab worked". First, confirm nginx is actually running and answering on the VM itself - testing locally on the box sidesteps the NSG, which currently only allows port 22:

taki@web01:~$ systemctl is-active nginx && curl -s localhost | head -n 3
active
<!DOCTYPE html>
<html>
<head>

Second, prove the security posture rather than trusting it. Ask the running sshd for its effective configuration and confirm password authentication is off - this is the check that validates the key-only decision made back in step 02:

taki@web01:~$ sudo sshd -T | grep -iE 'passwordauthentication|pubkeyauthentication'
passwordauthentication no
pubkeyauthentication yes

How to verify: active, the nginx welcome HTML, and passwordauthentication no together mean the server is bootstrapped, serving, and unreachable by password guessing. If you later want to browse to nginx from your own machine, open port 80 the same scoped way as step 03: az vm open-port -n web01 -port 80 -priority 110 and then update the rule's source to your /32.

Testing & Validation

Everything below runs from your own machine in one shot - no portal clicking required. The final command chains the whole validation: resolve the VM's public IP from Azure, connect with your key, and ask systemd whether the cloud-init-installed service is alive.

ssh taki@$(az vm show -d -n web01 -query publicIps -o tsv) 'systemctl is-active nginx'

You should connect with your key (no password) and see active, proving cloud-init bootstrapped the server.

For a complete end-to-end picture, run the full validation sequence and compare against the expected results:

# 1. VM exists and is running
az vm show -d -n web01 -query '{state:powerState,ip:publicIps}' -o jsonc
#    { "state": "VM running", "ip": "20.151.42.17" }

# 2. NSG exposes port 22 to your IP only
az network nsg rule list -g tyf-rg --nsg-name web01NSG \
  -query "[?destinationPortRange=='22'].{src:sourceAddressPrefix,access:access}" -o table
#    Src              Access
#    ---------------  --------
#    203.0.113.10/32  Allow

# 3. Key-only SSH and the bootstrapped service
ssh taki@20.151.42.17 'systemctl is-active nginx'
#    active

All three checks passing is your definition of done: the resource is healthy, the network exposure matches intent, and the unattended bootstrap produced a working service. If any one fails, the Troubleshooting section maps the symptom to a fix.

Troubleshooting
  • cloud-init did not run: check /var/log/cloud-init-output.log on the VM. The most common cause is a missing #cloud-config first line or broken YAML indentation - fix the file, then redeploy (custom data only executes on first boot, so editing the file alone does nothing for an existing VM).
  • SSH times out: confirm the NSG allows port 22 from your current IP. Also re-check that your public IP has not changed since step 03 (curl -s https://ifconfig.me) and update the rule's source if it has.
  • Password prompt: deploy with -ssh-key-values, not -admin-password. A password prompt on a key-deployed VM usually means the client offered no key the server accepts.
  • Permission denied (publickey): you are connecting as the wrong user or with the wrong key. The login name must match -admin-username (taki), and the private key must be the pair of the .pub file passed at creation - specify it explicitly with ssh -i ~/.ssh/id_ed25519 taki@... if your agent is offering a different one.
  • az vm create fails with a quota or SKU error: new subscriptions have low per-region vCPU quotas and some sizes are unavailable in some regions. Retry with a smaller size such as -size Standard_B2s, or request a quota increase in the portal under Subscriptions › Usage + quotas.

Key Takeaways

  • Declare the server's whole first-boot configuration in one cloud-init file - it makes the build reproducible and reviewable.
  • Passing -ssh-key-values at creation is what disables password authentication; key-only SSH is a deploy-time decision, not an afterthought.
  • az vm open-port defaults to an internet-wide source - always follow it by scoping the rule to your own /32.
  • "provisioningState": "Succeeded" means the VM exists, not that it is configured; use cloud-init status --wait to know when bootstrap is really finished.
  • Verify posture empirically: systemctl is-active, curl localhost, and sshd -T beat trusting the portal.
