Azure NSGs and Route Tables for Traffic Control

IntermediateCloud~3 hours
NSGUDReffective routespriority

You will filter traffic with Network Security Groups and steer it with user-defined routes (UDRs), including forcing traffic through a firewall appliance. By the end you will control both what is allowed and the path packets take.

These two services answer different questions, and keeping them separate in your head is the key to this lab. An NSG decides whether a packet is allowed: it is a stateful, 5-tuple filter (source IP, source port, destination IP, destination port, protocol) attached to a subnet or a NIC. A route table decides where an allowed packet goes next: it overrides Azure's built-in system routes so traffic between subnets, or out to the internet, takes the path you choose. Defense in depth in Azure networking means using both - the NSG shrinks what can talk at all, and the UDR guarantees that what can talk still passes your inspection point.

The scenario: a three-tier lab VNet with a web subnet, an app subnet, and a firewall appliance (a network virtual appliance, or NVA) in its own subnet. Internet clients may reach the web tier on 443 only; the app tier may not reach the internet directly - everything it sends must hairpin through the NVA, which inspects and forwards it.

Learning Objectives

  • Write priority-ordered NSG rules for least privilege.
  • Create a UDR that overrides default system routes.
  • Inspect effective rules and routes on a NIC.
  • Time: ~3 hours · Difficulty: Intermediate · Prereqs: a VNet with VMs.

Architecture Overview

Read the diagram left to right as a packet's life story. Inbound, the internet hits the web subnet, where the NSG is the gatekeeper: priority 100 allows TCP 443, and the implicit DenyAllInBound at priority 65500 swallows everything else. Outbound, the app subnet has a route table associated with it whose 0.0.0.0/0 route points at the firewall appliance as the next hop, so nothing leaves the subnet uninspected.

graph LR Net((Internet)) -->|NSG allow 443| Web[web subnet] Web -->|UDR next hop| FW[Firewall appliance] FW --> App[app subnet]

Two properties of the drawing matter more than the drawing itself. First, NSG evaluation is priority-ordered, lowest number first: the first rule that matches a flow decides it, and rules below the match are never evaluated. Second, route selection follows a fixed precedence: user-defined routes beat BGP routes, which beat system routes. That precedence is why a single UDR can redirect an entire subnet's egress without touching any VM configuration.

You will need: a VNet with at least two subnets and the Azure CLI.

Step-by-Step Execution

01
Create an NSG allow rule
az network nsg create -n web-nsg && az network nsg rule create -nsg-name web-nsg -n allow-https -priority 100 -destination-port-ranges 443 -access Allow -protocol Tcp

WHAT: this creates the NSG itself, then adds an inbound rule named allow-https at priority 100 permitting TCP traffic to destination port 443. WHY priority 100: Azure reserves 65000-65500 for its default rules and 100-4096 is the usable band for your own. Starting your most specific allow at 100 leaves room above it for even-more-specific exceptions later, and keeps it well ahead of the final DenyAllInBound at 65500. Priority ordering is the whole game - a rule that never gets evaluated because a broader rule matched first is indistinguishable from a rule that does not exist.

Every new NSG comes with three inbound defaults you did not write: AllowVNetInBound (65000), AllowAzureLoadBalancerInBound (65001), and DenyAllInBound (65500), plus a mirrored set for outbound. Your allow rule only has to land below 65000 in number to beat the catch-all deny. For least privilege, also add an explicit deny for management ports from the internet so the intent is documented in the rule list, not just implied by the catch-all.

FULL RULE SET - allow 443, explicitly deny management ports

az network nsg rule create --nsg-name web-nsg -n allow-https \
  --priority 100 --direction Inbound --access Allow --protocol Tcp \
  --source-address-prefixes Internet --source-port-ranges '*' \
  --destination-address-prefixes 10.0.1.0/24 --destination-port-ranges 443

az network nsg rule create --nsg-name web-nsg -n deny-mgmt-internet \
  --priority 200 --direction Inbound --access Deny --protocol Tcp \
  --source-address-prefixes Internet --source-port-ranges '*' \
  --destination-address-prefixes '*' --destination-port-ranges 22 3389

An NSG that is not associated with anything filters nothing. Attach it to the web subnet so it applies to every NIC in that subnet:

ASSOCIATE THE NSG WITH THE WEB SUBNET

az network vnet subnet update --vnet-name lab-vnet -n web-subnet \
  --network-security-group web-nsg

VERIFY - the custom rules should list ahead of the defaults

az network nsg rule list --nsg-name web-nsg -o table

Name                Priority  Direction  Access  Protocol  DestinationPortRanges
------------------  --------  ---------  ------  --------  ---------------------
allow-https         100       Inbound    Allow   Tcp       443
deny-mgmt-internet  200       Inbound    Deny    Tcp       22, 3389

Common mistake: creating the rule against the wrong NSG name (every lab has at least one orphaned NSG from a previous attempt) or forgetting the subnet association. Verify with the table above - if your rule appears but traffic behavior does not change, the association is the first thing to check with az network vnet subnet show --vnet-name lab-vnet -n web-subnet --query networkSecurityGroup.

02
Create a UDR forcing traffic via a firewall

A user-defined route overrides Azure's default routing so traffic must pass your inspection point.

az network route-table create -n rt-app && az network route-table route create -route-table-name rt-app -n to-fw -address-prefix 0.0.0.0/0 -next-hop-type VirtualAppliance -next-hop-ip-address 10.0.3.4

WHAT: a route table named rt-app holding one route, to-fw, that sends all traffic matching 0.0.0.0/0 to next-hop type VirtualAppliance at 10.0.3.4. WHY: by default, Azure system routes give every subnet a direct path to the internet and to each other. The moment this UDR is associated with the app subnet, UDR precedence kicks in and the subnet's default route becomes the NVA - without logging into a single VM. This is the standard pattern for forced tunneling through a firewall, and VirtualAppliance is the next-hop type that requires an explicit IP (unlike Internet or VirtualNetworkGateway, which are symbolic).

Like the NSG, a route table does nothing until it is associated with a subnet. Associate it with the app subnet, and enable IP forwarding on the NVA's NIC - Azure drops packets delivered to a NIC whose IP is not the packet's destination unless forwarding is explicitly on. That Azure-side flag is separate from the OS-level forwarding inside the appliance, and you need both.

ASSOCIATE THE ROUTE TABLE AND ENABLE FORWARDING ON THE NVA

az network vnet subnet update --vnet-name lab-vnet -n app-subnet \
  --route-table rt-app

# Azure-side: allow the appliance NIC to receive packets not addressed to it
az network nic update -n fw01VMNic --ip-forwarding true

# OS-side (on the appliance itself, e.g. a Linux NVA):
#   sysctl -w net.ipv4.ip_forward=1
#   echo "net.ipv4.ip_forward=1" >> /etc/sysctl.conf

VERIFY - route table contents and subnet association

az network route-table route list -g lab-rg --route-table-name rt-app -o table

Name   AddressPrefix  NextHopType       NextHopIpAddress
-----  -------------  ----------------  ------------------
to-fw  0.0.0.0/0      VirtualAppliance  10.0.3.4

Common mistake: pointing --next-hop-ip-address at the wrong interface of a multi-homed NVA (it must be an IP in a subnet the routing VM can reach, typically the appliance's trusted or LAN-side address), or forgetting that a route table can only be associated with subnets in the same region as the table. Also note that the address prefix is matched most-specific-first within the table: a 0.0.0.0/0 route is a catch-all, so any more specific route you add later for the same subnet wins over it.

03
Inspect effective rules and routes

WHAT: Azure merges system routes, your UDRs, and any BGP-learned routes into one effective route table per NIC, and merges all NSGs applied at the subnet and NIC level into one effective security rule view. WHY: this merged view is the ground truth. The individual resources can each look correct while the combination is wrong - a UDR on the wrong subnet, an old NSG still attached to a NIC - and the effective views are the only place where those composition errors become visible without sending traffic.

$ az network nic show-effective-route-table -n web01VMNic -o table
Source AddressPrefix NextHopType NextHopIp User 0.0.0.0/0 VirtualAppliance 10.0.3.4

The Source column tells you where each route came from: Default for system routes, User for your UDRs, VirtualNetworkGateway for BGP-learned routes. In the output above, the User-sourced 0.0.0.0/0 entry confirms the UDR is associated and winning. Note this NIC-level command reflects the route table of the NIC's subnet - run it against a NIC in the app subnet (e.g. app01VMNic) to see the to-fw route in effect.

EFFECTIVE SECURITY RULES - the merged NSG view for a NIC

az network nic list-effective-nsg -n web01VMNic -o table

# For full detail, ask for the JSON and filter to inbound allows:
az network nic list-effective-nsg -n web01VMNic \
  --query "value[].association.networkSecurityGroup.id" -o tsv

Common mistake: running these commands immediately after a change and reading a stale view - effective views can take a minute to converge after an association change. If the output does not match what you just configured, wait 60-90 seconds and re-run before assuming the configuration is wrong. Also remember both commands target a NIC, not a VM: use az vm nic list -g lab-rg --vm-name web01 if you only know the VM name.

Testing & Validation

Configuration views tell you what Azure thinks the network is; the tests below prove what it does. Run all three - a policy lookup, a real connection, and a route check - because each catches a different class of mistake.

az network nic show-effective-route-table -n web01VMNic -query "value[?nextHopType=='VirtualAppliance']"

You should see the appliance as the next hop for 0.0.0.0/0, confirming traffic is forced through your firewall. NSG denies should appear in flow logs.

First, use Network Watcher's IP flow verify to ask the policy engine directly whether a specific 5-tuple is allowed, without sending a single packet. This simulates an internet client at 203.0.113.10 hitting the web VM on 443:

POLICY CHECK - IP flow verify (requires the Network Watcher extension)

az network watcher test-ip-flow --vm web01 --direction Inbound \
  --protocol Tcp --local 10.0.1.4:443 --remote 203.0.113.10:54321

# Expected:
#   "access": "Allow",
#   "ruleName": "securityRule/allow-https"

# The same probe against port 22 should return:
#   "access": "Deny",
#   "ruleName": "securityRule/deny-mgmt-internet"

Second, test with real traffic, because stateful behavior and the appliance's own rules are not visible to a policy lookup. From an external host, HTTPS should connect and SSH should time out:

REAL TRAFFIC - allowed 443 succeeds, denied 22 times out

curl -vk https://<web01-public-ip>/       # TLS handshake completes
ssh -o ConnectTimeout=5 <web01-public-ip> # hangs, then: Connection timed out

The difference between timed out and connection refused is diagnostic gold: a timeout means the NSG dropped the packet (no listener ever saw it), while a refusal means the packet arrived and the host rejected it - in other words, your NSG let it through. Third, confirm from a VM in the app subnet that egress really traverses the appliance: traceroute to any external address should show 10.0.3.4 as the first hop outside the subnet.

OPTIONAL - enable NSG flow logs for ongoing evidence of denies

az network watcher flow-log create -n web-nsg-flowlog \
  --nsg web-nsg --storage-account labflowlogsa \
  --location eastus --format JSON --log-version 2

Flow logs record every allowed and denied 5-tuple against the rule that decided it. After your SSH test above, the flow log for web-nsg should contain deny records citing deny-mgmt-internet - the written proof an auditor (or your future self) wants that the deny rule is doing its job.

Troubleshooting
  • Rule has no effect: a lower-priority number wins; reorder so the intended rule precedes broad denies. Check for a stale or duplicate rule at a lower number with az network nsg rule list --nsg-name web-nsg -o table - a forgotten allow-all at priority 90 silently overrides everything below it. Also confirm the NSG is actually associated: rules on an unattached NSG evaluate against nothing.
  • UDR ignored: associate the route table with the subnet, not just create it. Creating rt-app and its routes changes nothing until az network vnet subnet update ... --route-table rt-app runs. Verify with az network vnet subnet show --vnet-name lab-vnet -n app-subnet --query routeTable - a null result means the association never happened or targeted a different subnet.
  • Appliance drops traffic: enable IP forwarding on the appliance NIC. Azure delivers routed packets to the NVA's NIC, but the NIC discards anything not addressed to its own IP unless --ip-forwarding true is set on the Azure side and the OS inside the appliance forwards too (net.ipv4.ip_forward=1 on Linux). Forgetting one of the two layers is the classic half-working NVA: the route table is perfect and packets still vanish.
  • Traffic is allowed but the app still cannot connect: check for NSGs stacked at both levels. An NSG can attach to the subnet and to the NIC, and traffic must pass both - they are evaluated independently, subnet first for inbound. A restrictive NIC-level NSG from an earlier experiment is a frequent invisible blocker. Compare both associations in the list-effective-nsg output.
  • Asymmetric routing through the appliance: if the UDR forces app-subnet egress through the NVA but return traffic from the web subnet takes the direct system route, stateful inspection on the NVA breaks (it sees only half the conversation) and connections reset. Fix by putting matching UDRs on every subnet involved so flows traverse the appliance symmetrically in both directions, or by disabling the NVA's statefulness for that flow if the design genuinely requires asymmetry.

Key Takeaways

  • NSGs filter, route tables steer. An NSG answers "is this flow allowed?" on the 5-tuple; a UDR answers "where does an allowed packet go next?" Use both - neither substitutes for the other.
  • Priority order is the policy. Lowest number wins and evaluation stops at the first match, so specific allows go low in number and the catch-all deny (yours or the built-in 65500) cleans up behind them.
  • Nothing works until it is associated. NSGs attach to subnets or NICs; route tables attach to subnets. An unassociated resource is inert - most "the rule does nothing" bugs are association bugs.
  • Route precedence is fixed: user-defined routes beat BGP routes beat system routes. One UDR on a subnet redirects its whole egress path with zero guest-OS changes.
  • Trust the effective views, then prove with traffic. show-effective-route-table and list-effective-nsg show the merged truth; test-ip-flow, a real curl/ssh probe, and NSG flow logs confirm the behavior.
  • An NVA needs forwarding at two layers. Azure-side IP forwarding on the NIC and OS-side forwarding in the guest - one without the other drops routed packets silently.
