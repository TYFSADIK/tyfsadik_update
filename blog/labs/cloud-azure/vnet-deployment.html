Azure Virtual Network Deployment with Subnets and Peering

IntermediateCloud~2 hours
VNetsubnetspeeringCIDR

You will deploy an Azure Virtual Network with tiered subnets and peer it to a second VNet. By the end you will have a segmented cloud network foundation that VMs and services can join.

A Virtual Network (VNet) is the fundamental isolation boundary in Azure networking: every VM, container app, or private endpoint you deploy lives inside one. Getting the address plan right on day one matters because the choices you make here - the VNet CIDR range, how you carve it into subnets, and which VNets are allowed to talk to each other - are painful to change once workloads are running. This lab walks through the entire lifecycle with the Azure CLI: planning a non-overlapping address space, creating the VNet, adding tiered subnets, and connecting two VNets with bidirectional peering so resources can reach each other over the Microsoft backbone instead of the public internet.

Learning Objectives

  • Create a VNet with non-overlapping subnets.
  • Peer two VNets for private connectivity.
  • Verify routing between peered networks.
  • Plan CIDR ranges so VNets can be peered later without renumbering.
  • Interpret peering states (Initiated vs Connected) and diagnose why traffic does not flow.
  • Time: ~2 hours · Difficulty: Intermediate · Prereqs: the Azure CLI configured.

Architecture Overview

The lab builds two VNets. vnet-a (10.0.0.0/16) holds the application tiers: a web subnet for internet-facing or load-balanced front ends and an app subnet for middle-tier services that should never be directly exposed. vnet-b (10.1.0.0/16) holds the data subnet - databases and storage that only the app tier should reach. Splitting data into its own VNet models a common production pattern where the data platform is managed by a different team or subscription and is connected on purpose, not by default.

graph LR subgraph VNet-A 10.0.0.0/16 Web[web 10.0.1.0/24] App[app 10.0.2.0/24] end subgraph VNet-B 10.1.0.0/16 Data[data 10.1.1.0/24] end App <-->|peering| Data

A few design notes on why it is built this way:

  • /16 VNets, /24 subnets: each VNet has 65,536 addresses and each subnet 256 (251 usable - Azure reserves five addresses per subnet for its own routing and DNS). /24 leaves room to grow; you can add dozens more subnets per VNet later.
  • Non-overlapping ranges: 10.0.0.0/16 and 10.1.0.0/16 share no addresses. VNet peering flat-out refuses overlapping address spaces, so planning this up front is what makes the peering step possible at all.
  • Peering, not a VPN gateway: peering is free of gateway VMs, keeps traffic on the Microsoft backbone, and adds no bandwidth cap beyond the VMs themselves. A VPN gateway would cost money and add latency for the same east-west traffic.
  • Peering is not transitive: if you later peer vnet-b to a third vnet-c, vnet-a cannot reach vnet-c through vnet-b unless you add gateway transit or a network virtual appliance. Design for this now, not after the incident.

Environment Setup

You will need: the Azure CLI authenticated with a default resource group set.

Before you begin: plan non-overlapping CIDR ranges; peered VNets cannot overlap.

Confirm you are logged in and pointed at the right subscription before creating anything. Networking mistakes are quiet - the CLI will happily deploy into the wrong subscription if you let it.

$ az account show --query "{name:name, id:id, state:state}" -o table
Name id state ------------- ----------------------------------- -------- Pay-As-You-Go 11111111-2222-3333-4444-555555555555 Enabled

Everything in this lab lives in one resource group so cleanup is a single command at the end. Create it and set it (plus a region) as your CLI defaults so you can stop typing -g on every command:

az group create -n tyf-net-rg -l eastus
Creates the lab resource group in East US.
az configure --defaults group=tyf-net-rg location=eastus
All later commands assume this group and region.
$ az group show -n tyf-net-rg --query provisioningState -o tsv
Succeeded

Common mistake: forgetting that az configure --defaults persists across terminal sessions. If a later lab deploys somewhere unexpected, check az configure --list-defaults first.

Step-by-Step Execution

01
Create the VNet and subnets

What: create vnet-a with its /16 address space and the first subnet (web) in one command. Why: az network vnet create requires at least one subnet if you pass subnet flags, so defining the web tier up front saves a second call. The subnet prefix must sit inside the VNet prefix - 10.0.1.0/24 is the first /24 carve-out of 10.0.0.0/16.

az network vnet create -n vnet-a -address-prefixes 10.0.0.0/16 -subnet-name web -subnet-prefixes 10.0.1.0/24

The command returns the full VNet object as JSON. The fields worth checking are addressSpace and the subnet's provisioningState:

$ az network vnet show -n vnet-a --query "{prefixes:addressSpace.addressPrefixes, subnets:subnets[].name}" -o json
{ "prefixes": [ "10.0.0.0/16" ], "subnets": [ "web" ] }

How to verify: az network vnet list -o table should show vnet-a with provisioning state Succeeded. Common mistake: typos in the CIDR (e.g. 10.0.0.0/8 when you meant /16) succeed silently - nothing validates your intent, only the syntax. Always echo the address space back with the query above before moving on.

02
Add a second subnet

What: add the app subnet to vnet-a. Why: tiers belong in separate subnets because Network Security Groups and route tables attach to subnets, not to individual VMs. If web and app shared a subnet, you could not write an NSG rule that lets the internet reach web but not app - the segmentation this whole lab is about would be impossible.

az network vnet subnet create -vnet-name vnet-a -n app -address-prefixes 10.0.2.0/24

List the subnets to confirm both exist and did not overlap:

$ az network vnet subnet list -vnet-name vnet-a -o table
Name AddressPrefix PrivateEndpointNetworkPolicies ------ --------------- ------------------------------ app 10.0.2.0/24 Enabled web 10.0.1.0/24 Enabled

Common mistake: trying to create a subnet whose range overlaps an existing one (say 10.0.1.128/25) fails with NetcfgSubnetRangesOverlap. Azure checks every new subnet against its siblings, which is your safety net - but the error means you have to pick a free range, so keep a written map of what is allocated.

03
Peer two VNets

What: create the second VNet and connect the two with peering. Why: peering is how separate VNets exchange private traffic. One critical detail trips up almost everyone the first time: peering is a pair of one-way links. Creating a-to-b alone leaves the peering stuck in the Initiated state; traffic only flows once the reverse link b-to-a also exists and both sides report Connected.

First, create vnet-b with its data subnet. Notice the completely different /16 - this is the non-overlap requirement in action:

az network vnet create -n vnet-b --address-prefixes 10.1.0.0/16 --subnet-name data --subnet-prefixes 10.1.1.0/24
Second VNet with the data tier; ranges must not overlap vnet-a.

Now create the first half of the peering pair, from vnet-a to vnet-b:

$ az network vnet peering create -n a-to-b -vnet-name vnet-a -remote-vnet vnet-b -allow-vnet-access
"peeringState": "Connected"

--allow-vnet-access is the flag that actually permits traffic between the address spaces; without it the peering exists but drops packets. Then create the reverse direction. Until this command runs, the first peering sits at Initiated and nothing routes:

$ az network vnet peering create -n b-to-a --vnet-name vnet-b --remote-vnet vnet-a --allow-vnet-access
"peeringState": "Connected"

Confirm both directions finished handshaking - you are looking for Connected on each side:

$ az network vnet peering list -vnet-name vnet-a --query "[].{name:name, state:peeringState, access:allowVirtualNetworkAccess}" -o table
Name State Access ------ --------- -------- a-to-b Connected True
$ az network vnet peering list -vnet-name vnet-b --query "[].{name:name, state:peeringState}" -o table
Name State ------ --------- b-to-a Connected

Common mistake: creating only one direction and assuming it worked because the command succeeded. The CLI happily creates a half-pair. How to verify: a peering stuck at Initiated always means the reverse link is missing - create it, do not delete and retry the existing one.

Testing & Validation

az network vnet peering show -n a-to-b -vnet-name vnet-a -query peeringState -o tsv

You should see Connected. With both directions peered, resources in app and data subnets can reach each other privately.

State checks prove the control plane agreed to peer, but they do not prove packets flow. The authoritative data-plane check is the effective routes on a network interface. If you have a VM in the app subnet (see the Azure VM Configuration lab), look at what its NIC learned from the peering:

$ az network nic show-effective-route-table --ids $(az vm show -n app-vm-01 --query networkProfile.networkInterfaces[0].id -o tsv) -o table
Source State Address Prefix Next Hop Type Next Hop IP -------- ------- ---------------- ---------------- ------------- Default Active 10.0.0.0/16 VnetLocal Default Active 10.1.0.0/16 VNetPeering Default Active 0.0.0.0/0 Internet

The line that matters is 10.1.0.0/16 → VNetPeering: the app subnet now routes the entire vnet-b address space across the peering. No manual route table entries were needed - peering programs these system routes automatically on every subnet in both VNets.

For an end-to-end test, deploy a small VM into the data subnet and one into app, then ping or SSH between their private IPs:

az vm create -n data-vm-01 --image Ubuntu2204 --vnet-name vnet-b --subnet data --size Standard_B1s --admin-username azureuser --generate-ssh-keys
Cheapest test VM; delete it when validation is done.
$ ssh azureuser@app-vm-01 "ping -c 3 10.1.1.4"
3 packets transmitted, 3 received, 0% packet loss, time 2003ms rtt min/avg/max/mdev = 1.242/1.389/1.604/0.151 ms

Sub-2ms latency between VNets in the same region is the signature of peering on the Microsoft backbone - a path through the public internet would show noticeably higher and more variable times. Note that default NSG rules allow VNet-to-VNet traffic, so this works before you lock anything down; once you attach NSGs in the next lab, expect to re-visit this test.

Cleanup when you are done, so test VMs do not bill overnight:

az group delete -n tyf-net-rg --yes --no-wait
Deletes the VNets, peerings, subnets, and test VMs in one shot.
Troubleshooting
  • Peering stuck at Initiated: create the peering in both directions; it requires a pair. Check both sides with az network vnet peering list -vnet-name <vnet> - whichever side is missing a link is the one you still need to create.
  • Overlapping address space: peered VNets must use non-overlapping CIDR ranges. The error NetcfgAddressPrefixesOverlapForPeering means exactly this. The only clean fix is to recreate one VNet with a different range - address spaces of peered VNets cannot be edited in place without removing the peering first.
  • No connectivity despite peering: check NSGs and that -allow-vnet-access is set. Run az network vnet peering show -n a-to-b -vnet-name vnet-a --query allowVirtualNetworkAccess - if it returns false, update the peering: az network vnet peering update -n a-to-b -vnet-name vnet-a --set allowVirtualNetworkAccess=true.
  • Ping fails but SSH works (or vice versa): this is almost never peering. NSG default rules allow all VNet-internal traffic, but a VM-level firewall (e.g. ufw on Ubuntu) or a custom NSG rule may block ICMP while allowing TCP/22. Test with a TCP tool like curl -v telnet://10.1.1.4:22 before blaming the network.
  • Cannot add a subnet or extend the address space after peering: Azure blocks az network vnet update --add addressSpace.addressPrefixes on peered VNets. You must delete the peering, change the address space, then re-create both peering directions - plan the /16 sizing generously at the start to avoid this outage-shaped maintenance.

Extension Ideas

  • Place a VM in a subnet with Azure VM Configuration.
  • Control traffic with NSGs & Route Tables.
  • Codify the whole network with IaC.
  • Add a third VNet and observe first-hand that peering is not transitive, then fix it with a hub-and-spoke design where a hub VNet hosts shared services.
  • Attach an NSG to the data subnet that only accepts traffic from 10.0.2.0/24 (the app tier), and re-run the connectivity test from the web subnet to prove it now fails.

Key Results

  • Deployed a VNet with two non-overlapping subnets.
  • Connected two VNets via bidirectional peering.
  • Confirmed the peering reached the Connected state.
  • Built a segmented foundation for cloud workloads.

Key Takeaways

  • Address planning is the real deliverable: non-overlapping CIDR ranges are a hard prerequisite for peering and are expensive to fix later.
  • Subnets are the unit of segmentation - NSGs and route tables attach there, so tier your workloads across subnets from day one.
  • Peering is a pair of one-way links; Initiated means the reverse side is missing, and --allow-vnet-access is what actually permits traffic.
  • Peering is not transitive: each pair of VNets that must talk needs its own peering (or a hub-and-spoke design).
  • Verify the data plane, not just the control plane: Connected state plus an effective-route-table entry plus a real ping is the complete proof.
