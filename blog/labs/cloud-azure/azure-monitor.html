You will route VM metrics and logs into a Log Analytics workspace, query them with KQL, and create an alert that notifies you on a threshold. By the end you will detect problems before users do.

This lab builds the observability backbone every production environment needs: a central place where telemetry lands, a query language to interrogate it, and a rule that wakes a human up when something drifts out of spec. Nothing here is abstract, every command below ran against a real VM, and every output block shows what you should expect to see. Follow it end to end and you will have a working detect-and-notify pipeline you can reuse for any Azure resource.

We work with three building blocks. Azure Monitor is the platform-level service that collects metrics and logs from every resource. Log Analytics is the workspace where log data is stored in tables (Heartbeat, Perf, Event, Syslog) and queried. KQL (Kusto Query Language) is the read-only language you use to search, filter, and aggregate those tables, the same language Microsoft Sentinel is built on, so the skills transfer directly to SOC work.

Learning Objectives

  • Connect resources to a Log Analytics workspace.
  • Query telemetry with KQL.
  • Create a metric/log alert with an action group.
  • Time: ~3 hours · Difficulty: Intermediate · Prereqs: a running Azure VM.

Architecture Overview

The data path has four hops. The Azure Monitor Agent (AMA) on the VM reads performance counters and event logs locally, then ships them over HTTPS to the ingestion endpoint. A Data Collection Rule (DCR) tells the agent exactly which counters and logs to collect and which workspace to send them to, no DCR, no data. The Log Analytics workspace stores everything in typed tables with a retention window (30 days by default). Finally, an alert rule evaluates either a metric (near-real-time, pre-aggregated numbers like CPU percentage) or a scheduled KQL query against the workspace, and when the condition trips it invokes an action group, email, SMS, webhook, Logic App, whatever you wire up.

Understanding which hop is broken is 90% of troubleshooting in this lab: agent installed but no DCR means silence; DCR pointing at the wrong workspace means you are querying an empty room; a valid rule with a broken action group means alerts fire into the void.

Metrics vs Logs: Choosing the Right Signal

Azure Monitor gives you two fundamentally different data types, and picking the wrong one is the most common design error beginners make. Metrics are lightweight, pre-aggregated numbers (CPU %, disk bytes, network in/out) stored for 93 days at no ingestion cost for platform metrics. They are near-real-time, typically under a minute old, which makes them the right choice for threshold alerting: "CPU over 80% for 5 minutes." Logs are rich, structured records (perf counter samples, syslog lines, Windows events) stored in Log Analytics tables. They cost money to ingest and retain, arrive with a few minutes of latency, but can answer questions metrics never could: "which process spiked," "what did sshd log right before the outage."

The rule of thumb this lab follows: alert on metrics, investigate with logs. The metric alert in step 03 wakes you up fast and cheap; the KQL queries in step 02 are what you run at 2 a.m. to figure out why. A log alert (the scheduled query also shown in step 03) is the middle ground, use it only when the condition you care about cannot be expressed as a simple numeric threshold, like "zero heartbeat rows in the last 10 minutes."

Environment Setup

Prerequisites

  • An Azure subscription with Contributor access on a resource group, and a running VM (Linux or Windows) to monitor.
  • Azure CLI 2.5x; no KQL experience needed, though basic familiarity with tables and filters helps.
  • Assumed skills: deploying a VM (see the Azure VM Configuration lab) and running az commands.

You will need: a VM, a Log Analytics workspace, and the Azure CLI.

Before you begin: enable diagnostic settings so data actually flows to the workspace.

Concretely, the prerequisites are: an Azure subscription where you hold at least Contributor on the resource group, one running Linux or Windows VM (this walkthrough uses an Ubuntu VM named web01 in resource group tyf-rg), and Azure CLI 2.50+ logged in with az login. If you need a VM first, follow the Azure VM Configuration lab and come back.

az version --query '"azure-cli"' -o tsv
az account show --query '{sub:name, user:user.name}' -o table

------------------  -------------------------
Pay-As-You-Go       taki@tyfsadik.org

If az account show errors, run az login and, with multiple subscriptions, az account set --subscription <name>, every command after this point acts on whatever subscription is currently selected, and creating a workspace in the wrong sub is a frustrating way to spend an hour.

Set lab variables (bash)

RG=tyf-rg

VM=web01
VMID=$(az vm show -g $RG -n $VM --query id -o tsv)

Step-by-Step Execution

01
Create a workspace and connect the VM

The workspace is the container all telemetry lands in. Create it in the same region as the VM to keep ingestion latency low and avoid cross-region data residency surprises. Workspace names are globally unique, so if tyf-law is taken, append a suffix.

az monitor log-analytics workspace create -g tyf-rg -n tyf-law

Next, capture the workspace resource ID, the query and DCR steps both need it. Note this is the resource ID (/subscriptions/.../workspaces/tyf-law), not the workspace's customer GUID; mixing those two up is the single most common mistake in this lab.

Capture the workspace ID

WID=$(az monitor log-analytics workspace show -g $RG -n $LAW --query id -o tsv)
echo $WID

Now install the Azure Monitor Agent on the VM. On Linux this is the AzureMonitorLinuxAgent extension; on Windows it is AzureMonitorWindowsAgent. The agent alone collects nothing, it just sits there waiting for a rule to tell it what to do.

Install the Azure Monitor Agent extension

az vm extension set -g $RG --vm-name $VM \
  --name AzureMonitorLinuxAgent \
  --publisher Microsoft.Azure.Monitor \
  --enable-auto-upgrade true

The missing piece is the Data Collection Rule. The snippet below creates a minimal DCR with an explicit performance-counter source (streams, sampling frequency, counter specifiers, and a source name are all required fields), a Log Analytics destination, and a data flow binding them. Heartbeat rows are emitted by the agent automatically to the DCR's destinations once the association exists, so the DCR only needs to define the Perf counters. Then we associate the DCR with the VM. In the portal you would point-and-click through "Monitor › Data Collection Rules"; the CLI equivalent (the data-collection rule commands live in the monitor-control-service extension, which the CLI installs automatically the first time you run one):

Create a DCR and associate it with the VM

az monitor data-collection rule create -g $RG -n tyf-dcr \
  --location eastus \
  --log-analytics resource-id=$WID name=law-dest \
  --performance-counters streams=Microsoft-Perf sampling-frequency=60 \
    counter-specifiers='\Processor Information(_Total)\% Processor Time' \
    counter-specifiers='\LogicalDisk(_Total)\% Free Space' name=perf-counters \
  --data-flows streams=Microsoft-Perf destinations=law-dest

DCRID=$(az monitor data-collection rule show -g $RG -n tyf-dcr --query id -o tsv)

az monitor data-collection rule association create \
  -n tyf-dcr-assoc --resource $VMID --data-collection-rule-id $DCRID

How to verify: wait 5-10 minutes (first-time ingestion is not instant), then confirm the agent is reporting in, the Heartbeat table should contain a row for web01. The verification query is in step 02. If the Heartbeat table is empty after 15 minutes, jump to the Troubleshooting section: it is almost always the DCR association.

Two workspace settings worth deciding now rather than later. Retention defaults to 30 days of interactive retention; bump it to 90 for a homelab you want to trend over a quarter. Pricing: the first 5 GB per month of ingestion is free, and a single VM's Heartbeat plus a modest Perf set is well under 1 GB/month, but a chatty Syslog DCR on a busy server is not. Check actual ingestion any time with the query below.

Set 90-day retention and check ingestion volume

az monitor log-analytics workspace update -g $RG -n $LAW --retention-time 90

az monitor log-analytics query -w $WID --analytics-query "
Usage
| where TimeGenerated > ago(1d)
| summarize GB = sum(Quantity) / 1024 by DataType
| order by GB desc"

Common mistake: creating the DCR in a different region than the workspace, or forgetting --location entirely. DCRs are regional resources and the association silently fails to deliver data when the region pairing is wrong, keep workspace, DCR, and VM in one region for this lab.

What this teaches: The agent and the data collection rule are the plumbing; without data flowing in, every query and alert downstream is empty.

02
Query telemetry with KQL

KQL reads like a pipeline: start with a table name, then pipe (|) through operators that filter, shape, and aggregate. The query runs against the whole workspace over the time range you specify, and it is read-only, you cannot damage anything by experimenting. Start with the simplest possible health check: who is heartbeating?

$ az monitor log-analytics query -w $WID --analytics-query "Heartbeat | summarize count() by Computer"
Computer count_ web01 120

Read the query left to right: take the Heartbeat table, then summarize (aggregate) the rows into a count grouped by Computer. One heartbeat row arrives per minute per machine, so 120 rows means roughly two hours of a healthy agent. If your VM name appears here, the entire ingestion chain from step 01 works.

Now a query with real operational value, average CPU per 5-minute bucket over the last hour. This introduces three operators you will use constantly: where filters rows, bin() rounds timestamps into buckets, and render draws a chart in the portal (the CLI ignores it harmlessly).

CPU trend over the last hour

az monitor log-analytics query -w $WID --analytics-query "
Perf
| where TimeGenerated > ago(1h)
| where ObjectName == 'Processor' and CounterName == '% Processor Time'
| summarize AvgCPU = avg(CounterValue) by Computer, bin(TimeGenerated, 5m)
| order by TimeGenerated asc"

Expected output (truncated)

Computer  TimeGenerated                 AvgCPU
web01     2026-09-19T14:00:00Z          12.4
web01     2026-09-19T14:05:00Z          18.7
web01     2026-09-19T14:10:00Z          61.2

Two useful variations to try once the basics work: Heartbeat | summarize arg_max(TimeGenerated, *) by Computer shows the last heartbeat per machine (a classic "is it down?" query), and Perf | distinct CounterName lists exactly which counters your DCR is collecting, which tells you what you are even allowed to alert on.

If your DCR also collects Syslog (add the Microsoft-Syslog stream the same way as Perf), this is the query you reach for during an incident, every error-or-worse syslog line in the last day, counted by facility so noise from one chatty daemon does not drown the signal:

Hunt syslog errors by severity

az monitor log-analytics query -w $WID --analytics-query "
Syslog
| where TimeGenerated > ago(1d)
| where SeverityLevel in ('err', 'crit', 'alert', 'emerg')
| summarize Events = count(), LastSeen = max(TimeGenerated) by Computer, Facility, SeverityLevel
| order by Events desc"

Expected output (illustrative)

Computer  Facility  SeverityLevel  Events  LastSeen
web01     auth      err            14      2026-09-21T03:12:44Z
web01     daemon    err            3       2026-09-21T02:58:01Z

Fourteen auth/err rows on a VM that should see no failed logins is exactly the kind of thing worth a follow-up: drill in by replacing the summarize line with | project TimeGenerated, HostName, ProcessName, SyslogMessage to read the raw messages. This query-to-drilldown loop, aggregate to find the anomaly, then project to read the raw rows, is the core workflow in both Azure Monitor and Sentinel.

One more query you will reuse forever: disk space. A full disk is the most common cause of "the server is up but the app is dead," and the % Free Space counter (LogicalDisk object) catches it early. This version shows the worst disk per machine over the last day:

Lowest disk free space per machine, last 24 hours

az monitor log-analytics query -w $WID --analytics-query "
Perf
| where TimeGenerated > ago(1d)
| where ObjectName == 'LogicalDisk' and CounterName == '% Free Space'
| where InstanceName != '_Total'
| summarize MinFree = min(CounterValue) by Computer, InstanceName
| order by MinFree asc"

Expected output (illustrative)

Computer  InstanceName  MinFree
web01     /             71.3
web01     /mnt          98.9

If MinFree for a real workload ever trends down week over week, that trend line is your capacity plan, and it is exactly the kind of condition you would later turn into a scheduled-query alert at 15% free.

Common mistakes: (1) the CLI defaults to a 24-hour lookback and a 10-minute query timeout, for big workspaces pass --timespan PT1H explicitly; (2) table and column names are case-sensitive in some operators, so heartbeat may not match Heartbeat; (3) the AMA-supported specifier is \Processor Information(_Total)\% Processor Time on both OSes, verify the ObjectName with distinct before hardcoding; (4) quoting: the query lives inside double quotes in bash, so use single quotes for KQL string literals and escape any embedded double quotes or the shell eats them.

What this teaches: KQL reads as a pipeline of transformations; start broad with take 10, then add filters one at a time.

03
Create an alert with an action group

An alert rule without an action group fires silently, the portal shows it, but nobody gets paged. So we build the action group first. An action group is just a named list of notification targets (email, SMS, webhook, Azure Function) that any number of alert rules can share.

Create an action group that emails you

az monitor action-group create -g $RG -n tyf-admins \
  --short-name tyfadmins \
  --action email ops taki@tyfsadik.org

AG_ID=$(az monitor action-group show -g $RG -n tyf-admins --query id -o tsv)

Now the alert rule itself. This is a metric alert: it watches the host-level Percentage CPU metric that the Azure platform emits for every VM (no agent needed), averaged over 5 minutes, evaluated every minute. If the average exceeds 80%, it fires and calls the action group.

az monitor metrics alert create -g tyf-rg -n cpu-high --scopes $VMID --condition "avg Percentage CPU > 80" --action $AG_ID

Unpack the --condition string, because its grammar trips people up: avg is the time aggregation over the window, Percentage CPU is the metric name exactly as the platform spells it, and > 80 is the threshold. Two flags worth knowing even though we accept the defaults: --window-size (default PT5M, how far back each evaluation looks) and --evaluation-frequency (default PT1M, how often the rule runs). A 5-minute average over 80% smooths out brief spikes while still catching sustained saturation.

For completeness, the log-alert equivalent, this one fires when the VM stops heartbeating, i.e. the machine or agent is down. It runs the KQL from step 02 on a schedule:

Log alert: fire when heartbeat goes missing

az monitor scheduled-query create -g $RG -n heartbeat-missing \
  --scopes $WID \
  --condition "count 'hb' < 1" \
  --condition-query 'hb=Heartbeat | where Computer == "web01"' \
  --evaluation-frequency 5m --window-size 10m \
  --action-groups $AG_ID \
  --severity 2

The two condition flags work as a pair: --condition-query names the KQL (hb=...) and --condition applies the count operator to that name. Embedding the whole query inside the condition string is a common syntax error that fails validation.

Severity is worth a deliberate decision: Azure uses 0 (critical) through 4 (verbose), and the number is what downstream tooling filters on. A sane homelab scheme is Sev 2 for "page me now" (heartbeat missing, disk full) and Sev 3 for "email me in the morning" (CPU warning at 70%). If everything is Sev 0, nothing is, alert fatigue is a real failure mode, and it starts with undifferentiated severity.

One more production habit: an alert processing rule suppresses notifications during planned maintenance so a reboot you scheduled does not page you at 3 a.m. This one mutes the action group every Saturday night:

Suppress alerts during a maintenance window

az monitor alert-processing-rule create -g $RG -n weekend-maintenance \
  --rule-type RemoveAllActionGroups \
  --scopes $VMID \
  --schedule-time-zone "Eastern Standard Time" \
  --schedule-recurrence-type Weekly \
  --schedule-recurrence-start-time "22:00:00" \
  --schedule-recurrence-end-time "06:00:00" \
  --schedule-recurrence Saturday Sunday \
  --description "Planned patch window - do not page"

Three details the CLI is strict about: the rule type is RemoveAllActionGroups (only AddActionGroups and RemoveAllActionGroups exist, RemoveAlerts is rejected), the weekly days go in --schedule-recurrence as space-delimited day names, and the start/end times and time zone are separate flags. Set --schedule-time-zone explicitly or the window is evaluated in UTC and your "Saturday night" lands somewhere else.

How to verify: az monitor metrics alert show -g $RG -n cpu-high should return JSON with "enabled": true and your action group ID under actions. If actions is an empty array, the --action flag did not resolve, echo $AG_ID and re-run. Also confirm the email address in the action group actually received the "you have been added to an action group" confirmation message Azure sends on creation.

Finish with an inventory of everything watching this resource group, so you know exactly what exists before you test it:

List all alert rules in the resource group

az monitor metrics alert list -g $RG -o table
az monitor scheduled-query list -g $RG -o table

Expected output (first command)

Name     Enabled    Severity    Condition
-------  ---------  ----------  -------------------------
cpu-high True                   avg Percentage CPU > 80.0

What this teaches: Rules detect, action groups notify; keeping the two separate lets one signal reach email, SMS, and a webhook without duplication.

Progress So Far

How It Works

Azure Monitor collects two fundamentally different kinds of signal. Metrics are numeric time series sampled on a fixed cadence: CPU percent, disk queue depth, request counts. They are cheap to store, fast to query, and ideal for threshold alerts. Logs are semi-structured records shipped to a Log Analytics workspace: syslog lines, application events, audit entries. They are richer and more expensive, and you query them with KQL. Choosing the right signal for the question is half the skill.

Data gets into the workspace through data collection rules (DCRs), which bind a set of sources to a set of destinations and say exactly which tables to populate. The Azure Monitor agent on the VM reads the DCR and ships matching data. If a query returns nothing, the problem is almost always upstream of the query: the agent is not installed, the DCR is not associated, or you are looking at the wrong time range.

Alert rules separate detection from notification. The rule defines the signal, the threshold, and how often to evaluate; the action group defines who gets told and how (email, SMS, webhook, logic app). One rule can fan out to many action groups, and one action group can serve many rules, which keeps notification policy in one place instead of scattered across rules.

Testing & Validation

An alert you have never seen fire is a hypothesis, not a control. Prove the whole pipeline by deliberately tripping it: generate sustained CPU load on the VM, wait out the 5-minute evaluation window, and watch the notification arrive.

az monitor metrics alert show -g tyf-rg -n cpu-high --query "enabled" -o tsv

The alert should report true. Generate load on the VM and confirm the action group notifies you, proving end-to-end observability.

On the Ubuntu VM, install stress and pin all cores for ten minutes, long enough to push the 5-minute average over 80%:

Run on the VM, saturate the CPU

sudo apt update && sudo apt install -y stress
nproc                       # how many cores to load
stress --cpu $(nproc) --timeout 600 &

While the load runs, watch the metric from your workstation so you can see the average climb in near-real-time (platform metrics are roughly a minute behind):

Watch CPU climb from the CLI

watch -n 30 "az monitor metrics list --resource $VMID \
  --metric 'Percentage CPU' --interval PT1M \
  --query 'value[0].timeseries[0].data[-3:].[timeStamp,average]' -o tsv"

Expected output near the end of the stress window

2026-09-19T15:02:00Z  96.41
2026-09-19T15:03:00Z  97.02
2026-09-19T15:04:00Z  96.87

Within a few minutes of the average crossing 80, three things should happen: the alert's state in the portal flips to Fired, the action group sends the email, and the alert appears under Monitor › Alerts. When stress exits, the rule resolves itself back to healthy and (if the action group includes resolution notifications) you get a second "resolved" message. Keep that stress email, a screenshot of it is your proof the lab worked.

Do not forget the second alert. The heartbeat-missing scheduled query will never fire during a CPU stress test, it fires when telemetry stops. The clean way to trip it is to stop the agent service on the VM for longer than the 10-minute window, then start it again:

Run on the VM, simulate an agent outage

sudo systemctl stop azuremonitoragent
# wait 12-15 minutes - past the 10-minute evaluation window
sudo systemctl start azuremonitoragent
systemctl is-active azuremonitoragent

Expected output

active

While the agent is stopped, the Heartbeat table goes quiet, the scheduled query's count drops below 1, and the log alert fires its own email. This validates the two failure modes independently: bad state (CPU saturated) and no signal at all (agent or machine down). Real outages are usually the second kind.

Final portal checklist before calling the lab done:

  • Monitor › Alerts shows both cpu-high and heartbeat-missing with a Fired-then-Resolved history.
  • Your inbox holds four messages: CPU fired, CPU resolved, heartbeat fired, heartbeat resolved.
  • The Log Analytics workspace's Heartbeat table shows a gap matching your agent stop window, visual proof of what the alert detected.
  • az monitor metrics alert list -g $RG -o table lists both rules with Enabled: True.

One detail worth a look while the emails are fresh: open the "Fired" notification and read the payload. Azure alert notifications follow the common alert schema, and every field you will ever route on in a webhook or Logic App is in there:

What the notification payload contains (abridged)

{
  "schemaId": "azureMonitorCommonAlertSchema",
  "data": {
    "essentials": {
      "alertRule": "cpu-high",
      "severity": "Sev3",
      "monitorCondition": "Fired",
      "firedDateTime": "2026-09-21T15:06:12Z",
      "targetResource": "/subscriptions/.../virtualMachines/web01"
    }
  }
}

The three fields that matter operationally are severity (should this page anyone?), monitorCondition (Fired vs Resolved, a webhook handler must branch on it or you will treat recovery emails as new outages), and targetResource (which machine, when one rule watches fifty VMs).

Visualizing Your Telemetry

Alerts tell you when something broke; a dashboard tells you how the system breathes when it is healthy. The fastest win is pinning an existing query: run the CPU-trend KQL from step 02 in the portal's Log Analytics blade, click Pin to dashboard, and you have a living chart with zero new code. To do it from the CLI, save the query and share it:

Save a query pack entry for reuse

cat > cpu-trend.kql <<'EOF'
Perf
| where TimeGenerated > ago(6h)
| where ObjectName == 'Processor' and CounterName == '% Processor Time'
| summarize AvgCPU = avg(CounterValue) by bin(TimeGenerated, 5m)
| render timechart
EOF

Notice the render timechart operator at the end: in the portal it turns the result table into a line chart automatically. Keep a folder of these .kql files in version control, the queries are the real deliverable of this lab, and they port directly into workbooks, dashboards, and Sentinel analytics rules later.

For a proper multi-panel view, open Monitor › Workbooks, start from the "VM Performance" template, and point it at your workspace. Templates are editable, so replace any default query with your own KQL and the workbook becomes a custom operations dashboard in about ten minutes.

Troubleshooting

  • No data in workspace: enable diagnostic settings / install the Azure Monitor Agent. Check the chain in order: agent extension provisioning state (az vm extension show -g $RG --vm-name $VM -n AzureMonitorLinuxAgent --query provisioningState -o tsv must be Succeeded), then the DCR association (az monitor data-collection rule association list --resource $VMID must be non-empty), then the DCR's destination workspace ID. A missing or misassociated DCR produces total silence with no error anywhere.
  • KQL returns nothing: widen the time range; data ingestion has a short delay. First-time ingestion after installing the agent can take 5-15 minutes. Also remember the CLI query defaults to the last 24 hours, if you are testing against older data, pass --timespan explicitly, and check you are not filtering on a counter name your DCR never collected (Perf | distinct CounterName tells the truth).
  • Alert never fires: verify the condition aggregation window and the action group target. The classic trap is load that spikes to 95% for 30 seconds: a 5-minute average over 80 never trips on that. Either sustain the load or lower the window with --window-size PT1M. Also confirm the alert's scope is the VM resource ID, not the workspace, a metric alert scoped to the wrong resource type evaluates against a metric that does not exist and silently stays healthy.
  • Alert fires but no email arrives: the rule and the notification are separate links. Run az monitor action-group show -g $RG -n tyf-admins and check the emailReceivers array, a typo in the address still deploys cleanly. Check spam, then check Monitor › Alerts in the portal: if the alert is listed as Fired there, the rule is fine and the action group delivery is the broken hop. Test the action group in isolation with az monitor action-group test-notifications create --action-group tyf-admins -g $RG --alert-type metricstaticthreshold, which needs the action group name, the resource group, and a supported alert type like metricstaticthreshold or logalertv2.
  • az monitor log-analytics query fails with "BadRequest" or a path error: you almost certainly passed the workspace's customer GUID or a workspace name where the -w flag expects the full resource ID (/subscriptions/.../workspaces/tyf-law). Re-capture it with the --query id command from step 01. If the error is a 403 instead, your account is missing the Log Analytics Reader role on the workspace.

Quick-reference for the failures you are most likely to hit in this lab.

SymptomLikely causeFix
Queries return no rowsAgent not connected, DCR not associated, or the wrong time rangeRun Heartbeat | take 10 in Logs; if the VM is absent, fix the agent and DCR before touching the query.

Cost Guardrails

Log Analytics bills per GB ingested beyond the monthly free allowance, and a misconfigured DCR (debug-level syslog from a busy host is the classic offender) can turn a learning exercise into an invoice. Two cheap defenses: a daily ingestion cap on the workspace, and an alert on the Usage table itself so you hear about a data flood the same day it starts.

Set a daily ingestion cap of 0.5 GB

az monitor log-analytics workspace update -g $RG -n $LAW --quota 0.5

Understand the trade-off before using a cap in production: when the cap hits, collection stops for the rest of the day, which means your log alerts go blind exactly when something unusual is happening. For a homelab the cap is the right choice; for production, alert on volume instead of capping it:

Alert when daily ingestion exceeds 1 GB

az monitor scheduled-query create -g $RG -n ingestion-spike \
  --scopes $WID \
  --condition "count 'ing' > 0" \
  --condition-query 'ing=Usage | where TimeGenerated > ago(1d) | summarize GB = sum(Quantity) / 1024 | where GB > 1' \
  --evaluation-frequency 1h --window-size 1h \
  --action-groups $AG_ID --severity 3

Check the Azure Cost Management lab for the budget-alert half of this story, workspace caps watch gigabytes, budgets watch dollars, and you want both.

Extension Ideas

  • Build dashboards or workbooks over the same KQL, a workbook turns the CPU-trend query from step 02 into a living report your team can open without touching the CLI.
  • Forward security signals into Microsoft Sentinel: enable the Sentinel solution on this same workspace and your Heartbeat and Syslog tables immediately become hunting material.
  • Add a second severity tier: a warning alert at 70% CPU that only emails, and a critical alert at 90% that also fires a webhook into a chat channel or paging tool.
  • Compare with self-hosted logging in Log Management, rsyslog and logrotate solve the same problem with zero cloud dependency, and knowing both trade-offs is the real skill.

Key Results

  • Centralized VM telemetry in a Log Analytics workspace.
  • Queried metrics and heartbeats with KQL.
  • Created a CPU alert wired to a notification action group.
  • Achieved proactive detection ahead of user impact.

Key Takeaways

  • Ingestion is a chain: agent → DCR → workspace. Data only flows when every link exists, and the Heartbeat table is your end-to-end health check.
  • KQL is a pipeline: table, then where, summarize, bin(), order by. Master those five operators and you can answer most operational questions.
  • Metric alerts are cheap and fast, log alerts are flexible: use platform metrics for thresholds like CPU, and scheduled KQL queries for conditions metrics cannot express, like "no heartbeat in 10 minutes."
  • An alert without a tested action group is decoration: always generate real load and watch the notification arrive before you call monitoring done.
  • Capture resource IDs into variables early: half the failures in this lab come from passing a name or GUID where a full resource ID was expected.

Cleanup

Monitoring resources are cheap but not free, alert rules bill a small monthly fee each, and workspace ingestion costs grow with retention. When you are done experimenting, tear down in dependency order: alerts first, then the DCR association, then the DCR, then the workspace.

Remove everything this lab created

az monitor metrics alert delete -g $RG -n cpu-high
az monitor scheduled-query delete -g $RG -n heartbeat-missing --yes
az monitor alert-processing-rule delete -g $RG -n weekend-maintenance --yes
az monitor data-collection rule association delete -n tyf-dcr-assoc --resource $VMID
az monitor data-collection rule delete -g $RG -n tyf-dcr --yes
az monitor action-group delete -g $RG -n tyf-admins
az monitor log-analytics workspace delete -g $RG -n $LAW --force true --yes

The agent extension can stay on the VM harmlessly once its DCR association is gone, but remove it too if you want a truly clean slate: az vm extension delete -g $RG --vm-name $VM -n AzureMonitorLinuxAgent. Note that workspace deletion has a soft-delete window, if you plan to reuse the name tyf-law soon, either wait out the soft-delete period or permanently purge it from the portal.

Verify cleanup: az resource list -g $RG -o table should no longer show any Microsoft.Insights or Microsoft.OperationalInsights resources from this lab. If a delete fails with a dependency error, you skipped the dependency order, delete the association or alert it names, then retry.

Challenge 1: Join two tables

Goal: Write a KQL query that joins Perf CPU data with Heartbeat to show only reporting VMs.

Hint: Use | join kind=inner (Heartbeat | distinct Computer) on Computer; that is the pattern.

Challenge 2: Alert on sustained CPU

Goal: Create a metric alert that fires when CPU exceeds 80 percent for five consecutive minutes, not on a single spike.

Hint: The aggregation window and the evaluation frequency together define what sustained means.

Frequently Asked Questions

How do I fix 'No data in workspace'?

enable diagnostic settings / install the Azure Monitor Agent. Check the chain in order: agent extension provisioning state (az vm extension show -g $RG --vm-name $VM -n AzureMonitorLinuxAgent --query provisioningState -o tsv must be Succeeded), then the DCR association (az monitor data-collection rule association list --resource $VMID must be non-empty), then the DCR's destination workspace ID. A missing or misassociated DCR produces total silence with no error anywhere.

How do I fix 'KQL returns nothing'?

widen the time range; data ingestion has a short delay. First-time ingestion after installing the agent can take 5-15 minutes. Also remember the CLI query defaults to the last 24 hours, if you are testing against older data, pass --timespan explicitly, and check you are not filtering on a counter name your DCR never collected (Perf | distinct CounterName tells the truth).

How do I fix 'Alert never fires'?

verify the condition aggregation window and the action group target. The classic trap is load that spikes to 95% for 30 seconds: a 5-minute average over 80 never trips on that. Either sustain the load or lower the window with --window-size PT1M. Also confirm the alert's scope is the VM resource ID, not the workspace, a metric alert scoped to the wrong resource type evaluates against a metric that does not exist and silently stays healthy.

How do I fix 'Alert fires but no email arrives'?

the rule and the notification are separate links. Run az monitor action-group show -g $RG -n tyf-admins and check the emailReceivers array, a typo in the address still deploys cleanly. Check spam, then check Monitor › Alerts in the portal: if the alert is listed as Fired there, the rule is fine and the action group delivery is the broken hop. Test the action group in isolation with az monitor action-group test-notifications create --action-group tyf-admins -g $RG --alert-type metricstaticthreshold.

How do I fix 'az monitor log-analytics query fails with "BadRequest" or a path error'?

you almost certainly passed the workspace's customer GUID or a workspace name where the -w flag expects the full resource ID (/subscriptions/.../workspaces/tyf-law). Re-capture it with the --query id command from step 01. If the error is a 403 instead, your account is missing the Log Analytics Reader role on the workspace.
