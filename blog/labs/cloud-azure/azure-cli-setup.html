Azure CLI Setup: Authenticate and Configure Defaults

BeginnerCloud~1 hour
az loginsubscriptionsdefaultsservice principal

You will install the Azure CLI, authenticate, select the right subscription, and set defaults so later commands are short and safe. By the end you will have a reproducible az workflow ready for every other Azure lab.

This is deliberately the first lab in the Cloud & Azure series, because every other lab assumes you can already run az commands against the correct subscription. Getting this foundation right prevents the two most common beginner disasters: deploying resources into the wrong subscription (surprise billing) and typing the same long flags on every command (typos and drift). We will also create a service principal now so that when you reach the DevOps labs you already have a non-human identity ready for CI/CD.

Learning Objectives

  • Authenticate interactively and view your subscriptions.
  • Set the active subscription and default resource group/location.
  • Create a service principal for automation.
  • Time: ~1 hour · Difficulty: Beginner · Prereqs: an Azure account.

Architecture Overview

graph LR You[You] -->|az login| AAD[Microsoft Entra ID] AAD -->|token| CLI[Azure CLI] CLI -->|set subscription| Sub[Subscription] CLI -->|create SP| SP[Service Principal for automation]

The flow is simple but worth understanding. When you run az login, the CLI never sees your password - it opens a browser window where you authenticate directly against Microsoft Entra ID (formerly Azure Active Directory). Entra ID returns an access token and a refresh token, which the CLI caches locally under ~/.azure. Every subsequent command attaches that token to calls against the Azure Resource Manager (ARM) API.

A single Entra ID account can have access to multiple subscriptions (billing and quota boundaries). The CLI always executes against exactly one active subscription at a time, which is why selecting it explicitly - instead of trusting whatever happens to be the default - is a core habit in this lab. Finally, the service principal you create is a second, non-human identity in the same tenant, scoped to only the permissions your automation needs.

Environment Setup

You will need: the Azure CLI (install docs) and an Azure account.

Before you begin: know which subscription you should deploy into to avoid surprise billing. If you only have one, note its name anyway - you will type it in Step 02.

Install the CLI using your platform's package manager rather than a manual download, so updates arrive automatically:

# Windows (elevated PowerShell)
winget install -e --id Microsoft.AzureCLI

# macOS
brew update && brew install azure-cli

# Debian/Ubuntu
curl -sL https://aka.ms/InstallAzureCLIDeb | sudo bash

After installing, open a new terminal session (so the updated PATH is picked up) and verify the installation. The version check confirms the binary runs and shows which components are installed:

$ az version
{ "azure-cli": "2.67.0", "azure-cli-core": "2.67.0", "azure-cli-telemetry": "1.1.0", "extensions": {} }

Anything in the 2.5x-2.6x range is fine for this lab. If az version works, your PATH is correct and you can move on. Common mistake: running the verify command in the same terminal window that was open during the install - the shell caches the old PATH, so it reports az: command not found even though the install succeeded.

Step-by-Step Execution

01
Authenticate

az login starts an interactive OAuth flow. On a machine with a browser it opens your default browser; on a headless server it prints a device-code URL instead. Sign in with the account that owns your Azure subscription. After a successful login the CLI prints a JSON array of every subscription your account can see - read it, because it tells you exactly which subscription landed as the default.

az login
Opens a browser to sign in to Microsoft Entra ID.

Expected output (abbreviated - one object per subscription):

$ az login
A web browser has been opened at https://login.microsoftonline.com/organizations/oauth2/v2.0/authorize [ { "cloudName": "AzureCloud", "homeTenantId": "9b1e5f2a-....", "id": "a1b2c3d4-0000-1111-2222-333344445555", "isDefault": true, "name": "Pay-As-You-Go", "state": "Enabled", "tenantId": "9b1e5f2a-...." } ]

How to verify: run az account show immediately. If it returns subscription JSON (instead of an error like Please run 'az login'), your token cache is working.

az account show --query "{Name:name, Id:id, Tenant:tenantId}" -o table

Common mistake: if your account belongs to multiple Entra ID tenants (for example a work tenant and a personal tenant), az login may sign you into the wrong one. Pin the tenant explicitly with az login --tenant <tenant-id-or-domain>. On a headless Linux box with no browser, use az login --use-device-code and complete the flow from any device.

02
Select the subscription

Even if you only have one subscription, make the selection explicit. Commands like az group create never ask which subscription to use - they silently target whatever is active, and the active subscription persists across terminal sessions. Setting it by name is safer than by ID because a typo in a name fails loudly, while a pasted GUID from the wrong subscription can look plausible.

$ az account list -o table && az account set -subscription "Pay-As-You-Go"
Name IsDefault Pay-As-You-Go True

az account set produces no output on success - silence is normal. Confirm the switch took effect by checking the isDefault flag:

$ az account list -o table --query "[].{Name:name, IsDefault:isDefault, State:state}"
Name IsDefault State --------------- ----------- ------- Pay-As-You-Go True Enabled Visual Studio False Enabled

Common mistake: confusing az account set (chooses which subscription commands target) with subscription permissions. If a subscription shows State: Disabled or is missing from the list entirely, that is a billing or RBAC issue on the account, not a CLI problem - no amount of re-login will fix it.

03
Set defaults to shorten commands

Almost every az command needs a resource group (-g) and often a location (-l). az configure --defaults stores these in ~/.azure/config so you can omit them. This is not just convenience: it makes scripts reproducible and removes a whole class of "forgot the flag, deployed to the wrong region" errors. Note that defaults live on this machine only - a teammate running the same script elsewhere needs the same config or the explicit flags.

az configure -defaults group=tyf-rg location=eastus

The command is silent on success. Read the defaults back to verify they were written:

$ az config get defaults.group defaults.location -o table
Name Value Source ---------------- ------- ------------- defaults.group tyf-rg /home/taki/.azure/config defaults.location eastus /home/taki/.azure/config

How to verify: the real test is behavioral - after Step 04 validation, az group show -n tyf-rg should work without any location or subscription flags. Common mistake: setting a default resource group that does not exist yet. Defaults are just strings; the CLI will not create the group for you, and the first command that relies on the default will fail with ResourceGroupNotFound until you create it (we do that in the validation step).

04
Create a service principal for automation

A service principal lets pipelines authenticate without your personal account. Your interactive login from Step 01 is tied to you as a person - it expires, requires MFA, and should never be pasted into a CI system. The service principal we create here gets the Contributor role scoped to one subscription only, following least privilege: it can manage resources in that subscription but cannot touch billing, other subscriptions, or Entra ID itself.

az ad sp create-for-rbac -name tyf-ci -role Contributor -scopes /subscriptions/$(az account show -query id -o tsv)

The output is shown exactly once. The password field is the client secret - it is not stored anywhere retrievable, so capture it now into a password manager or secret store:

$ az ad sp create-for-rbac -name tyf-ci -role Contributor -scopes /subscriptions/$(az account show -query id -o tsv)
{ "appId": "b2c3d4e5-1111-2222-3333-444455556666", "displayName": "tyf-ci", "password": "EXAMPLE~8xQ~secret~value~shown~once", "tenant": "9b1e5f2a-...." }

The three fields map directly onto a login: appId is the username, password is the secret, and tenant identifies the directory. Verify the principal can actually authenticate before you trust it in a pipeline:

$ az login --service-principal -u b2c3d4e5-1111-2222-3333-444455556666 -p "EXAMPLE~8xQ~secret~value~shown~once" --tenant 9b1e5f2a-.... --query "[].name" -o tsv
Pay-As-You-Go

Log back in as yourself afterwards (az login) so your interactive identity is active for the rest of the lab. Common mistake: leaving the secret in your shell history or a script in a git repo. Clear it from history (history -d <line> or start the command with a leading space) and treat any committed secret as compromised - rotate it with az ad sp credential reset.

All four stages are complete: you hold a cached token for your account, the CLI is pinned to the intended subscription, defaults shorten every future command, and a least-privilege service principal exists for automation. The only thing left is to prove the whole chain works end to end.

Testing & Validation

Validation has two parts: confirm who the CLI thinks you are and where commands will land, then exercise the defaults by creating a real resource. The resource group created here is the same tyf-rg referenced by later labs, so this step doubles as scaffolding.

az account show -o table && az group create -n tyf-rg -l eastus
$ az account show -o table
EnvironmentName IsDefault Name State TenantId ----------------- ----------- ------------- ------- ---------------- AzureCloud True Pay-As-You-Go Enabled 9b1e5f2a-....
$ az group create -n tyf-rg -l eastus
{ "id": "/subscriptions/a1b2c3d4-.../resourceGroups/tyf-rg", "location": "eastus", "name": "tyf-rg", "properties": { "provisioningState": "Succeeded" } }

You should see your active subscription and a created resource group using your defaults. If so, your CLI is ready. Three final checks worth running once, so you know what "healthy" looks like before something breaks in a later lab:

# 1. The resource group exists in the expected region
az group show -n tyf-rg --query "{Name:name, Location:location, State:properties.provisioningState}" -o table

# 2. The service principal's role assignment is active
az role assignment list --assignee b2c3d4e5-1111-2222-3333-444455556666 -o table

# 3. No stale defaults pointing somewhere unexpected
az config get defaults -o table

Check 2 should show exactly one Contributor assignment scoped to your subscription - nothing broader. If any check surprises you, stop and fix it now; every later lab builds on this state.

Troubleshooting
  • az: command not found: the CLI is not on PATH; reinstall or restart your shell.
  • Wrong subscription used: always confirm with az account show before deploying.
  • SP secret printed once: store it immediately in a secret manager; it is not retrievable later.
  • Browser login fails behind a proxy or WAM errors on Windows: bypass the Windows broker with az config set core.enable_broker_on_windows=false, or fall back to az login --use-device-code, which works through any browser on any device.
  • az account set fails with "The subscription ... could not be found": the name is case-sensitive and must match exactly - copy it from az account list -o table, and quote names that contain spaces.
  • Insufficient privileges to create a service principal: your Entra ID role (not your subscription role) controls this. If the tenant restricts app registrations, ask an admin to enable "Users can register applications" or have them create the SP and hand you the credentials.

Key Takeaways

  • az login authenticates you to Entra ID, not to a subscription - always follow it with an explicit az account set and verify with az account show.
  • az configure --defaults stores group/location per machine in ~/.azure/config; it shortens commands but never substitutes for knowing where a command will land.
  • A service principal's secret is displayed exactly once. Capture it immediately, scope it to the smallest possible target, and rotate it if it ever touches a repo or log.
  • Every az mutation silently targets the active subscription - make az account show a reflex before any create or delete.
  • Validate your toolchain once, early: a healthy az version + az account show + az group show baseline makes later failures much easier to isolate.
