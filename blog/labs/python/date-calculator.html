I built a date calculator that performs timezone-aware arithmetic with datetime, timedelta, and the zoneinfo database, correctly handling daylight saving transitions. Using aware datetimes eliminated the off-by-an-hour bugs that plague naive timestamp math.

Objective & Context

Date math is deceptively error-prone: naive datetimes ignore timezones and DST. This lab computes durations and future dates with aware datetimes and zoneinfo, the correctness pattern behind scheduling and log-timestamp normalization.

Learning Objectives

  • Create timezone-aware datetimes with zoneinfo.
  • Add and subtract durations with timedelta.
  • Compute differences between dates correctly.
  • Format output with strftime.
  • Avoid naive/aware mixing bugs and DST off-by-one-hour errors.

Environment & Prerequisites

Prerequisites

  • Python 3.11 with datetime and zoneinfo (standard library)
  • The system tz database available (Linux ships it; Windows may need tzdata)
  • Test cases spanning a DST boundary
  • Assumed skill: basic Python syntax

Step-by-Step Execution

1. Compute a future date in a timezone

from datetime import datetime, timedelta
from zoneinfo import ZoneInfo
now = datetime.now(ZoneInfo("America/Toronto"))
due = now + timedelta(days=30)
print("now:", now.strftime("%Y-%m-%d %H:%M %Z"))
print("due:", due.strftime("%Y-%m-%d %H:%M %Z"))

Expected output:

now: 2026-06-17 09:14 EDT
due: 2026-07-17 09:14 EDT

What this teaches: Attaching ZoneInfo at construction makes the datetime aware from birth; arithmetic then respects DST transitions instead of blindly adding 24-hour days. (Your "now" line shows the current time; the "due" line is exactly 30 days later.)

2. Difference between two dates

python -c "from datetime import date; print((date(2026,12,31)-date(2026,6,17)).days)"

Expected output:

197

What this teaches: Subtracting two dates yields a timedelta whose .days attribute is the calendar difference; no manual month-length math is needed.

3. Format the output

python -c "from datetime import datetime; from zoneinfo import ZoneInfo; d=datetime(2026,6,17,9,14,tzinfo=ZoneInfo('America/Toronto')); print(d.strftime('%Y-%m-%d %H:%M %Z'))"

Expected output:

2026-06-17 09:14 EDT

What this teaches: strftime renders the aware datetime with its zone abbreviation, so the output is unambiguous about which wall-clock time is meant. A fixed datetime is used here (not now()) so the expected output is deterministic; %Z prints empty on a naive datetime, which is exactly the bug this guards against.

How It Works

How It Works

Naive datetimes have no timezone information and aware datetimes do; Python refuses to mix them in arithmetic because the result would be meaningless. Making every datetime aware at creation time eliminates an entire class of comparison bugs.

zoneinfo reads the IANA timezone database, which encodes the full history of DST rules per region. When you add a timedelta across a spring-forward transition, the library adjusts the wall-clock result so 'same time tomorrow' stays correct.

The classic bug this lab prevents is the off-by-an-hour error: computing a deadline with naive datetimes across a DST boundary silently shifts the real instant. Aware datetimes plus timedelta keep the instant stable while the wall clock follows local rules.

Validation & Testing

Add an interval that crosses the spring-forward DST change and confirm the wall-clock result is correct. Pass criteria: aware datetimes used throughout, DST handled by zoneinfo, and day-count differences match a manual calendar check.

Advanced: Troubleshooting
  • Off-by-one-hour: never mix naive and aware datetimes; localize first.
  • zoneinfo missing: install tzdata where the OS lacks the tz database.
  • Wrong DST: use IANA names (America/Toronto), not fixed UTC offsets.

Key Takeaways

  • Always work with timezone-aware datetimes; naive datetimes are a bug source.
  • zoneinfo plus the IANA database handles DST history correctly.
  • timedelta arithmetic on aware datetimes survives DST transitions.
  • Python refuses naive/aware mixing: treat that TypeError as a helpful guardrail.
  • Format with strftime only at the boundary, after all math is done.
