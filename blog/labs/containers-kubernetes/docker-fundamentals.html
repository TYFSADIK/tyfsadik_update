Docker Fundamentals: Run Your First Container

BeginnerContainers~2 hours
Dockerimagesvolumesnetworks

You will install Docker and run, inspect, and persist your first containers. By the end you will understand the difference between an image and a container and keep data alive with volumes.

This lab is the foundation for everything else in the Containers & Kubernetes track. Every later lab - building custom images, wiring containers together with networks, composing multi-service stacks, and deploying to Kubernetes - assumes you are comfortable with the core Docker CLI workflow covered here: run, ps, exec, logs, stop, and rm.

We use the official nginx:stable image because it is small, starts instantly, and serves real HTTP traffic, which gives us something concrete to verify at every step. Everything you learn transfers directly to databases, application servers, and any other image on Docker Hub.

Learning Objectives

  • Run and manage containers from public images.
  • Persist data with named volumes.
  • Inspect container networking and logs.
  • Explain the image / container / volume relationship and the container lifecycle.
  • Debug common failures using ps -a, logs, and inspect.
  • Time: ~2 hours · Difficulty: Beginner · Prereqs: a Linux host with sudo.

Architecture Overview

Three ideas explain almost everything in Docker. A image is the immutable blueprint pulled from a registry such as Docker Hub. A container is a live, isolated process created from that blueprint - you can start many containers from one image. A named volume is storage managed by Docker that outlives any individual container, which is how stateful data survives restarts and rebuilds.

graph LR Reg[(Docker Hub registry)] -->|docker pull| Img[Image] Img -->|docker run| Ctr[Container] Vol[(Named volume)] -->|mount| Ctr You[You] -->|port 8080| Ctr

Follow the arrows as you work through the lab: docker run first pulls the image from the registry if it is not cached locally, then creates and starts the container. The -p 8080:80 flag publishes the container's internal port 80 onto the host's port 8080, which is the path your browser (or curl) takes to reach nginx. The volume mounts into the container's filesystem at a path you choose, so writes to that path land on durable storage instead of the container's throwaway layer.

Mental model: an image is like a class, a container is like an object instantiated from it, and a volume is like an external hard drive you plug into whichever object needs it. Deleting the object never wipes the drive.

Environment Setup

You will need: Docker Engine 24.x (install docs).

Before you begin: add your user to the docker group or prefix commands with sudo.

On a fresh Ubuntu or Debian host, the fastest way to a working engine is Docker's convenience script. It detects your distribution, configures the official apt repository, and installs the engine, the CLI, and containerd in one shot. For production servers, follow the manual repository setup in the official docs instead; the script is ideal for a lab VM.

INSTALL DOCKER ENGINE (UBUNTU/DEBIAN)

sudo apt update
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh

The Docker daemon runs as root and listens on the Unix socket /var/run/docker.sock. By default only root can talk to it, which is why every tutorial tells you to join the docker group. Membership takes effect only on a fresh login session, so either log out and back in or use newgrp to activate it immediately.

RUN DOCKER WITHOUT SUDO

sudo usermod -aG docker $USER
newgrp docker   # or log out and back in

Now verify the install end to end. docker version confirms both the CLI and the daemon are alive (you should see a Client and a Server section). docker run hello-world proves the daemon can pull an image from Docker Hub and start a container from it.

$ docker version --format 'Server: {{.Server.Version}}'
Server: 24.0.7
$ docker run hello-world
Unable to find image 'hello-world:latest' locally latest: Pulling from library/hello-world c1ec31eb5944: Pull complete Digest: sha256:d000bc569937abbe195e20322a0bde6b2922d805332fd6d8a68b19f524b7d21d Status: Downloaded newer image for hello-world:latest Hello from Docker! This message shows that your installation appears to be working correctly.
Verify: if docker version shows only a Client section and then a connection error, the daemon is not running - jump to the Troubleshooting section below. If hello-world prints its banner, you are ready for the lab.

Step-by-Step Execution

01
Run a container

An image becomes a container the moment you run it.

The command below does four things at once. -d runs the container detached so nginx keeps serving in the background instead of tying up your terminal. --name web gives the container a human-friendly handle you will use in every later command (otherwise Docker invents a random name like grumpy_beaver). -p 8080:80 publishes the container's internal port 80 to host port 8080 - without it, nginx would be reachable only from inside Docker's private network. Finally, nginx:stable is the image reference: the stable tag tracks nginx's stable release line, which is safer for repeatable labs than the floating latest tag.

docker run -d --name web -p 8080:80 nginx:stable
Runs nginx detached, mapping host 8080 to container 80.

The first run prints pull progress as each image layer downloads, then a long hex string - the full container ID - once the container is up.

$ docker run -d --name web -p 8080:80 nginx:stable
Unable to find image 'nginx:stable' locally stable: Pulling from library/nginx a2abf6c4d29d: Pull complete a9edb18cadd1: Pull complete 589b7251471a: Pull complete 186b1aaa4aa6: Pull complete b4df32aa5a72: Pull complete a0d0a0d46f8b: Pull complete Digest: sha256:0d17b565c37bcbd895e9d92315a05c1c3c9a29f762b011a10c54a66cd53c9b31 Status: Downloaded newer image for nginx:stable 4f8a1c9e2b7d3a5f6e0c1d2b3a4f5e6d7c8b9a0f1e2d3c4b5a6f7e8d9c0b1a2f3e
$ curl -I http://localhost:8080
HTTP/1.1 200 OK Server: nginx/1.24.0 Content-Type: text/html
Common mistake: forgetting -d leaves nginx running in the foreground and your prompt frozen - press Ctrl+C (which stops the container) or open a second terminal. Verify: curl -I http://localhost:8080 returns 200 OK with Server: nginx.
02
List and inspect

docker ps is your dashboard: it shows every running container with its image, status, published ports, and name. Add -a to also see stopped containers - this is the single most useful flag when debugging, because a container that crashed two seconds after launch is invisible to a plain docker ps.

$ docker ps
CONTAINER ID IMAGE STATUS PORTS a1b2c3 nginx:stable Up 5 seconds 0.0.0.0:8080->80/tcp

For the full picture, docker inspect dumps the container's complete configuration as JSON: mounts, environment variables, network settings, restart policy, and more. Piping it through a Go template with --format (or through jq) lets you pull out exactly one field, which is how you will script against Docker later.

PULL ONE FIELD OUT OF INSPECT

docker inspect --format '{{.State.Status}} | {{.Config.Image}} | {{.HostConfig.RestartPolicy.Name}}' web
$ docker inspect --format '{{.State.Status}} | {{.Config.Image}}' web
running | nginx:stable
Common mistake: panicking when docker ps comes back empty after a reboot or a crash - containers do not restart by default. Verify: the STATUS column says Up; if the container is missing, check docker ps -a for an Exited entry and read its logs (step 04).
03
Persist data with a volume

Volumes keep data when a container is removed, the key to stateful workloads.

Anything a container writes to its own filesystem lives in a writable layer that is destroyed with the container. A named volume is the escape hatch: Docker stores it under /var/lib/docker/volumes/ on the host and mounts it into the container at a path you choose. Here we mount a volume called webdata over nginx's document root, /usr/share/nginx/html, so the site's files survive no matter what happens to the container serving them.

docker volume create webdata && docker run -d --name web2 -p 8081:80 -v webdata:/usr/share/nginx/html nginx:stable
Creates the volume, then starts a second nginx with the volume mounted as its web root on host port 8081.

Now prove persistence. Write a custom page into the volume through web2, confirm it is served, then delete the container entirely and attach the same volume to a brand-new container, web3. If the page is still there, the data lived in the volume - not in the container.

WRITE, DESTROY, REATTACH

docker exec web2 sh -c 'echo "<h1>persisted by webdata</h1>" > /usr/share/nginx/html/index.html'
curl -s http://localhost:8081        # shows our custom page

docker rm -f web2                    # container is gone
docker run -d --name web3 -p 8081:80 -v webdata:/usr/share/nginx/html nginx:stable
curl -s http://localhost:8081        # still shows our custom page
$ curl -s http://localhost:8081
<h1>persisted by webdata</h1>
$ docker volume ls
DRIVER VOLUME NAME local webdata
Common mistake: writing important data inside the container without a volume and losing it on the next docker rm - every docker rm in this lab would have wiped it. Verify: docker volume ls shows webdata, and the custom page survives a full container replacement.
04
Read container logs

Docker captures whatever a container writes to stdout and stderr and stores it per container, so well-behaved images like nginx never need log files on disk. docker logs is how you read that stream. --tail 10 shows the last ten lines, -f follows new output live (like tail -f), and --timestamps prefixes each line with an RFC 3339 timestamp, which is invaluable when correlating events across containers.

docker logs --tail 10 web
Shows the last ten log lines; add -f to follow live.
$ curl -s -o /dev/null http://localhost:8080 && docker logs --tail 2 web
172.17.0.1 - - [17/Jun/2026:14:02:11 +0000] "GET / HTTP/1.1" 200 615 "-" "curl/8.5.0" 172.17.0.1 - - [17/Jun/2026:14:02:19 +0000] "GET / HTTP/1.1" 200 615 "-" "curl/8.5.0"

Hit the server once with curl, then read the log: you should see your own request recorded with your client IP (from Docker's bridge network), the path, and the 200 status. This request-then-log loop is the most basic debugging rhythm in container work.

Common mistake: running docker logs on a container whose app writes to a log file instead of stdout and seeing nothing - the fix is at the image level, not the CLI level. Verify: each curl you issue produces exactly one new access-log line.
05
Shell into a running container

Sometimes reading logs is not enough and you need to look around inside. docker exec starts an additional process inside an already-running container; combined with -it (interactive TTY) and a shell, it drops you into a live session. This is the container equivalent of SSH, without any SSH server installed.

OPEN A SHELL IN THE CONTAINER

docker exec -it web sh
# inside the container:
ls /usr/share/nginx/html
cat /etc/nginx/conf.d/default.conf
exit
$ docker exec -it web sh
# ls /usr/share/nginx/html 50x.html index.html # exit

Use this to check config files, test DNS resolution, or verify which process is PID 1. Remember that any changes you make from inside are ephemeral unless they land on a mounted volume - the whole point of step 03.

Common mistake: assuming bash exists - minimal images (alpine, distroless) ship only sh or no shell at all. Try sh first, and if neither exists the image was never meant to be shelled into. Verify: the prompt changes to # and ls /usr/share/nginx/html lists nginx's default pages.
06
Stop, start, and remove: the container lifecycle

A container is a process with an on/off switch, not a machine you reinstall. docker stop sends SIGTERM and waits (ten seconds by default) before SIGKILL; docker start resurrects a stopped container with all its filesystem changes and port mappings intact; docker rm deletes the stopped container and its writable layer for good. Knowing the difference saves you from rebuilding containers you could have simply restarted.

FULL LIFECYCLE IN FOUR COMMANDS

docker stop web            # graceful shutdown; curl now fails
docker ps -a               # web shows "Exited (0)"
docker start web           # same container back up, port 8080 works again
docker rm -f web           # force-remove even while running
$ docker stop web && docker ps -a --filter name=web
web CONTAINER ID IMAGE STATUS PORTS NAMES a1b2c3 nginx:stable Exited (0) 2 seconds ago web

Note the exit code: Exited (0) means the process shut down cleanly. A nonzero code like Exited (1) or Exited (137) (SIGKILL, often the OOM killer) is your first clue when a container will not stay up. Finish by force-removing the container so later labs start from a clean slate; -f combines stop and remove in one step.

Common mistake: trying docker rm on a running container and getting Error response from daemon: cannot remove container ... container is running - either stop it first or use rm -f. Verify: after docker stop, curl localhost:8080 fails with connection refused; after docker start, it returns 200 again.
07
Inspect container networking

Every container gets its own network namespace and an IP address on one of Docker's virtual networks. Out of the box, containers attach to the default bridge network (subnet 172.17.0.0/16) and can reach the internet outbound, but inbound traffic only arrives through ports you explicitly publish with -p. Understanding this split - internal reachability versus published ports - is what makes container networking click.

LOOK UNDER THE HOOD

docker network ls
docker inspect --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web3
docker network inspect bridge --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
$ docker network ls
NETWORK ID NAME DRIVER SCOPE b2c3d4e5f6a7 bridge bridge local c3d4e5f6a7b8 host host local d4e5f6a7b8c9 none null local
$ docker inspect --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web3
172.17.0.2

Try it: curl http://172.17.0.2 from the host reaches nginx on the container's internal IP without any published port, because the host sits on the bridge too. Other machines on your LAN cannot do this - from the outside, only published ports exist. That default-deny posture is a genuine security feature of the bridge model.

Common mistake: publishing -p 80:80 and expecting containers to talk to each other through it - containers on a network reach each other directly by name or IP, and publishing is only for host/external access. Verify: docker network inspect bridge lists your container under Containers with a 172.17.0.x address.

Testing & Validation

Do not trust that things work - prove each claim with a command. Run through this checklist before calling the lab complete.

1. The service answers HTTP:

curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080

You should see 200. If so, your container is serving traffic and you have completed the lab.

2. The container is actually running (not just recently started and crashed):

STATUS CHECK

docker ps --filter name=web --format '{{.Names}}: {{.Status}}'

Expect web: Up X minutes. An Up time of a few seconds when you started the container long ago means it is crash-looping - check the logs.

3. The volume survived the container swap from step 03:

PERSISTENCE CHECK

curl -s http://localhost:8081     # expect: <h1>persisted by webdata</h1>
docker volume inspect webdata --format '{{.Mountpoint}}'

4. Clean up when you are done, so the containers and volume do not linger into the next lab:

TEARDOWN

docker rm -f web web3
docker volume rm webdata
docker system prune              # optional: reclaim dangling images and stopped containers
Verify: after teardown, docker ps -a lists none of the lab containers and docker volume ls no longer shows webdata. A clean slate is part of the deliverable.
Troubleshooting
  • permission denied on docker.sock: add your user to the docker group and re-login. The full error is permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock. Run sudo usermod -aG docker $USER, then log out and back in (or newgrp docker). Confirm with groups - docker must appear.
  • port already allocated: another service uses 8080; map a different host port. Find the squatter with sudo ss -lntp | grep 8080, then either stop it or pick a free host port, e.g. -p 8090:80. A stale container from an earlier attempt is the usual culprit - check docker ps -a first.
  • data lost on remove: mount a named volume rather than writing inside the container layer. If you already lost data, it is unrecoverable - the writable layer was deleted with the container. Treat this as the lesson it is: anything that matters gets -v name:/path from day one.
  • Cannot connect to the Docker daemon: the error Is the docker daemon running? means the service is down, not your CLI. Check with sudo systemctl status docker, start it with sudo systemctl start docker, and enable it at boot with sudo systemctl enable docker. On VMs that were suspended or rebooted, this is the most common failure of all.
  • container exits immediately after run: a container lives only as long as its PID 1 process. If docker ps is empty but docker ps -a shows Exited (1) 3 seconds ago, the app crashed on startup - read docker logs <name> for the actual error. Exited (137) specifically points to the OOM killer; give the VM more memory or set a --memory limit to see it fail predictably.

Key Takeaways

  • An image is the read-only blueprint; a container is a running instance of it. One image, many containers.
  • -d detaches, --name labels, and -p host:container publishes a port - you will type these three flags more than any others.
  • Container filesystems are disposable by design. Anything that must survive goes in a named volume (-v name:/path).
  • Your debugging trio is docker ps -a (is it up?), docker logs (what did it say?), and docker inspect (how is it configured?).
  • Containers on the default bridge get private 172.17.0.x IPs; only published ports are reachable from outside the host.
  • Exit codes tell the story: Exited (0) is a clean stop, 137 is a kill (often OOM), anything else means read the logs.
